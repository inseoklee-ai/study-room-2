🧿 프로덕션의 벽

LLM을 프로덕션에 배포하는 일은
단순히 모델이 돌아가게 만드는 것과는
차원이 다른 문제 묶음을 던진다
  • LLM은 놀라운 능력을 주지만, 그 대가로 상당한 계산 자원을 요구한다
  • 지연 시간 문제를 끌고 들어온다
  • 규모가 커지면 순식간에 비용을 감당할 수 없게 만든다
💡 자주 간과되는 간극 — 질의 하나로 동작하는 개념 증명과 수천 명을 동시에 감당하는 프로덕션 시스템 사이의 거리.
🚗 비유 — 시제품으로 만든 수제 스포츠카가 있습니다. 시승은 잘 됩니다. 그런데 "이걸 하루 1만 대 팔자"가 되는 순간 전혀 다른 질문들이 쏟아집니다. 부품값이 감당되나? 공장 라인이 밀리진 않나? 고객이 기다리는 시간은?
이 장은 시승용 LLM을 양산 라인에 올릴 때 생기는 문제들만 모은 장입니다.

③ 패턴 26 — 추론 최적화

LLM을 직접 호스팅할 때 모델 추론의 효율을 끌어올린다. 의료 · 금융 · 법률처럼 데이터가 자기 서버 안에 머물러야 하는 경우가 전제입니다.
1연속 배칭 — GPU 코어가 나는 즉시 큐에서 요청을 꺼내 밀어 넣는다
2추측 디코딩 — 작은 모델이 감당할 구간에서는 SLM(패턴 24)으로 다음 토큰 묶음을 계산
3프롬프트 압축 — 프롬프트를 전처리해 짧게 만들어 메모리 사용량을 줄인다
기법저자들의 실측
연속 배칭처리량 약 20배 (개별 106.11초 → 배치 4.60초, 가속 23.07배)
추측 디코딩대략 14.2% 더 빠름
⚠️ 추측 디코딩의 개선 폭은 작은 모델이 올바른 토큰을 예측하는 능력에 크게 좌우됩니다. num_speculative_tokens가 너무 길면 큰 모델만 쓸 때보다 오히려 느려질 수 있습니다.
같은 추측 디코딩이 패턴 24와 26 양쪽에 나옵니다. 책이 의도한 중복입니다.

AI 애플리케이션이 겉보기에는 전통적인 서버 애플리케이션처럼 보일지 몰라도, 전통적인 부하 테스트만으로는 충분하지 않다. 부하 테스트는 400/500 오류 같은 실패 지점을 찾아 주지만, AI 애플리케이션에서는 성능을 더 세밀하게 이해해야 한다.

✅ 대신 필요한 것 — 요청의 5% 이상이 느려지기 시작하는 저하 지점과, 애플리케이션을 그 지점 가까이 밀어붙이는 제약이 무엇인지

⑤ 패턴 28 — 장기 기억

🔒 근본 문제 — LLM 호출은 하나하나가 상태 없이(stateless) 이전 호출과 독립적이다. 챗봇은 이전 대화 턴을 프롬프트 앞에 덧붙이는 방식으로 상태 유지를 흉내 낼 뿐이다.
트랜스포머는 시퀀스 길이에 대해
2차(quadratic)로 확장된다
대화가 2배 길어지면 비용은 4배
기억무엇을 저장검색 기준
작업 기억
Working		지금 세션의 메시지 목록최근 N토큰
일화 기억
Episodic		과거 세션의 메시지 원본주로 최신성
절차 기억
Procedural		지시문과 사용자 프로필이 사용자인가
의미 기억
Semantic		추출한 사실주로 내용 유사도
💡 저자의 권고 — 일반적으로는 일화 기억보다 의미 기억을 쓰는 편이 좋다. 메시지를 통째로 쌓아 두면 검색 지연이 붙고, 캐시 미스로 인한 기억 오류는 원인 추적도 어렵다.
장기 기억은 대화를 다 기억하는 게 아니라 기억할 만한 것만 골라 남기는 기술입니다.
