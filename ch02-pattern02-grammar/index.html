💬 프롬프트는 부탁이다

LLM 출력은 대개 다운스트림 애플리케이션으로 넘어간다. 그쪽은 파싱·검증 없이 응답을 바로 쓰기를 기대한다.

system: "결과를 JSON으로 출력해 줘. 키는 author, title, year."

→ 이건 지켜주면 좋고 아니면 마는 요청이다
Anthropic 같은 일부 제공자는 실제로 이 접근을 권장합니다. 문제는 이 방법이 나쁘다는 게 아니라, 보장이 없다는 것입니다.
여기서 중요한 건 "프롬프트로 하면 틀린다"가 아닙니다. 좋은 모델은 대부분 잘 지켜요. 문제는 "대부분"이라는 말이 프로덕션에서 무엇을 뜻하느냐입니다.

① BNF 문법 + 로짓 프로세서

배커스-나우르 형식(BNF, Backus–Naur Form)으로 구문을 쓰고, 그것을 적용하는 LogitsProcessor를 파이프라인에 넘긴다.

grammar = IncrementalGrammarConstraint(
              grammar_str, "timestamp_literal", pipe.tokenizer)
grammar_processor = GrammarConstrainedLogitsProcessor(grammar)

results = pipe(input_message, max_new_tokens=256,
               do_sample=False,
               logits_processor=[grammar_processor])
  • 루트 요소를 지정한다 → SQL 명세 전체를 넘기면서도 원하는 데이터 타입만 골라 쓸 수 있다
  • 거의 모든 형식·언어에 이미 만들어진 BNF가 있다 — "BNF for [주제]"로 검색
루트 요소 지정이 은근히 실용적입니다. SQL 전체 문법을 넣어두고 "이번엔 TIMESTAMP만", "이번엔 CREATE INDEX만" 하고 뽑아 쓸 수 있어요.

🔍 BNF는 겁먹을 게 없다

"이건 이런 것들로 이루어진다"를 적는 표기법일 뿐이다.

year ::= [1-2][0-9][0-9][0-9] | unk
  ↑        ↑                     ↑
 이름   이런 모양이거나        아니면 unk
📜 읽으면 이렇다 — "연도는 1이나 2로 시작하고 숫자가 3개 더 붙거나, 아니면 unk다."
등록해 두면 모델은
물리적으로 다른 형태를 못 만든다
정규표현식을 읽을 줄 알면 BNF도 읽을 수 있습니다. ::= 는 "~로 정의된다", | 는 "또는"이에요. 이 두 개가 전부입니다.

② JSON 모드 — 가장 쉬운 길

response = client.chat.completions.create(
    model=MODEL_ID, messages=input_message,
    response_format={"type": "json_object"})
⚠️ 필수 조건 — 프롬프트(시스템이든 사용자든)에서 JSON 출력을 원한다고 명시해야 합니다. 그래야 필요한 토큰을 생성합니다.
파라미터만 넣고 프롬프트에 아무 말도 안 하면 동작하지 않습니다. 둘 다 필요해요.
이 조건을 빠뜨려서 헤매는 경우가 많습니다. response_format은 "JSON이 아닌 토큰을 막는" 장치지, "JSON을 만들라"는 지시가 아니에요. 지시는 여전히 프롬프트가 합니다.

③ 스키마 — 구조화된 출력

@dataclass
class LineItem:
    description: str
    quantity: int
    amount: float

@dataclass
class Receipt:
    items: LineItem[]
    total_amount: float

response = client.models.generate_content(
    model='gemini-2.0-flash',
    contents=["Parse the receipt contained in the image", image],
    config={'response_mime_type': 'application/json',
            'response_schema': Receipt})
💡 응답 자체는 여전히 JSON 문자열입니다. Pydantic 객체는 오로지 구조를 지정하는 용도이고, 파싱은 따로 합니다.
여기서 헷갈리기 쉬운데, dataclass를 넘긴다고 dataclass 객체가 돌아오는 게 아닙니다. JSON 문자열이 오고, object_hook으로 파싱해야 객체가 됩니다. PydanticAI 같은 래퍼가 그걸 대신 해주는 거고요.

예제 네 개가 전부 다른 걸 증명합니다. 특히 A와 C를 나란히 보는 게 중요해요.

🔢 예제 A — 산술식

초등 교육 소프트웨어. 답("36")이 아니라 산술식을 생성하게 하고 싶다.

root  ::= (expr "=" ws term "\n")+
expr  ::= term ([-+*/] term)*
term  ::= ident | num | "(" ws expr ")" ws
ident ::= [a-z] [a-z0-9_]* ws
num   ::= [0-9]+ ws
질문응답판정
사과가 총 몇 개?bill_apples + mae_apples = total_apples
3 + 2 = 5		✅ 정확
사과가 오렌지보다 많나?3 + 2 = 5
2 + 4 = 6		❌ 못 냄
두 번째 질문의 정답은 (3+2) > (2+4)입니다. 그런데 문법에 > 가 없어요. 그래서 모델은 식만 나열하고 비교는 하지 못했습니다.

🎭 같은 사실을 뒤집어 읽기

✅ 저자의 해석

문법에 >가 없으니 출력할 수 없다. 제약이 제대로 작동하는 증거.

⚠️ 뒤집으면

문법을 잘못 만들면 모델은 틀린 답을 낼 수밖에 없다. 그것도 아주 그럴듯하게.

📝 객관식 시험지에서 정답 보기를 빼버린 것과 같습니다. 학생은 답을 알아도 고를 수 없어 오답을 찍고, 채점자는 학생이 모른다고 오해합니다.
📑 패턴 1 노트의 "평가 기준을 우리가 느슨하게 만들었다"와 같은 종류의 함정입니다 — 제약을 걸면 결과가 좋아 보이지만, 무엇을 막았는지는 결과에 안 나타납니다.
이게 이 덱에서 가장 중요한 슬라이드입니다. 문법은 강력한 만큼 위험해요. 내가 만든 문법이 정답을 막고 있는지는 반례를 던져보기 전엔 모릅니다.

🔢 예제 B — 문법이 데이터를 정제한다

record    ::= author separator title separator year
author    ::= [a-zA-Z ]* | unk
title     ::= [a-zA-Z ]* | unk
year      ::= [1-2][0-9][0-9][0-9] | unk
unk       ::= "NULL"

악센트·발음 구별 기호가 붙은 비영어 문자를 허용하지 않는다. 다운스트림이 7비트 ASCII를 기대하는 레거시 시스템이라면 결정적이다.

입력출력관찰
Gabriel García Márquez, 1985Gabriel Garcia Marquez | Love in the Time of Cholera |1985악센트 제거
Tirukkural (ྌி்), 연도 정보 상충Valluvar | The Tirukkural |NULL타밀 문자 탈락

제목이 본문에 두 형태로 나오는데 문법에 맞는 건 하나뿐이라 그게 선택됐습니다. 연도는 본문에 상충하는 정보가 있어서 NULL을 골랐고요. 문법이 "모르겠으면 NULL"이라는 탈출구를 열어둔 덕분입니다.

⚠️ 예제 C — JSON 모드의 한계

{"author": "Gabriel García Márquez",
 "title": "Love in the Time of Cholera",
 "year": 1985}
필드가 author·title·year인 것은 제약된 결과가 아니라 GPT-4o-mini 같은 고성능 모델에 의존한 결과입니다.
  • 저자 이름에 악센트가 들어가는지 제약하지 않는다 — 들어갈 때도, 안 들어갈 때도 있다
  • 제목이 영어 문자로만 되도록 제약하지 않는다 — 가끔 타밀어 제목이 반환될 가능성에 대비해야 한다
JSON 모드는 "JSON임"만 보장하고
"무엇이 들어가는지"는 보장하지 않는다
예제 B와 나란히 놓으면 차이가 분명합니다. B는 문법이 실제로 악센트를 제거했고, C는 운에 맡겼어요. 같은 입력, 다른 보장 수준입니다.

📦 예제 D — 보장의 맛

class CurrencyEnum(str, Enum):
    USD = 'USD'; UKP = 'UKP'; INR = 'INR'; EUR = 'EUR'

@dataclass
class Invoice:
    purpose: str
    amount: float
    currency: CurrencyEnum = CurrencyEnum.USD

agent = Agent(model, result_type=Invoice, system_prompt=system_prompt)
response = agent.run_sync(paragraph)   # → Invoice 객체가 보장된다
입력

"Requesting reimbursement for taxi ride to airport. I paid $32.30."

출력
Invoice(purpose='taxi ride to airport', amount=32.3,
        currency=<CurrencyEnum.USD: 'USD'>)
PydanticAI를 쓰면 LLM 비종속적으로 구조화된 출력을 얻습니다. 모델을 바꿔도 이 코드는 그대로예요. 1장에서 본 "LLM 비종속 프레임워크"의 실제 이득이 여기서 나타납니다.

⚖️ BNF vs Pydantic

Pydantic이 나은 점이유
사용 편의성dataclass 몇 줄이 BNF 규칙보다 쉽다
지연 시간BNF는 클라이언트 처리, Pydantic은 서버 처리 → 네트워크 왕복이 준다
모델 지원BNF는 logprobs 접근 필요(보편적이지 않다). 모든 현대 모델이 dataclass 제약을 지원
🔑 그럼에도 BNF가 유연하다 — 스타일 규칙이 단순한 데이터 형식 이상이면 BNF여야 합니다. Enum을 넘어서는 검증은 Pydantic으로 하기 어렵습니다.
<credit_card_number> ::= <visa> | <mc> | <amex>
<visa> ::= "4" <digit>{12,15}
<mc>   ::= ("51".."55" <digit>{14}) | ("2221".."2720" <digit>{12})
<amex> ::= "34" <digit>{13} | "37" <digit>{13}
같은 일을 Pydantic으로 하려면 field_validator로 검증 로직을 직접 써야 하고, 책에 40행 가까운 구현이 실려 있습니다. 더 이상 단순한 dataclass가 아니게 되죠. 참고로 자바스크립트에서는 Zod로 같은 걸 합니다.

✅ 정답 & 해설

A1. 아니다. JSON 모드는 "JSON임"만 보장한다. 필드 이름·문자 집합은 모델 성능에 기댄 결과이고 악센트는 들어갈 때도 안 들어갈 때도 있다. 문자 집합을 보장하려면 BNF가 필요하다.
A2. 정답을 못 낸다. 허용된 토큰만 나오므로 식만 나열하고 비교는 하지 못한다. 제약이 작동한 결과이자, 문법 설계 실수가 오답으로 나타나는 방식이다.
A3. 문법에 막혔는데 공백만 허용된 상태. 공백은 문법이 대개 허용하고 후보에 거의 항상 있어, 다른 길이 다 막히면 공백만 반복된다.
A4. 유연성. 단순한 데이터 형식을 넘는 검증(신용카드 번호 규칙 등)을 표현할 수 있다. 편의성·지연시간·모델 지원은 모두 Pydantic이 낫다.
A5. "어떻게 구현했나요?" — 생성 중에 토큰을 막는지(진짜), 생성 후 LLM을 한 번 더 불러 맞추는지(가짜).
A6. 탈출구를 준다. float | Literal["Unknown"]. 반드시 숫자를 내놓으라고 하면 없는 숫자를 지어낸다.
A4가 은근히 헷갈립니다. BNF가 "더 좋은 것"이 아니라 "더 유연한 것"이에요. 나머지 세 축은 전부 Pydantic이 이깁니다.
