7.1.1 문제

LLM과 API 사이의 간극
멀티모달 LLM은 여러 형태의 콘텐츠를 생성합니다. 리서치 리포트, 번역, 코드 생성에는 그것으로 충분하죠.

🚫 문장과 실행 사이

환불이 처리됐다는 이메일 문구는 생성할 수 있지만
당신 은행 계좌에 돈이 들어오게 만들 수는 없다

✈️ 구체적으로

LLM은 "6월 12일 모리셔스발 이스탄불행 TK 161 항공편 좌석 한 자리를 예약하라"는 문장을 생성할 수 있다.

그런데 어떻게 하면 그 텍스트를 생성하는 데서 그치지 않고, 항공사의 예약 API나 Booking.com·Expedia 같은 여행 중개사를 통해 실제로 항공편을 예약하게 만들 수 있을까?

❓ LLM과 API 사이의 간극을 어떻게 메워야 LLM이 그 API를 호출해 일을 끝낼 수 있을까?
RAG로 지식을 주입할 수는 있지만, 지식이 아니라 행동이 필요한 겁니다.

7.1.2 해법

특별한 토큰을 뱉는다
Tool Calling은 2장 패턴 2 Grammar의 확장입니다.

🔧 작동 원리

LLM은 함수를 호출해야 할 때마다 특별한 토큰을 인자와 함께 내보내도록 학습돼 있다.

모델 출력
항공편을 예약해 주셔서 감사합니다!
[CALL_TOOL: book_flight, TK 161, 2025-06-12, Economy]
당신 코드가 처리
fd = book_flight("TK 161", datetime.strptime("2025-06-12"), "Economy")

프로그램이 함수 이름과 인자를 뽑아내고, 필요한 형 변환(날짜 같은 것)을 한 뒤 호출한다. 반환값은 원래 응답에서 툴 호출이 있던 자리에 끼워 넣어진다.

최종 응답
항공편을 예약해 주셔서 감사합니다!
예약 확인 내역입니다:
{fd.flight_number} {fd.departure_time} … {fd.seat_number}
{fd.payment_method}로 {fd.invoiced_amount}를 청구했습니다.
💡 호출이 실패하면 그 자리에는 적절한 오류 메시지가 대신 들어갑니다. (실제 툴 호출 형식은 보통 JSON입니다 — 위는 설명용 예)
손이 없는 비서에 비유하면 딱 맞습니다. 말할 수만 있고, 전화기는 당신이 듭니다.

🔑 Tool Calling이 열어 주는 것

영역내용
최신 지식RAG는 비교적 정적이고 미리 색인해 둘 수 있는 출처에만 작동한다. 툴은 더 동적 — 현재 뉴스 · 날씨 · 주가
개인화개인 작업 공간(이메일 · 캘린더)에 연결해 응답을 개인화
엔터프라이즈 API사내 검색 엔진, 사내 DB. 제품 정보를 기억에서 떠올리는 데 그치지 않고 최신 상세 정보와 가격을 가져온다
계산계산기 · GIS 분석 · 최적화 솔버
ReActCoT(패턴 13)가 단계를 나열하는 데 그치지 않고 실제로 수행하며, 툴의 응답에 따라 행동을 바꾼다 — reasoning + action
📑 ReAct는 CoT와 Tool Calling의 조합"일 뿐"이므로 이 책에서 별도 패턴으로 두지 않았습니다.
RAG와 툴의 차이가 명확합니다. 미리 색인할 수 있으면 RAG, 지금 물어봐야 하면 툴.

📏 OpenAI 함수 호출 — 5단계

단계누가무슨 일
1당신함수를 짠다 — 외부 API에 위임하고 정형 응답을 돌려주는 book_flight
2당신함수 설명서를 모델에 건넨다 — 함수 자체가 아니라!
3모델 → 당신모델이 "이거 호출해"라고 뱉고, 당신 코드가 실제로 호출
4당신결과를 대화에 붙여 모델을 한 번 더 부른다
5모델결과를 자연어 답변에 녹여 낸다
tools = [{"type": "function", "name": "book_flight",
  "description": "Books a flight using the airline API",
  "parameters": {"type": "object", "properties": {
    "flight_code": {"type": "string",
       "description": "IATA flight code like AA 123"},
    "cabin_class": {"type": "string",
       "enum": ["economy", "premium_economy", "business", "first"]}
  }}}]

response = client.responses.create(model="gpt-4.1",
    input=[...], tools=tools)
💡 모델이 적절한 정형 데이터를 생성할 수 있느냐에 달려 있으므로, 좋은 명명 규칙과 문서화 주석으로 함수를 자기 설명적으로 만드는 것이 중요합니다.
enum을 쓴 것도 2장 Grammar 패턴을 활용한 겁니다.

🔒 3단계 — 모델이 직접 호출하지 않는다

[{
  "type": "function_call",
  "call_id": "call_12345xyz",
  "name": "book_flight",
  "arguments": "{\"flight_code\":\"TK 161\", ...
}]
tool_call = response.output[0]
if tool_call.name == "book_flight":
     args = json.loads(tool_call.arguments)
     result = book_flight(args["flight_code"], ...)   # 당신이 호출
⚠️ 그러면 안전하지 않기 때문입니다(웹 검색이나 샌드박스 코드 실행처럼 지원되는 툴이 아닌 한). OpenAI는 적대적 행위자가 자기 LLM에 임의의 코드를 주입하는 것을 원하지 않습니다!
✅ book_flight() 함수는 당신이 직접 짰으니 신뢰한다고 봐도 될 것입니다 — 그래서 클라이언트 쪽에서 호출합니다.

이용 가능한 항공편 검색, 요금 비교, 여권 정보 추출 등 다른 함수들도 있을 수 있고, LLM은 대화나 워크플로의 맥락에서 호출할 올바른 함수를 고른다 — 이런 단계를 여러 개 묶어 CoT로 엮는 것이 바로 ReAct다.

보안이 설계의 이유입니다. 그래서 "calling"이 "use"보다 정확한 이름이라는 거고요.

⚠️ LLM마다 툴 정의 형식이 다르다

LLM인자를 어디에
OpenAIparameters
Anthropicinput_schema
Llamaparameters지만 정의를 function 키 아래에 한 겹 더 중첩
같은 내용을 세 번 다르게 써야 한다
💡 세 가지가 겹칩니다 — ① LLM 간 차이 ② 에이전틱 유스케이스에서 Tool Calling의 중요성 ③ 프로젝트 도중 LLM을 여러 번 바꾸게 될 가능성
🔑 이 셋 모두가 LLM 비의존적 프레임워크(PydanticAI · LangChain · LangGraph · LiteLLM)로 개발해야 한다는 쪽을 가리킵니다. 다른 선택지가 없는 경우가 아니라면 개발 단계에서 모델 제공자의 클라이언트 API를 직접 쓰지 마세요.
6장 패턴 19(의존성 주입)에서 "LLM에 종속되지 않아야 한다"고 했던 이유가 여기서 구체적으로 드러납니다.

💾 MCP 서버 — 툴을 내놓는 쪽

@mcp.tool()
async def book_flight(flight_code: str, departure_date: datetime,
                      cabin_class: CabinClass, ...) -> BookingData:
    """Books a flight using the airline API
    Args:
        flight_code: IATA airline flight code such as AA 123
        departure_date: Date of departure ...
    Returns:
        Booking confirmation details including booking reference ..."""

docstring이 곧 모델에게 주는 설명서입니다 — OpenAI 2단계에서 적었을 모든 설명이 이제는 함수 정의 자체에 담깁니다.

7.1.3 예제

실시간 날씨 질의응답
"화요일에 시카고에 비가 올까?" 같은 질문에 답합니다. MCP를 쓰되 LangGraph는 쓰지 않습니다.

🌦 두 개의 툴이 필요하다

@mcp.tool()
async def get_weather_from_nws(latitude: float, longitude: float) -> str:
    """Fetches weather data from the National Weather Service API
    for a specific geographic location."""
    points_url = f"https://api.weather.gov/points/{latitude},{longitude}"
    metadata = requests.get(points_url, headers=headers).json()
    forecast_url = metadata.get("properties", {}).get("forecast")
    weather_data = requests.get(forecast_url, headers=headers).json()
    return weather_data.get("properties", {}).get("periods")
❓ 그런데 — 시카고의 위도와 경도는 얼마인가?
@mcp.tool()
async def latlon_geocoder(location: str) -> (float, float):
    """Converts a place name such as "Kalamazoo, Michigan"
    to latitude and longitude coordinates"""
    geocode_result = gmaps.geocode(location)
    return (round(...['lat'], 4), round(...['lng'], 4))
💡 툴 두 개를 이어서 써야 합니다 — 지오코딩으로 좌표를 얻고, 그 좌표로 예보를 받는다. 이 순서를 에이전트가 스스로 추론합니다.
미국 국립기상청 API는 그리드 포인트를 먼저 알아내야 예보를 받을 수 있는 구조입니다.

⚙️ 서버 · 클라이언트 · 퓨샷 예시

if __name__ == '__main__':
    mcp.run(transport="streamable-http")
# Cloud Run · AWS Fargate · Azure Container Instances 에 배포

시스템 프롬프트에 넣은 퓨샷 예시
Question: What's the weather in Kalamazoo, Michigan?
Step 1: The user is asking about Kalamazoo, Michigan.
Step 2: Use the latlon_geocoder tool to get the lat/lon.
Step 3: latitude, longitude is (42.2917, -85.5872)
Step 4: Use the get_weather_from_nws tool at the lat/lon

📑 5장 패턴 13 Few-shot CoT가 여기 그대로 쓰입니다 — 툴을 어떤 순서로 쓸지를 예시로 시연한 것입니다.
단계 번호까지 그대로 따라 하게 만드는 게 CoT의 효과였죠.

7.1.4 고려사항

신뢰성 · MCP 한계 · 프롬프트 인젝션
Tool Calling은 LLM이 툴을 호출해야 한다는 판단을 내리고 그 호출을 생성하는 것에 의존합니다.

🎯 신뢰성 높이기

  • 명확하고 상세한 함수 이름과 파라미터 설명을 쓴다
  • 시스템 프롬프트로 각 함수를 언제 쓸지에 대한 정책을 서술한다 — 항공편을 검색할 때와 예약할 때의 구분, 검색 결과가 얼마나 오래 유효한지
  • 유효한 입력의 예시(항공편 코드 같은 것)를 넣고, Grammar 패턴을 활용하도록 파라미터 타입(enum)을 쓴다
  • 오류가 났을 때는 서술적인 메시지를 돌려줘야 패턴 18 Reflection으로 입력을 고쳐 재시도할 수 있다
함수와 파라미터가 적을수록 모델은 더 정확해진다
2025년 6월 기준 LLM에 따라 3~10개 툴이 한계로 보인다
💡 결정론적으로 이미 알고 있는 정보를 모델이 채우게 하지 마세요. 승객 상세 정보를 이미 알고 있다면 그것을 관리하는 부담을 모델에서 덜어 낼 수 있습니다.
👉 함수가 SQL 같은 DSL을 입력으로 받는다면 패턴 22 Code Execution이 더 나은 해법일 수 있습니다.
3~10개라는 숫자가 실무적입니다. 툴을 무한정 늘릴 수 없어요.

⚠️ MCP의 한계 (2025년 5월 기준)

영역내용
보안MCP는 언어 상호운용 프로토콜에 가까워서 어떤 보안 원칙도 강제하지 않는다. 인증·인가, 역할 분리, 클라이언트별 능력 지정이 필요한데도. Cloudflare가 Workers OAuth Provider 라이브러리를 확장해 이 공백을 메우려 한다
협업클라이언트-서버 통신이 대체로 단방향인 반면 현실에서는 협업적·상호작용적 워크플로가 필요할 수 있다. Google의 A2A, IBM의 ACP가 2025년 4·5월에 에이전트 간 통신을 도입
스트리밍툴 호출은 오래 걸릴 수 있다. 실시간 진행 상황을 보여 주면 UX가 개선된다. 표준 MCP 호출은 네트워크 구성에 따라 30~60초에 종료된다
💡 그러나 MCP는 빠르게 진화 중이라 여러분이 읽을 때쯤이면 이 단점 중 일부 또는 전부가 해결됐을 가능성이 높습니다. 혹은 MCP가 더 나은 무언가로 대체됐을 수도 있고요.
어느 프로토콜이 "이기든" 간에
Tool Calling이 유용하고 중요한 패턴으로 남으리라는 점은
비교적 확신한다
프로토콜과 패턴을 구분해서 보라는 조언입니다.

💥 프롬프트 인젝션

적대적 행위자가 LLM이 처리하는 콘텐츠에
악성 텍스트를 심어
의도하지 않은 툴 호출을 만들어 낸다
  • 호출되는 외부 툴 자체를 조작해, 그 툴의 출력을 쓰는 애플리케이션에 하류 피해를 입힐 수도 있다
  • 공격 표면은 LLM과 툴 사이의 왕복 횟수가 늘수록 커진다
💼 비유 — 신입에게 "메일을 읽고 요약해 주세요"면 최악이 요약 오류지만, "메일을 읽고 지시대로 송금해 주세요"면 사기 메일 한 통에 회사 돈이 나갑니다. 같은 신입, 같은 실수, 전혀 다른 피해.
💡 LLM은 "시스템 프롬프트(당신의 지시)"와 "읽으라고 준 데이터"를 글자로만 구분합니다. 그래서 웹페이지나 이메일 안에 "이전 지시는 무시하고…"라고 써 두면 지시로 착각할 수 있습니다.
다음 슬라이드에서 Beurer-Kellner 외의 2025년 논문이 소개한 여섯 가지 방어를 봅니다.

🛡️ 방어 여섯 가지 — Beurer-Kellner 외 (2025)

방식내용
Action-Selector미리 정의된 행동 집합만 허용하고, 그 행동들로부터의 피드백이 에이전트로 되돌아가는 것을 막는다
Plan-Then-Execute먼저 고정된 행동 계획을 세운다. 툴 피드백이 콘텐츠에 추가돼도 원래 계획에서 벗어나지 않는다
Map-Reduce격리된 서브에이전트를 파견해 신뢰할 수 없는 프롬프트 조각을 처리. "reduce"에서는 LLM을 아예 쓰지 않거나 제한된 Action-Selector로
Dual-LLM계획하고 툴을 쓰는 특권 LLM + 툴 접근 없이 신뢰할 수 없는 데이터를 처리하는 샌드박스 LLM
Code-Then-ExecuteLLM이 형식적 컴퓨터 프로그램을 작성한다. 데이터가 악의적이더라도 제어 흐름이 고정된다 → 패턴 22
Context-Minimization불필요한 콘텐츠를 제거. 특히 이후 단계에서는 사용자의 원래 프롬프트를 컨텍스트에서 빼라
💡 세 부류로 묶으면 — 할 수 있는 일을 미리 못 박기(1·2·5) · 오염된 데이터를 격리하기(3·4) · 보여 주는 것을 줄이기(6)
⚠️ 현대 LLM들이 이 중 하나 이상으로 방어하며 웹 검색·코드 실행을 내장하기 시작했지만, 프롬프트 인젝션으로부터 지키는 일은 여전히 진행 중인 과제입니다.
공통점은 "무엇을 할 수 있는지"를 미리 좁혀 두는 것입니다.
