2.3.1 문제

규칙으로 쓸 수 없는 스타일
앞의 두 패턴은 동적 로직이나 구조화된 규칙으로 스타일을 제어했습니다. 많은 상황에서 뉘앙스를 규칙으로 표현하기는 어렵습니다.

🎯 성립 조건 셋

조건내용
가용한 콘텐츠
available content		원하는 내용은 이미 있지만 원하는 톤·스타일이 아니다 — 내용이 학술 논문에 있는데 비기술직 임원용 마케팅 브로슈어에 쓰고 싶다
미묘한 스타일
nuanced style		뉘앙스를 몇 가지 규칙으로 표현하기 어렵다. 사람도 말로 표현하기 힘들지만 맞는 스타일을 보면 알아본다 — 브로슈어에 파인튜닝은 써도 될까? 강화학습은?
변환 예시
example conversions		전문가가 가용한 콘텐츠를 원하는 스타일로 변환해 놓은 사례가 실제로 있다
💡 세 번째가 이 패턴과 패턴 4를 가르는 조건입니다. 변환 전·후 쌍이 있으면 패턴 3, 결과물만 있으면 패턴 4.
두 번째 조건의 "보면 안다"가 핵심입니다. 규칙으로 쓸 수 있으면 패턴 1·2가 낫고, 못 쓰겠으면 여기로 옵니다.

📝 어디에 쓰나 — 책의 다섯 상황

  • 학술 논문 → 흥미로운 블로그 글 — 복잡한 주제를 일반 용어로. 단 정확성과 핵심 메시지는 보존
  • 일반 회사 콘텐츠 → 브랜드 스타일 가이드 — 표준 헬프데스크 문서를 따뜻하고 친근한 톤으로
  • 소셜 미디어 플랫폼별 변환 — 긴 LinkedIn 글을 X·BlueSky의 짧은 형식이나 Instagram의 시각 중심 스타일로. 핵심 메시지와 브랜드 보이스는 유지
  • 기술 문서 → 숙련도별 — 초급·중급·전문가용으로 나눠 각각에 맞는 용어와 설명으로
  • 메모 → 정식 이메일 — 임원의 짧은 메시지를 정식 메모나 이메일로
공통점 — 내용은 그대로, 옷만 갈아입힌다
다섯 번째가 뒤에 나올 실행 예제입니다. 메모를 이메일로 바꾸는 것.

2.3.2 해법

퓨샷 러닝 · 모델 파인튜닝
입력-출력 예시로 생성 콘텐츠의 스타일을 제어합니다. 이렇게 하면 더 일관된 결과를 얻어요.

① 퓨샷 러닝

프롬프트에 입력과 기대 출력의 예시를 보통 1~10개 넣는다. 예시는 예상 문제 영역과 관련이 있어야 한다.

in_context_examples = [{
    "input_text": "The movie was fantastic!",
    "output_text": """The cinematography was exceptional, with
masterful use of light and shadow to convey emotional depth.""",
}, ... ]

prompt = "Convert the following text into the following style:\n\n"
for ex in in_context_examples:
    prompt += f"Input: {ex['input_text']}\nOutput: {ex['output_text']}\n"
prompt += f"Input: {input_text}\nOutput:"
🎓 학생-교사 관계로 생각하면 됩니다. 교사(당신)가 LLM(학생)에게 예시 몇 개를 보여 주고, 학생이 앞으로의 문제에서 그 예시를 모방하기를 기대하는 것.
1장의 컨텍스트 내 학습이 그대로 쓰입니다. 가중치는 전혀 안 바뀌고 그 요청 안에서만 유효해요.

② 모델 파인튜닝

여러 예시를 기대 출력으로 사용한다. 보통 100개 남짓, 수천 개일 수도. 대응하는 입력과 짝지어 파인튜닝한다. (어댑터 조정, 패턴 15 참고)

✅ 더 높은 충실도

예시 몇 개를 넘어 튜닝할 수 있다. 복잡한 작업에서 특히 — 논문을 브로슈어로 바꾸려면 많은 어휘 매핑을 학습해야 하는데 파인튜닝이 그럴 가능성이 높다

⚡ 더 빠르고 저렴한 추론

모델이 이미 작업에 맞춰져 있어 프롬프트를 최소한으로 줄인다. 예시를 처리할 필요가 없으니 지연이 줄고 비용도 낮아진다

💡 두 장점은 서로를 강화합니다. 많은 경우 퓨샷으로 실패했던 복잡한 작업에 더 작은 모델을 튜닝할 수 있고, 그러면 추론은 더 빠르고 호스팅 비용은 더 낮아집니다.
단점내용
데이터 큐레이션·거버넌스학습 세트를 수집·정제·유지해야 한다
학습 비용스타일이 바뀌면 파인튜닝을 다시 해야 할 수도
학습 전문성핵심 학습 파라미터가 여럿. 파국적 망각 때문에 학습률을 신중히
운영 전문성호스팅·운영에 LLMOps 역량 — 프롬프트에 예시를 넣는 것보다 희소하고 비싼 기술
파국적 망각은 1장에서 본 개념입니다. 미세조정 예시를 과대평가해 기존 지식을 잃는 현상이죠.

⚖️ 퓨샷 vs 파인튜닝 — 선택 기준

퓨샷 러닝파인튜닝
예시 개수1~10개100~수천 개
준비 시간즉시몇 시간~며칠
매 요청 비용비쌈 — 예시를 매번 전송쌈 — 프롬프트가 짧다
속도느림빠름
수정즉시재학습
필요 인력없음AI 엔지니어 + LLMOps
비용이 역전되는 지점이 핵심
퓨샷은 시작이 공짜지만 요청 1건마다 예시 토큰 값을 낸다
파인튜닝 실행 — OpenAI 관리형

글이 짧아진 것보다 플레이스홀더 통일이 실무적으로 훨씬 중요합니다. 프로그램이 다룰 수 있게 됐으니까요.

🎨 확장 — 이미지 스타일 전이

텍스트에 국한되지 않는다. 카스파르 다비트 프리드리히의 「안개 바다 위의 방랑자」 스타일로 스타워즈 포스터를 만든다.

pipe = StableDiffusionControlNetImg2ImgPipeline.from_pretrained(
        "stable-diffusion-v1-5/stable-diffusion-v1-5",
        controlnet=controlnet, torch_dtype=torch.float16)

depth_estimator = pipeline("depth-estimation")
depth_image = depth_estimator(image)["depth"]      # 깊이 맵

output = pipe("Star Wars' Darth Vader with a red light saber",
              image=wanderer_image, control_image=wanderer_depth_map)
📏 왜 제어 이미지(control image)를 주나? 전통적 신경망 스타일 전이는 공간 배치와 깊이 관계를 왜곡합니다. 깊이 맵이 "거리 관계는 건드리지 마"라고 못 박아 줍니다. (가까운 픽셀은 희고 먼 픽셀은 어둡다)
🎭 결과 — 방랑자가 다스 베이더로 바뀌었지만 공간 원근·인물 자세·배경이 보존됐고 지팡이는 라이트세이버가 되어 같은 위치에 있습니다. 다만 창의성도 생겼습니다 — 먼 지평선의 우주선, 그리고 원작과 달리 관람자를 향해 선 인물. 원치 않으면 스타일 이미지와 콘텐츠 프롬프트의 상대 가중치를 조절합니다.
실무 교훈은 이겁니다. 스타일의 어떤 측면이 중요한지 따로 지정할 수단이 있으면 결과가 훨씬 좋아집니다. "스타일"이라고 뭉뚱그리면 색감과 붓터치만 흉내 내고 구도는 날아가요.

📏 준수에 영향을 주는 세 요인

요인내용
큰 모델이 더 좋다오픈소스든(Llama, Qwen) 클로즈드소스든 예시를 잘 외삽하지만 파라미터가 많은 모델이 일반화를 더 쉽게 한다. 결과가 나쁘면 ① 예시를 검토 ② 예시를 늘림 ③ 더 큰 모델로. 단 프로덕션에선 파라미터 수 ↔ 추론 비용·지연의 지속적 트레이드오프
컨텍스트의 한계예시를 넣으면 입력 토큰이 늘어난다. 많이 넣을수록 실제 프롬프트에 쓸 여유가 줄고, 너무 많으면 예시의 "메시지"가 묻히거나 예시들끼리 서로 모순돼 모델이 "혼란"에 빠진다
추론 속도입력이 길면 더 긴 컨텍스트에 어텐션을 적용해야 하므로 지연이 커진다. 결국 인컨텍스트 러닝은 같은 베이스 모델이라도 파인튜닝 모델보다 느리다
💡 컨텍스트 한계나 속도 저하를 겪는다면 — 컨텍스트 엔지니어링을 고려하거나 최적의 예시를 선별하거나, 어댑터 조정(5장)으로 넘어가세요. 좁은 작업에서는 더 작은 LLM을 파인튜닝해 큰 모델과 동등한 성능을 내는 경우가 많습니다.
마지막 문장이 중요합니다. LLM 애플리케이션이 실시간으로 사용자를 응대한다면 이 점이 결정적일 수 있어요.
