4.4.1 문제

단순 RAG가 무너지는 다섯 지점
RAG는 복잡한 정보 검색 작업에서 효과가 떨어집니다. 이유가 다섯 가지예요.

❌ 다섯 지점

문제내용과 예
컨텍스트 윈도 제약한 번의 검색에 담을 토큰 수가 제한돼 불완전한 컨텍스트가 된다 — "기후변화 완화 전략의 경제적 영향을 개발도상국과 선진국에 걸쳐 비교하라"는 여러 나라·전략·경제 모델·시간 축을 단일 윈도에 담기 어렵다
질의 중의성초기 발견을 근거로 질의를 다듬을 장치가 없다. 패턴 10은 중의성을 알아차리는 데서 그쳤다 — 조치는 되묻기뿐. 그런데 한쪽이 훨씬 그럴 법하다면?
정보의 낡음과 검증미리 색인된 정보에 의존하는데 그것이 낡을 수 있고, 최신성·정확성을 검증할 장치가 없다
추론 깊이의 한계문서에 명시적으로 존재하는 정보에 국한된 얕은 추론 — "선형 어텐션 트랜스포머를 엣지 디바이스 실시간 영상 처리에 쓴다면?"은 문서를 따로따로 가져오되 개념을 연결하지 못한다
멀티홉 질의검색과 생성이 단 한 단계뿐 — "MIT 최신 양자 ML 논문의 알고리즘 구현에 가장 적합한 언어는?"은 논문 식별 → 알고리즘 이해 → 언어 판단의 3단을 요구한다
두 번째가 패턴 10과 이어집니다. 뉴캐슬 예제에서 되묻기까지만 갔던 걸 여기서는 추론으로 밀고 갑니다.

4.4.2 해법

검색 → 사고 → 생성, 그리고 루프
충분히 좋은 답을 찾거나 시간·비용 예산이 소진될 때까지 반복합니다.

🔄 전통적 RAG를 세 방식으로 넘어선다

기존검색 → 생성
→
Deep Search검색 → 사고 → 생성
↶
그리고반복
1검색과 생성 사이에 사고(thinking) 단계를 추가해 어떤 정보를 더 모아야 하는지(모을 필요가 있는지) 판단한다
2검색이 한 번이 아니라 여러 단계의 검색과 생성을 반복한다
3기업 지식 베이스에만 의존하지 않고 검색 엔진과 기업 API 같은 도구를 써서 능동적으로 지식을 모은다
💡 대부분의 구현은 매번 원래 질의를 되풀이하는 대신 반복 사이에 상태를 유지합니다. 갱신된 질의로 추가 정보를 묻고, 그 응답이 상태에 덧붙습니다. 최종 응답은 전체 컨텍스트로 종합됩니다.
파란 단계들은 전부 파운데이션 모델에 프롬프트를 넣어 구현할 수 있습니다. 새로운 모델이 필요한 게 아니에요.

✅ 다섯 문제가 어떻게 풀리나

문제반복 아키텍처의 답
컨텍스트 윈도 제약여러 컨텍스트 윈도에 걸쳐 처리한다. 상태를 유지해 지식을 점진적으로 축적하고, 핵심 통찰만 남기고 덜 관련된 정보는 버린다
질의 중의성질의 분해와 정제로 명확화하는 하위 질의를 만든다. 초기 결과를 해석해 빈틈을 찾는다
정보의 낡음·검증사고 단계에 사실 확인과 신뢰도 점수를 통합. 실시간 출처를 포함해 교차 확인하고 근거 없는 정보를 삭제할 수 있다
추론 깊이다단계 추론을 수행하고 서로 다른 결과를 연결하며 이후 검색을 이끄는 중간 결론을 생성한다
멀티홉 질의초기 반복의 발견을 이후 검색을 지시하는 데 쓴다 → 여러 지식 도메인을 가로질러 점을 잇는다
전부 "한 번에 안 되면 나눠서 여러 번"이라는 하나의 아이디어에서 나옵니다.

🧠 사고 — 빈틈을 찾아 후속 질문으로

종합된 답 (발췌)

제1차 라이베리아 내전의 원인은 복잡하고 다면적이며 역사적 요인, 직접적 도화선, 지역적 불안정에서 비롯한다 …

사고 단계가 식별한 후속 질문
1사회경제적 격차는 서로 다른 민족 집단의 자원·교육·기회 접근이라는 측면에서 구체적으로 어떻게 나타났는가?
2시에라리온과 코트디부아르의 분쟁 같은 지역적 불안정이 무기 확산과 전투원 모집이라는 측면에서 어떻게 기여했는가?
3반란에 불을 지핀 새뮤얼 도 정권의 구체적인 인권 유린과 정치적 탄압을 상술할 수 있는가?
💡 세 질문 모두 첫 답에 이미 등장한 단어를 파고듭니다 — "사회경제적 격차", "지역적 불안정". 사고 단계가 자기 답을 읽고 얕은 부분을 짚은 것입니다.
💬 이 기법은 챗봇 설계에서 흔히 쓰입니다. 시각적 인터페이스는 보통 후속 질문을 칩(chips), 즉 클릭 가능한 버튼으로 제시합니다.
우리가 챗봇에서 흔히 보는 "이런 것도 물어보세요" 버튼이 사실 이 메커니즘입니다.

🎵 오케스트레이션 — 재귀로 보고서를

@dataclass
class Section:
  query: str
  answer: str
  sections: list['Section']      # 하위 절 — 재귀 구조

def create_section(query):
  pages = search_wikipedia(query)
  ranked = rank_pages(query, pages)[:3]
  for page in ranked: add_relevant_text(query, page)
  return Section(query, synthesize_answer(query, ranked), [])

def add_subsections(parent):
  for follow_up in identify_gaps_and_followups(parent.query, parent.answer):
    parent.sections.append(create_section(follow_up))

def deep_search(query, depth, report=None):
  if report is None: report = create_section(query)
  add_subsections(report)
  if depth > 1:
    for section in report.sections:
      deep_search(section.query, depth-1, section)
  return report
💡 depth 하나로 보고서의 깊이를 통제합니다. 이게 시간·비용 예산의 실질적 손잡이예요.
각 질의와 그 답이 보고서의 한 절이 되고, 후속 질문이 하위 절이 됩니다.
