9.3.1 문제

환각을 어떻게 알아채나
환각이 생기는 이유부터 짚습니다.

📉 환각률은 떨어지고 있다

❓ 환각이란 — LLM이 실제 세계나 입력 컨텍스트와 맞지 않는 부정확하거나 말이 안 되거나 날조된 내용을 생성하는 것.

왜 생기나 — LLM은 본질적으로 통계적 토큰 생성기다. 자기가 생성하는 것의 의미를 모르며, 실제 지식이 없는 상태에서 만들어 낸 응답은 사실과 맞지 않을 수 있다.
Vectara 측정 (상위 25개 LLM · 텍스트 요약)가장 좋은 LLM25번째
2024년 12월1.3%4.1%
2025년 4월0.7%2.4%
넉 달 만에 전반적으로 40~50% 하락
⚠️ 그러나 더 제약적이거나 복잡한 상황에서는 여전히 문제다.

예를 들어 LLM으로 이미지에서 숫자를 뽑는데 이미지 하나가 뭉개져 있다면? 응답을 숫자로 제약한다면(패턴 2 Grammar) 환각된 숫자가 돌아온다.
📑 패턴 2의 그림자 — 2장에서 "문법이 정답을 막을 수 있다"고 경고했던 문제가 여기서 다시 나옵니다. 숫자만 허용하면 모델은 "모르겠다"고 말할 자리가 없어 반드시 숫자를 지어냅니다.
제약이 안전장치이면서 동시에 위험 요인이 되는 지점입니다.

🔢 깨끗한 입력에서도 문제는 남는다

이미지에서 추출한 필드의 정확도는
90~97% 수준
💳 즉 청구서나 영수증에서 뽑아낸 숫자의 3~10%가 환각이라는 뜻이다!
📈 그리고 복리로 불어난다 — 데이터 추출 결과를 다른 LLM 호출의 입력 컨텍스트로 넘기면 오류 발생 확률이 복리로 불어난다 — 오류 탐지 · 정정을 갖춰 두었더라도. LLM 호출 체인이 복잡할수록 응답이 환각일 가능성은 커진다.
📑 7장의 계산이 여기서도 — 패턴 23에서 본 0.958 ≈ 66%와 같은 구조입니다. 각 단계가 아무리 좋아도 곱하면 무너집니다.
1발상 — 서로 아주 다른 방식으로, 겹치지 않는 데이터셋에서 학습된 LLM 셋으로 응답을 생성해 서로 비교한다면? 응답이 서로 다르면 환각일 가능성이 높다
2그런데 프런티어 모델들의 학습 데이터셋은 상당히 많이 겹친다 — 그런 LLM 셋을 구하기 어렵다
3게다가 여러 LLM으로 추론하면 비용도 곱절이 된다
LLM 응답 하나만 보고
환각 위험 지점을 짚어 낼 방법은 없을까?
직관은 "응답의 변동성을 쓴다"인데, 그 변동성을 한 응답 안에서 찾아야 합니다.

📏 9.3.2 해법 — logprobs 읽기

많은 LLM은 생성한 토큰과 함께 그 토큰의 logprobs(로그 확률, logits라고도 한다)를 제공한다. logprobs로부터 특정 토큰이 정답 토큰일 확률을 계산할 수 있다.

확률 = elogit
상황확률
생성된 토큰이 압도적인 1순위100%에 가깝다
가능성이 여럿인 상황"이긴" 토큰이 정답일 확률이 더 낮게 나온다
OpenAI — logprobs와 상위 후보 5개를 함께 요청
message = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[ ... ],
        logprobs=True,
        top_logprobs=5
    )
response_text = message.choices[0].message.content
logprobs = message.choices[0].logprobs
for token_info in logprobs.content:
   token = token_info.token
   logprob = token_info.logprob
   probability = math.e ** logprob
   if token_info.top_logprobs:
      for alt_token in token_info.top_logprobs:
          if alt_token.token != token:
             alt_probability = math.e ** alt_token.logprob
1장과 2장에서 다룬 개념이 여기서 실제로 쓰입니다.

🇹🇷 logprobs가 어떻게 움직이나

프롬프트
What year was Ataturk born? Answer in one sentence.
응답
Ataturk was born in 1881.
🔢 1881은 두 개의 토큰 — 188과 1. 모델은 이 답에 상당히 확신하고 있다. 1980년대나 1830년대, 1930년대에 태어났다는 다른 후보들의 확률은 전부 0에 가깝다.
⚠️ 그렇다고 낮은 확률이 전부 의심스럽다는 뜻은 아니다
문장 시작 토큰확률
At… ("Ataturk was born…")58%
Must… ("Mustafa Kemal Atatürk was born…")다음 후보
💡 At 토큰의 확률이 왜 58%밖에 안 될까? 다음 후보가 Must라는 점이 단서를 줍니다 — "Mustafa Kemal Atatürk was born in 1881."도 이 질문에 대한 정답이기 때문입니다. 정답이 여러 갈래였을 뿐, 틀린 게 아닙니다.
🔍 움라우트의 흔적 — 성(姓)의 ü 위에 붙는 움라우트가, 두 번째 자리의 두 번째 후보 토큰이 at인 이유를 설명해 줍니다 — 이름의 세 번째 토큰 자리에 움라우트가 올 수 있도록 자리를 비워 두는 것이죠.
그림 9-4의 (a)와 (b)가 이 두 경우를 보여 줍니다.

🔒 움라우트가 드러낸 학습 데이터

📌 각주 2 — 저자의 추론

토큰 확률로부터 합리적으로 추론하자면, OpenAI가 모델을 학습시킨 이 터키 정치가 관련 문서의 98.4%가 이름에서 움라우트를 빠뜨렸다는 뜻이다.
이런 종류의 학습 데이터 유출이야말로
일부 독점 모델이
logprobs 제공을 거부하는 이유일지도 모른다
🔬 왜 그런가 — 이름을 움라우트로 표기한 문서가 단 하나뿐이었다면, 생성된 응답에 움라우트가 한 번도 나오지 않더라도 — 그 문서가 모델 학습에 쓰였다는 증거가 되기 때문입니다.
📑 이 패턴의 근본적 제약 — 9.3.4에서 저자가 다시 짚습니다. 모든 모델이 logprobs에 접근을 허용하지는 않습니다. 그 이유가 기술적 한계가 아니라 영업 비밀 보호라는 것이 이 각주의 통찰입니다.
💡 2장 패턴 1(로짓 마스킹)의 「주의사항」에서도 같은 제약을 언급했습니다 — logprobs에 의존하는 모든 기법이 공유하는 한계입니다.
확률 숫자 하나에서 학습 데이터 구성을 역추론한다는 발상이 흥미롭습니다.

❌ 모델이 찍고 있을 때

이번에는 모델이 환각하는 상황을 보자. 이 오류가 고쳐지지 않았기를 기대하며 일부러 오래된 모델(GPT-3.5-turbo)을 쓴다.

🔍 이유는 짐작할 만하다

그래서 프로그램 이름과 배우 이름의 확률이 낮게 나온 것이다 — 이 지점에서 모델은 사실상 찍고 있다.

🔬 환각을 식별하기 — 거짓 양성을 조심하라

✅ 기본 발상 — 모델이 비슷하게 그럴듯한 선택지 여럿 중에서 골라야 할 때 logprobs가 낮은 토큰을 내놓는다. 그러니 logprobs에 임계값을 걸고 낮은 확률을 환각 가능성의 지표로 삼을 수 있다.
⚠️ 다만 거짓 양성을 조심하라 — 아타튀르크 예가 보여 주듯, 정답인데도 확률이 낮은 토큰이 섞이는 정당한 이유가 있다.
접근내용
관심 토큰을
특정하기		특정 토큰의 logprobs만 검사한다. 구조화된 출력을 생성할 때는 검증해야 할 핵심 값의 위치를 알아낼 수 있으므로 그 토큰들만 검사하는 것이 가능한 경우가 많다
생성 시퀀스를
표본으로 뽑기		확률이 낮은 토큰을 만날 때마다 시퀀스 생성(2장 패턴 1)을 쓴다. 여러 시퀀스를 생성해 답이 모두 일치하는지 검증한다.
→ 아타튀르크 예라면 문장 시작은 서로 달라도 두 생성 모두 출생 연도가 1881이라는 데는 합의했을 것. 두 생성의 임베딩을 비교하면 답이 실질적으로 같은지 견줄 수 있다

9.3.3 예제

영수증 숫자 보정
식당에서 서명된 영수증을 처리하는 소프트웨어입니다.

🧾 네 숫자와 체크섬

팁이 일반적이고 식사에 세금이 붙는 나라의 식당. 영수증마다 청구액 · 세금 · 팁 · 총액 네 개의 숫자를 뽑아야 한다.

✅ 네 값 모두 추출

312.32, 28.76, 60, 401.08
총액이 체크섬 역할을 한다 — 나머지 세 숫자로 총액을 계산해 추출된 값이 맞는지 확인할 수 있다
⚠️ 하나 누락

312.32, 28.76, , 400
(네 번째 이미지가 뭉개져서) 셋만 뽑을 수 있었다면 — 누락된 숫자를 LLM에게 추정해 채우게 하고 싶다
프롬프트
You are a helpful AI assistant that helps parse restaurant receipts.
I will give you a set of parsed values containing the following on
each line:
billed_amount, tax, tip, paid_amount

If tax is missing, calculate it as 9.21% of the billed_amount.
If the tip is missing, calculate it as
   (paid_amount - billed_amount - tax).
If the paid_amount is missing, calculate it as
   (billed_amount + tax + tip).
Do not add any headers or explanations.
📌 각주 3 — 저자가 인정하는 한계 — 이건 다소 억지스러운 예다. 실제로는 수학 계산에 LLM을 쓰지 않는다 — 계산기 도구를 붙여 준다(7장 패턴 21). 다만 LLM 결과의 정확성을 자동으로 평가할 수 있다는 장점 때문에 이 예를 골랐다.
다른 유형의 생성에서도 같은 효과가 나타나지만 책에서 보여 주기가 훨씬 어렵다고 합니다.

🔢 줄마다 가장 낮은 신뢰도를 붙인다

parse_result(response_text=message.choices[0].message.content,
             logprobs=message.choices[0].logprobs)
def parse_result(response_text, logprobs) -> pd.DataFrame:
   csv_file = StringIO(response_text)
   result_df = pd.read_csv(csv_file, header=None,
                  names=['billed_amount','tax','tip','paid_amount'])
💡 모델은 내용과 함께 logprobs도 돌려준다. 반환된 각 토큰을 그것이 등장한 줄과 연결해, 그 줄에서 가장 신뢰도가 낮은 토큰을 계산할 수 있다.
line_no = 0
confidence_of_line = 1.0
last_col_no = len(result_df.iloc[0]) - 1
for token_info in logprobs.content:
    token = token_info.token
    logprob = token_info.logprob
    probability = (2.718281828459045 ** logprob)
    confidence_of_line = min(confidence_of_line, probability)
    result_df.iloc[line_no, last_col_no] = confidence_of_line
    if '\n' in token:   # 다음 줄
       line_no = line_no + 1
       confidence_of_line = 1.0
📑 min()을 쓰는 점을 보세요 — 한 줄에서 가장 자신 없었던 토큰이 그 줄의 점수가 됩니다. 9.3.2에서 "최솟값은 과대평가할 수 있다"고 했지만, 줄 단위로 짧게 끊었으므로 여기서는 적절합니다.
정규화가 필요한 것은 긴 시퀀스일 때입니다.

✅ Self-Check보다 간단하면서도 많은 상황에서 꽤 효과적인 방법은, 모델에게 빠져나갈 구멍을 명시적으로 주는 것입니다.
1학습 데이터 밖의 질문을 받으면 "모르겠습니다"라고 답하라고 시킨다
2구조화된 출력(패턴 2 Grammar)을 생성할 때는 필드를 유니온으로 모델링해 그중 한 갈래를 "모른다"로 둔다
currency_rate: float | Literal["Unknown"]
📑 9.3.1의 문제를 정면으로 푸는 코드입니다 — "응답을 숫자로 제약하면 환각된 숫자가 돌아온다"고 했죠. "모른다"를 허용된 값에 넣으면 모델은 더 이상 지어낼 필요가 없습니다.
📚 RAG에서 특히 유용하다 — Self-Check는 RAG에서 데이터가 서로 모순될 때를 짚어 내는 데 아주 유용합니다.

검색된 두 청크가 서로 상충하면, 생성된 응답의 logprobs는 생성 경로가 둘이었음을 드러냅니다. 어느 쪽이 선택됐든, logprobs를 보고 문제 소지가 있는 답을 골라낼 수 있습니다.
⚠️ 물론 경로가 둘이라고 해서 반드시 충돌은 아닙니다 — 두 경로가 같은 답으로 이어졌을 수도 있습니다(아타튀르크 예처럼). 거짓 양성을 줄이려면 9.3.2의 더 견고한 접근들을 쓰면 됩니다.
🔒 근본적 제약 — 2장 패턴 1의 「주의사항」에서 논한 대로, 모든 모델이 logprobs에 접근을 허용하지는 않습니다.
가장 간단한 해법을 먼저 제시하는 것이 이 절의 미덕입니다.
