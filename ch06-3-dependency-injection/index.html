6.3.1 문제

GenAI 앱은 테스트하기 어렵다
일반 소프트웨어보다 GenAI에서 더 절실한 이유가 있습니다.

❌ 테스트하기 어려운 세 이유

이유내용
비결정적이다대부분의 API나 통계 모델과 달리 정확히 같은 입력으로 호출해도 매번 다른 출력이 나온다 → 합성 입력을 넣고 기대 출력과 대조하는 방식으로 검증할 수 없다
모델이 빠르게 바뀐다업그레이드 일정을 알 수 없는 모델 위에 짓는다. 날짜 기준으로 고정하면 버전은 못 박지만 역량 향상의 이득을 놓친다. 프롬프트가 길고 상세할수록 기반 기술의 변화에 더 취약
LLM에 종속되지 않아야둘 이상의 환경(온프레미스와 구글, AWS와 Azure)에서 쓰려면 여러 모델에서 동작해야 한다. 프레임워크(PydanticAI · LangChain)가 코드는 이식 가능하게 만들어 주지만 프롬프트를 이식 가능하게 만들어 주지는 않는다
특히 어려운 것은 LLM 호출의 체인
한 모델의 출력이 다음 모델의 입력 컨텍스트에 박힌다
❓ 체인의 각 단위를 서로 독립적으로 어떻게 개발하고 테스트할 것인가?
이 질문을 붙들고 예제로 넘어갑니다.

6.3.2 예제

마케팅 문구 개선 — 두 단계 체인
O'Reilly 책의 마케팅 설명문을 LLM으로 개선합니다. 패턴 13 CoT와 패턴 18 Reflection을 결합한 예이기도 합니다.

① 1단계 — 비평 생성

@dataclass
class Critique:
    target_audience: List[str]
    improvements: List[str]

def critique(in_text: str) -> Critique:
    prompt = """You are an expert marketer for technology books.
    Identify the target audience by roles (eg: Data Analyst)
    Suggest exactly 5 ways that the *marketing description*
    can be improved ...
    Do not suggest improvements to the book itself."""
    agent = Agent(GEMINI, result_type=Critique)
    return agent.run_sync([prompt, in_text]).data

『Machine Learning Design Patterns』에 대한 응답

대상 독자: 데이터 과학자, 머신러닝 엔지니어, AI 연구자
제안 5가지: ① "데이터 과학자" 대신 더 구체적인 직함 ② 실용적 응용과 업무 효율 개선 부각 ③ 확장성·유지보수성 강조 ④ 트러블슈팅·디버깅을 다루는 절을 포함하라 ⑤ 추천사·지지 문구 추가

💡 맞는 것처럼 보입니다. 그런데 정말 맞는가?
구조화된 출력(2장 패턴 2)을 쓴 것에도 주목하세요. Critique이 데이터클래스입니다.

🧪 1단계 테스트하기

🚫 결과를 "눈으로 대충 보고" 판단하는 데 기대고 싶지 않습니다 — 이것을 비하해서 바이브 체킹(vibe checking)이라고 부릅니다.

사람의 피드백 — 명시적(좋아요/싫어요)과 암묵적(제안 목록을 보여 주고 어느 것을 고르는지 보는 것) — 은 제품 설계에서 나름의 자리가 있지만, 그래도 테스트 스위트로 코드의 정확성을 테스트하고 싶습니다.

def assert_critique(critique: Critique):
    assert len(critique.improvements) > 3, "Should have 4+ improvements"
    assert len(critique.target_audience) > 0, "Should have 1+ role"
📑 더 뉘앙스 있는 검사에는 패턴 17 LLM-as-Judge를 쓸 수 있습니다. 예컨대 네 번째 제안은 뒤표지가 아니라 책 자체에 내용을 추가하라는 권고처럼 읽힙니다 — 프롬프트가 "Do not suggest improvements to the book itself"라고 했는데도요.
📅 단언 코드를 정기적으로 실행하는 테스트 스위트에 넣어 두세요 — 배포 전마다, 혹은 커밋할 때마다.
지시를 어긴 제안이 섞여 들어온 걸 사람 눈으로 잡았습니다. 이런 걸 자동으로 잡으려면 LLM-as-Judge가 필요하죠.

② 2단계 — 제안 구현

@dataclass
class Improvement:
    change: str
    reason: str
    modified_marketing_description: str

def improve(marketing_text: str, c: Critique) -> Improvement:
    prompt = """... Pick one change from the list that best meets:
    - does not require changing the book itself
    - will make the book much more appealing
    - requires only 1-5 lines to be changed
    ... {marketing_text} {c}"""
    agent = Agent(GEMINI, result_type=Improvement)
    return agent.run_sync(prompt).data
⚠️ 이 함수의 입력 중 하나가 1단계에서 생성된 Critique 객체입니다.

응답

변경: "데이터 과학자" 대신 더 구체적인 직함 사용
이유: 대상 독자에 ML 엔지니어와 AI 연구자가 포함되므로 … 한 줄만 수정하면 되고 책 자체를 바꿀 필요가 없다
새 설명문: … 머신러닝 엔지니어와 AI 연구자가 흔한 문제를 다루도록 돕는 …

다시 한번, 맞는 것처럼 보입니다. 그런데 정말 맞는가?

⚠️ 그런데 여기서 문제가 생깁니다. 두 번째 단계에 넘길 Critique 객체를 얻으려면 1단계의 LLM을 반드시 호출해야 합니다.
def improvement_chain(a_text):
    a_critique = critique(a_text)        # ← LLM 호출이 강제된다
    improved = improve(a_text, a_critique)
    assert_improvement(improved, a_text, a_critique)

6.3.3 해법

목으로 갈아 끼우기
2단계를 개발·테스트하는 동안 1단계를 하드코딩된 결과를 반환하는 목 구현으로 대체합니다.

🔧 핵심 — 함수를 인자로 받게

다른 구성 요소를 개발·테스트하는 동안
LLM 호출과 외부 도구를 가벼운 목으로 대체하라
def improvement_chain(
      in_text: str,
      critique_fn: Callable[[str], Critique] = critique,
      improve_fn: Callable[[str, Critique], Improvement] = improve
        ) -> Improvement:
    c = critique_fn(in_text)
    assert_critique(c)
    improved = improve_fn(in_text, c)
    assert_improvement(improved, in_text, c)
    return improved
💡 이 체인은 이 함수들에 의존한다(depends). 체인을 호출할 때 다른 구현 — 여기서는 목 — 을 주입한다(inject). 이것이 이 패턴의 이름이 된 이유입니다.
✅ 기본값이 진짜 critique() 함수이므로 체인의 기본 동작은 두 단계 모두 LLM을 호출하는 것입니다 — 평소 사용에는 아무 변화가 없습니다.
기법이 이것뿐입니다. 기본값을 둔 함수 인자 하나로 끝나요.

    print(f"Using mock to critique text")
    return Critique(

        improvements = """
Use more precise language to define the problems the book solves.

Include testimonials from data scientists...
        """.strip().split('\n'))
# 체인에서 진짜 대신 목을 쓴다
improved = improvement_chain(mldp_text, critique_fn=mock_critique)
💡 시그니처가 같아야 합니다 — str을 받아 Critique를 반환. 그래야 갈아 끼울 수 있습니다.
📑 이 목 하나로 2단계를 몇 번이고 빠르게·공짜로·똑같은 입력으로 테스트할 수 있게 됩니다.
비결정성·비용·지연이 한꺼번에 사라집니다. 그게 목의 값어치죠.

📌 파이썬 assert의 성질

상황동작
-O 플래그로 실행모든 단언이 꺼진다 → 코드 자체를 바꾸지 않고 개발 중엔 켜고 프로덕션에선 끌 수 있다
Pytest 환경assert 문이 데코레이트되어 단언이 실패한 호출 스택의 상세 정보를 제공한다
같은 코드가 —
개발에선 엄격하게, 프로덕션에선 가볍게
💡 그래서 체인 안에 assert_critique, assert_improvement를 그대로 넣어 둬도 프로덕션 성능에 부담이 없습니다.
파이썬을 쓴다면 이 성질을 알고 쓰는 것과 모르고 쓰는 것의 차이가 큽니다.

⚠️ 6.3.4 고려사항

항목내용
목 함수 vs 목 객체여기서는 목 함수를 예로 들었지만 추상 클래스와 상속으로 목 객체를 만들 수도 있다. 자기가 쓰는 언어(Go · TypeScript)에서 관용적인 방식으로 하라
목 값을 잡기 어려울 때단계 사이의 상호작용이 늘어날수록 하드코딩된 목 값을 제대로 잡기 어려워진다. 예제에서는 제안들이 충분히 일반적이어서 하드코딩된 지시문이 다양한 책에 잘 통했다. 그렇지 않으면 어떤 목 객체를 반환할지 고르는 일 자체가 난제가 된다
외부 함수도LLM 호출 외에도, 개발·테스트 중에 네트워크 지연과 서비스 가용성에 휘둘리지 않도록 외부 함수를 목으로 대체할 수 있다
💡 두 번째가 실무적 한계입니다 — 목이 현실을 대표하지 못하면 테스트를 통과해도 프로덕션에서 깨집니다.
목을 너무 특수하게 만들면 그 목에만 맞는 코드가 됩니다. 균형이 필요해요.

출처기여

⚠️ 그러나 과학 배경에서 온 많은 AI 엔지니어들은 이를 모릅니다.
집필 시점에
Dependency Injection을 네이티브로 지원하는
GenAI 프레임워크는 없다
💡 Pydantic이 근접해 있습니다 — 프롬프트와 도구를 에이전트에 의존성 주입할 수 있지만, 에이전트 자체를 주입하지는 못합니다. 저자들은 이것이 바뀌기를 바란다고 적었습니다.
🔧 즉 지금은 직접 손으로 구현해야 합니다. 다행히 기법이 단순해서 부담은 크지 않습니다.
참고문헌이 하나뿐인 이유가 있습니다. 새로운 아이디어가 아니라 잊힌 아이디어를 가져온 거예요.

💡 일반 소프트웨어보다 GenAI에서 더 절실한 이유

이유설명
비결정적같은 입력에 매번 다른 출력 — 기대값 비교 테스트가 원천적으로 안 됨
비싸고 느림테스트 한 번 돌릴 때마다 API 요금과 네트워크 지연
모델이 바뀜내가 안 고쳤는데 어제 되던 게 오늘 깨짐
🏭 비유 — 자동차 조립 라인에서 2번 공정만 시험하고 싶은데, 2번은 1번이 만든 부품이 있어야 돌아갑니다. 1번을 매번 돌리자니 느리고 비싸고, 게다가 나올 때마다 부품이 조금씩 다릅니다. 그래서 미리 만들어 둔 표준 부품 하나를 넣고 2번만 시험합니다.
그 표준 부품이 목(mock)이다
세 이유 모두 일반 소프트웨어에는 없거나 약한 문제입니다. 그래서 GenAI에서 이 패턴의 값어치가 더 큽니다.
