패턴 17 심판자 LLM — 요약

❌ 문제

GenAI의 과업은 열린 결말이라 평가가 어렵다. 성과 측정은 교란 변수가 많고, 사람 평가는 확장이 안 되고, 자동 지표(BLEU·ROUGE)는 의미·뉘앙스·사실 정확성을 못 잡는다

✅ 해법

채점 기준을 만들어 LLM에게 적용시킨다. 세 방식 — 프롬프팅 / ML / 파인튜닝

쥐덫은 쥐를 몇 마리 잡았는지 세면 되지만
마케팅 콘텐츠는 그럴 수가 없다
⚠️ 세 가지 버릇 — ① 같은 글에 점수가 흔들린다 ② 웬만하면 다 A를 준다 ③ 자기가 쓴 글을 유난히 좋아한다

상세 → 패턴 17 덱

이 패턴은 2장 패턴 5, 4장 패턴 10, 5장 패턴 14·16에서 이미 평가 단계로 계속 쓰였습니다. 여기서 제대로 다룹니다.

패턴 18 리플렉션 — 요약

❌ 문제

웹 인터페이스에서는 후속 질문으로 고치게 할 수 있는데, API 호출은 무상태다. 어떻게 비평에 반응해 고치게 할 것이며, 비평을 자동으로 생성하려면?

✅ 해법

한 번이 아니라 두 번 이상 호출한다 — 생성 → 평가자에게 → 비평으로 프롬프트 수정 → 재생성

💡 17번과의 관계 — LLM-as-Judge는 점수를 내고, 리플렉션은 그 점수에 "그래서 어떻게 고치라는 건데?"를 붙여 되돌려 보냅니다. 리플렉션의 평가자 자리에 LLM-as-Judge를 꽂는 것이 가장 흔한 구성입니다.
💡 평가를 LLM이 해야 할 이유는 전혀 없고, 하물며 콘텐츠를 생성한 그 LLM이 해야 할 이유는 더더욱 없습니다. 외부 도구여도, 사람이어도 됩니다.

패턴 19 의존성 주입 — 요약

❌ 문제

GenAI 앱은 비결정적이고, 모델이 빠르게 바뀌고, LLM에 종속되지 않아야 한다. 체인의 각 단위를 어떻게 독립적으로 테스트하나?

✅ 해법

어느 단계든 같은 시그니처의 목(mock)으로 갈아 끼울 수 있게 만든다

🔧 기법은 하나뿐 — 함수를 인자로 받게 만들면 됩니다. 기본값은 진짜 LLM 호출, 테스트할 때만 목을 넘깁니다.
💡 소프트웨어 공학에서는 오래된 패턴이지만 과학 배경에서 온 많은 AI 엔지니어들은 이를 모릅니다. 그리고 집필 시점 기준 이를 네이티브로 지원하는 GenAI 프레임워크가 없습니다.

패턴 20 프롬프트 최적화 — 요약

❌ 문제

파운데이션 모델을 바꾸면 프롬프트 시행착오를 전부 다시 해야 한다. 애플리케이션이 기반 LLM 변화에 매우 취약해진다

✅ 해법

한 겹의 간접 계층을 더한다 — 프레임워크가 프롬프트 변형을 주입해 가며 데이터셋 위에서 자동 최적화

"컴퓨터과학의 모든 문제는
한 겹의 간접 계층을 더하면 풀 수 있다"
💡 네 구성 요소 — 파이프라인(단계들) · 데이터셋(예제, 하나여도 됨) · 평가자(LLM-as-Judge) · 옵티마이저(DSPy 등)
🔑 핵심 이득 — 코드 자체에는 프롬프트가 들어 있지 않습니다. LLM 버전이 바뀌면 파이프라인을 다시 돌리기만 하면 됩니다.
