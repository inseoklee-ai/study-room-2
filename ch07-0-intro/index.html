패턴 21 툴 호출 — 요약

❌ 문제

"TK 161 좌석 한 자리 예약"이라는 문장은 생성할 수 있는데, 어떻게 실제로 예약하게 만드나? LLM과 API 사이의 간극

✅ 해법

LLM이 특별한 토큰과 인자를 뱉으면, 클라이언트 후처리기가 실제로 호출하고 결과를 되돌려 준다

모델은 "무엇을 호출할지 말할 뿐"
실제 실행은 언제나 당신 코드가 한다
🔒 왜 나눠 두나 — 모델에 전화기를 직접 쥐여 주면 누가 모델을 속였을 때 무슨 짓을 할지 모릅니다. 그래서 "말하는 쪽"과 "실행하는 쪽"을 일부러 분리해 뒀습니다.

상세 → 패턴 21 덱

ReAct — 추론과 행동을 교차시키는 것 — 는 CoT와 Tool Calling의 조합"일 뿐"이라 별도 패턴으로 두지 않았습니다.

패턴 22 코드 실행 — 요약

❌ 문제

그래프를 그릴 때 API를 부르지 않는다 — Matplotlib이나 Mermaid로 명세를 작성한다. 호출할 함수가 DSL로 된 긴 구문을 받으면 Tool Calling으로는 부족하다

✅ 해법

LLM이 DSL 코드를 생성하고, 샌드박스 안의 후처리기가 그것을 실행할 시스템에 보낸다

🍳 비유 — ① 메뉴판에서 고르기("2번 세트, 매운맛") = Tool Calling ② 레시피를 적어 주방에 넘기기("이 재료를 이 순서로, 이 온도에서") = Code Execution. 표현할 수 있는 게 무한합니다.
⚠️ 대신 위험이 커집니다 — 코드는 무엇이든 할 수 있으니까요. 반드시 샌드박스에서 돌립니다.

상세 → 패턴 22 덱

데이터베이스를 갱신할 때는 LLM이 데이터 무결성을 지켜 주길 기대하는 것보다 SQL을 생성해 하나의 트랜잭션으로 보내는 편이 쉽습니다.

💡 프롬프트 인젝션 — LLM은 "시스템 프롬프트(당신의 지시)"와 "읽으라고 준 데이터"를 글자로만 구분합니다. 공격자가 웹페이지나 이메일 안에 "이전 지시는 무시하고…"라고 써 두면 모델이 그걸 지시로 착각할 수 있습니다.
🔒 공격 표면은 LLM과 툴 사이의 왕복 횟수가 늘수록 커집니다. 그래서 "무엇을 할 수 있는지"를 미리 좁혀 두는 것이 최선의 방어입니다.

🌹 이름이 다르다고 다른 것은 아니다

Tool Calling의 바탕이 되는 기법을 처음 만든 연구자들은 그것을 Toolformer라고 불렀다. 이 책은 패턴을 만든 사람들이 붙인 이름(CoT, ToT, Grammar 등)을 그대로 지켜 왔지만, Toolformer라는 이름은 끝내 자리 잡지 못했다.

부르는 곳이름
Andrew Ng · AnthropicTool Use
OpenAI · GeminiFunction Calling
이 책Tool Calling
💡 저자들의 선택 이유 — tool이 더 일반적이어서 API와 원격 프록시까지 아우른다. 그리고 calling이 use보다 더 서술적이다 — LLM은 함수 이름과 인자를 생성만 하고 실제 호출은 클라이언트 코드가 해야 한다는 점을 상기시켜 주기 때문.
이름 하나에 이 패턴의 핵심 설계가 담겨 있다는 게 재미있습니다.
