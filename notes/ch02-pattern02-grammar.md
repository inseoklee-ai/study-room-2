## 1. 패턴 1과 무엇이 다른가

**하는 일은 똑같다.** 규칙에 안 맞는 후보 토큰의 확률을 0으로 만드는 것. 차이는 **누가 하느냐**다.

| | 패턴 1 로짓 마스킹 | 패턴 2 문법 |
|---|---|---|
| **실행 위치** | 내 코드 (클라이언트) | **모델 서버** |
| **속도** | 느림 — 매 토큰 왕복 | 빠름 |
| **표현력** | **아무 로직이나** | 형식 · 스키마만 |
| **모델 지원** | 제한적 (로짓 접근 필요) | **거의 전부** |
| **보장** | 100% | 100% |

### 비유 — 시험장의 감독관

- **로짓 마스킹** — **내가** 학생 옆에 앉아 직접 감시한다. 어떤 규칙이든 적용할 수 있지만, 내가 계속 붙어 있어야 하고(지연), 학생이 답안을 보여 주는 걸 허락해야 한다(로짓 접근).
- **문법** — **시험장에** 규칙을 등록해 두면 감독관이 알아서 막아 준다. 훨씬 편하지만 **등록 가능한 형태의 규칙**만 된다.

책이 쓰는 정의는 **문맥 자유 메타구문(context-free metasyntax)**이다. 메타구문이란 실제 *내용*에는 제약을 거의 두지 않고 **허용되는 구조와 구성**만 형식적으로 기술하는 방식. 그래서 "무슨 말을 하라"가 아니라 **"어떤 모양이어야 한다"**를 지정한다.

## 2. 문제 — 부탁의 3가지 죄

LLM 출력은 대개 **다운스트림 애플리케이션**으로 넘어간다. 그 애플리케이션은 파싱·검증 없이 응답을 바로 다루기를 기대한다.

순진한 접근(안티패턴)은 프롬프트에 형식을 쓰고("JSON으로 출력해 줘") LLM이 **따라 주기를 바라는** 것이다. Anthropic 등 일부 제공자는 이 접근을 권장하지만, **지시 이행 능력에 의존**하는 것은 이렇다.

| 죄 | 내용 |
|---|---|
| **취약함**(brittle) | LLM 버전이 바뀌면 깨질 수 있다 |
| **불안정함**(unstable) | LLM 생성은 확률적(stochastic)이다 |
| **비쌈**(expensive) | 지시를 잘 따르는 것은 보통 **더 큰 모델**이다 |

### 이걸 안티패턴으로 만드는 결정적 한 문장

> **"LLM 호출을 소비하는 모든 쪽이, LLM이 지시를 안 따를 가능성에 대비해야 한다."**

이 절에서 가장 실무적인 문장이다. "JSON으로 줘"라고 부탁하면 그것을 받는 **모든 코드에** try-catch와 검증 로직이 들어간다. 문법을 쓰면 그게 전부 사라진다. **이게 진짜 이득이다.**

패턴 1의 「부탁 → 일부 차단 → 전면 차단」 축에서, 문법은 **일부 차단을 서버에 위탁한 지점**에 있다.

## 3. 해법 — 세 가지 방법

모델은 토큰 단위로 생성하며 각 지점에서 후보 집합을 만들고 고른다. 일부 제공자·프레임워크는 **이 후보에 적용할 문법을 지정**하게 해 준다. 문법이 허용하지 않는 토큰의 **확률을 0으로** 만든다.

### 3-1. 방법 1 — BNF 문법 + 로짓 프로세서

**배커스-나우르 형식(BNF, Backus–Naur Form)**으로 구문을 쓰고, 그것을 적용하는 `LogitsProcessor`를 파이프라인에 넘긴다.

```python
grammar = IncrementalGrammarConstraint(grammar_str, "timestamp_literal", pipe.tokenizer)
grammar_processor = GrammarConstrainedLogitsProcessor(grammar)

results = pipe(input_message, max_new_tokens=256, do_sample=False,
               logits_processor=[grammar_processor])
```

- 제약을 만들 때 문법의 **루트 요소**(`"timestamp_literal"`)를 지정한다. → SQL 명세 전체를 넘기면서도 **원하는 데이터 타입이나 명령만 골라** 쓸 수 있다.
- 거의 모든 형식·프로그래밍 언어에 **이미 만들어진 BNF**가 있다. `"BNF for [주제]"`로 검색하면 정규표현식, SQL `TIMESTAMP`·`CREATE INDEX`, CSV 한 행 등이 나온다.

**BNF가 무섭게 생겼지만** "이건 이런 것들로 이루어진다"를 적는 표기법일 뿐이다.

```
year ::= [1-2][0-9][0-9][0-9] | unk
  ↑        ↑                     ↑
 이름   이런 모양이거나        아니면 unk
```

"연도는 1이나 2로 시작하고 숫자 3개가 더 붙거나, 아니면 `unk`다." 등록해 두면 모델은 **물리적으로** 다른 형태를 못 만든다.

### 3-2. 방법 2 — 표준 데이터 형식 (JSON 모드)

```python
response = client.chat.completions.create(
    model=MODEL_ID, messages=input_message,
    response_format={"type": "json_object"})
```

**필수 조건** — 프롬프트(시스템이든 사용자든)에서 **JSON 출력을 원한다고 명시**해야 한다. 그래야 필요한 토큰을 생성한다.

### 3-3. 방법 3 — 사용자 지정 스키마 (구조화된 출력)

속성까지 지정하려면 **JSON Schema** 또는 파이썬 `dataclass`(Pydantic)를 쓴다. 많은 모델이 이 기능을 **구조화된 출력(structured output)**이라 부른다.

```python
@dataclass
class LineItem:
    description: str
    quantity: int
    amount: float

@dataclass
class Receipt:
    items: LineItem[]
    total_amount: float

response = client.models.generate_content(
    model='gemini-2.0-flash',
    contents=["Parse the receipt contained in the image", image],
    config={'response_mime_type': 'application/json', 'response_schema': Receipt})
```

응답 자체는 여전히 **JSON 문자열**이다. Pydantic 객체는 오로지 **구조를 지정하는 용도**이고 파싱은 따로 한다.

```python
data_obj = json.loads(response.text, object_hook=lambda args: Receipt(**args))
```

이때 **모델 제공자가 로짓 마스킹을 대신 수행할 책임**을 진다. 스키마를 규칙·로직으로 바꿔 **서버 쪽에서** 처리한다.

### 실무에서 무엇부터?

| | 방법 | 언제 | 난이도 |
|---|---|---|---|
| **①** | **스키마 · dataclass** | **여기서 시작한다.** 실무의 대부분이 여기서 끝난다 | 쉬움 |
| ② | JSON 모드 | 구조는 아무래도 좋고 "JSON이기만 하면" 될 때 | 아주 쉬움 |
| ③ | BNF | SQL·정규식처럼 **진짜 문법**이 필요할 때 | 어려움 |

### ⚠️ 문법 패턴이 **아닌** 것

**LangChain의 XML 파서**는 이 패턴이 **아니다.** 필요한 XML 태그를 만드는 데 **모델의 지시 이행 능력에 의존**하므로, 규격에 맞는 XML을 받는다는 **보장이 없다**.

## 4. 책 예제 네 개가 증명하는 것

| 예제 | 방법 | 증명하는 것 |
|---|---|---|
| **A. 산술식** | BNF | 제약은 확실히 작동한다 — **정답까지 막을 정도로** |
| **B. 파이프 구분자** | BNF | 문자 집합 제한 → 악센트 **자동 제거**, 형식 미달은 `NULL` |
| **C. JSON 출력** | JSON 모드 | 필드 이름은 **보장이 아니라 모델 성능** |
| **D. 인보이스** | dataclass | `Invoice` 객체 수신이 **보장**됨 |

### A. 산술식 — 가장 중요한 관찰

초등 교육 소프트웨어에서 답("36")이 아니라 **산술식**을 생성하게 하려고 문법을 쓴다.

```
root  ::= (expr "=" ws term "\n")+
expr  ::= term ([-+*/] term)*
term  ::= ident | num | "(" ws expr ")" ws
ident ::= [a-z] [a-z0-9_]* ws
num   ::= [0-9]+ ws
ws    ::= [ \t\n]*
```

| 질문 | 응답 | 판정 |
|---|---|---|
| 사과가 총 몇 개? | `bill_apples + mae_apples = total_apples` / `3 + 2 = 5` | ✅ 정확 |
| 사과가 오렌지보다 많나? | `3 + 2 = 5` / `2 + 4 = 6` | ❌ **답을 못 냈다** |

정답은 `(3+2) > (2+4)`인데 문법에 `>`가 **없어서** 모델이 출력할 수 없다.

저자는 이를 *"제약이 제대로 작동하는 증거"*로 제시한다. **맞는 말이지만 뒤집어 읽어야 한다** — 문법을 잘못 만들면 모델은 **틀린 답을 낼 수밖에 없고, 그것도 아주 그럴듯하게 낸다.** 객관식 시험지에서 정답 보기를 빼 버린 것과 같다. 학생은 답을 알아도 고를 수 없어 오답을 찍고, 채점자는 학생이 모른다고 오해한다.

### B. 파이프 구분자 — 문법이 데이터를 정제한다

```
record    ::= author separator title separator year
author    ::= [a-zA-Z ]* | unk
title     ::= [a-zA-Z ]* | unk
year      ::= [1-2][0-9][0-9][0-9] | unk
unk       ::= "NULL"
separator ::= "|"
```

이 문법은 **악센트·발음 구별 기호가 붙은 비영어 문자를 허용하지 않는다.** 다운스트림이 7비트 ASCII를 기대하는 레거시 시스템이라면 결정적이다.

| 입력 | 출력 | 관찰 |
|---|---|---|
| *Gabriel García Márquez*, 1985 | `Gabriel Garcia Marquez \| Love in the Time of Cholera \|1985` | **악센트 제거됨** |
| *Tirukkural* (திருக்குறள்), 연도 정보 상충 | `Valluvar \| The Tirukkural \|NULL` | 타밀 문자 제목 탈락, 연도는 `NULL` |

제목이 본문에 두 형태로 등장하지만 **문법에 맞는 것은 하나뿐**이고 그것이 결과에 나타난다.

### C. JSON 모드의 한계 — 반드시 기억할 것

```json
{"author": "Gabriel García Márquez", "title": "Love in the Time of Cholera", "year": 1985}
```

필드가 `author`·`title`·`year`인 것은 **제약된 결과가 아니라** GPT-4o-mini 같은 고성능 모델에 **의존한 결과**다. JSON 모드는

- 저자 이름에 **악센트가 들어가는지 제약하지 않는다** — 들어갈 때도, 안 들어갈 때도 있다
- 제목이 영어 문자로만 되도록 **제약하지 않는다** — 가끔 타밀어 제목이 반환될 가능성에 대비해야 한다

> **JSON 모드는 "JSON임"만 보장하고, "무엇이 들어가는지"는 보장하지 않는다.**

예제 B와 나란히 놓고 보면 차이가 분명하다. B는 문법이 **실제로** 악센트를 제거했고, C는 운에 맡겼다.

### D. 인보이스 — 보장의 맛

```python
class CurrencyEnum(str, Enum):
    USD = 'USD'; UKP = 'UKP'; INR = 'INR'; EUR = 'EUR'

@dataclass
class Invoice:
    purpose: str
    amount: float
    currency: CurrencyEnum = CurrencyEnum.USD
```

PydanticAI를 쓰면 **LLM 비종속적(LLM-agnostic)**으로 구조화된 출력을 얻는다.

```python
agent = Agent(model, result_type=Invoice, system_prompt=system_prompt)
response = agent.run_sync(paragraph)   # → Invoice 객체가 보장된다
```

입력 *"Requesting reimbursement for taxi ride to airport. I paid $32.30."*
→ `Invoice(purpose='taxi ride to airport', amount=32.3, currency=<CurrencyEnum.USD: 'USD'>)`

### 🚫 구걸하지 말 것 (Don't Beg for Compliance)

책이 안티패턴으로 못 박는 프롬프트.

> *"제발 추가 서식이나 긴 설명을 붙이지 마세요. 그냥 YES 또는 NO로만 답하세요. 반드시 대문자로 써 주세요."*

대신 **보장**한다.

```python
agent = Agent(model, result_type=Literal["YES", "NO"])
```

## 5. BNF vs Pydantic — 언제 무엇을

### Pydantic이 나은 점 3가지

| | 이유 |
|---|---|
| **사용 편의성** | `dataclass` 몇 줄이 BNF 규칙보다 쉽다 |
| **지연 시간** | BNF는 **클라이언트** 쪽 처리, Pydantic 제약은 **서버** 쪽 처리 → 네트워크 왕복이 줄어든다 |
| **모델 지원** | BNF는 `logprobs` 접근이 필요(지원이 보편적이지 않다). **모든 현대 모델이** `dataclass`를 통한 문법 제약을 지원한다 |

### 그럼에도 BNF가 더 유연하다 — 신용카드 검증

스타일 규칙이 단순한 데이터 형식 **이상**이면 BNF를 써야 한다. `Enum`을 넘어서는 검증은 Pydantic으로 하기 어렵다.

```
<credit_card_number> ::= <visa_number> | <mc_number> | <amex_number>
<visa_number> ::= "4" <digit>{12,15}
<mc_number>   ::= ("51".."55" <digit>{14}) | ("2221".."2720" <digit>{12})
<amex_number> ::= "34" <digit>{13} | "37" <digit>{13}
```

같은 일을 Pydantic으로 하려면 `@field_validator`로 **검증 로직을 직접 작성**해야 하고, 더 이상 단순한 `dataclass`가 아니게 된다(책에 40행 가까운 구현이 실려 있다).

> **파이썬만의 이야기가 아니다** — 자바스크립트에서는 **Zod**로 Ollama·OpenAI의 스키마 지정 기능을 쓴다.

## 6. 실패의 세 얼굴 — 문법이 정답을 막는다

문법 제약을 만족하는 토큰이 **하나도** 없으면 **생성이 실패**한다. 실패는 세 모습으로 나타난다.

| 증상 | 진짜 원인 | 대처 |
|---|---|---|
| **끝없는 공백**(endless whitespace) | 막혔는데 공백만 허용됨 — 공백은 문법이 대개 허용하고 후보에 거의 항상 있다 | 문법 완화 · 타임아웃 |
| **거부율 증가**(increased refusals) | 구조가 **너무 깊거나 길다** → 어떤 후보도 안 맞는 지점에 도달할 확률↑ | 중첩 줄이기 · 쪼개기 |
| **부정확한 결과**(inaccurate results) | **문법이 정답을 막고 있다** | **탈출구를 준다** |

### 탈출구(escape hatch)를 꼭 둔다

```python
# 나쁨 — 모르면 아무 숫자나 지어낸다
currency_rate: float

# 좋음 — 모른다고 말할 수 있다
currency_rate: float | Literal["Unknown"]
```

이 한 줄이 **환각을 크게 줄인다.** "반드시 숫자를 내놔"라고 하면 모델은 없는 숫자라도 만들어 낸다.

패턴 1의 「정직하게 볼 한계」와 같은 종류의 함정이다. **제약을 강하게 걸면 결과가 좋아 보이지만, 무엇을 막았는지는 결과에 안 나타난다.**

## 7. 이름에 속지 말 것

이 패턴에는 다른 이름들이 있다.

- **구조화된 출력**(structured outputs) — 데이터 구조가 문법 명세의 흔한 형식이므로
- **제약 디코딩**(constrained decoding) — 가능한 로짓을 제약하는 방식으로 작동하므로

**그러나** "구조화된 출력을 지원한다"고 해서 **반드시 이 패턴을 쓰는 것은 아니다.**

| | 구현 | 결과 |
|---|---|---|
| **진짜** | 생성 중에 토큰을 막는다 | **100% 보장** |
| **가짜** | 일단 생성하고 **LLM을 한 번 더 불러** 형식을 맞춘다 | 느리고, 비싸고, 여전히 틀릴 수 있다 |

책은 집필 시점(2025년 6월) 기준 **LangGraph**를 가짜 사례로 지목한다. 후처리 방식은 로짓 조작으로 준수를 보장하는 이 패턴보다 **더 낭비적이고, 더 비싸고, 덜 신뢰할 수 있다.**

각주에 따르면 **Claude의 구현도 제약 디코딩을 쓰지 않는 것으로 보인다.** Anthropic 문서는 대신 원치 않는 서두를 피하려 **응답을 원하는 형식의 시작 부분으로 미리 채우는(prefill)** 방법을 제안한다.

> 도구를 고를 때 물어야 할 질문 — **"그거 어떻게 구현했나요?"**

패턴 1에서 Claude가 로짓을 안 준다는 제약을 봤는데, 여기서도 같은 벽이 다른 모습으로 나타난다.

## 8. 언제 무엇을 쓰나

### 문법 대신 **패턴 1 로짓 마스킹**으로 가야 하는 6가지 신호

| 신호 | 예 |
|---|---|
| 규칙을 `dataclass`로 **표현할 수 없다** (표현이 아니라 **로직**이다) | 특정 상황에서만 경쟁사 제품명 마스킹 |
| BNF가 **지나치게 복잡하고 디버깅이 어렵다** | — |
| 규칙이 **동적이며 내용에 따라 달라진다** | 신제품 출시 얘기일 땐 가리고, 기출시 제품엔 안 가림 |
| 규칙을 **DB나 규칙 엔진에서 가져와야** 한다 | 가릴 대상이 고객사마다 다름 |
| 마스킹이 **사용자 입력에 의존**한다 | 자동완성(autocomplete) 유스케이스 |
| 규칙이 **외부 도구·API 호출을 수반**한다 | — |

로짓 마스킹의 다른 대안들(스타일 전이, 더 강력한 모델, 될 때까지 다시 해 보기, 성찰)은 **같은 이유로 문법의 대안**이기도 하다.

### 결정 흐름

1. **JSON·스키마가 필요한가?** → 방법 3. 고민 끝
2. **금지어·복잡한 로직인가?** → 패턴 1. 단 로짓 접근이 되는 모델이어야 한다
3. **둘 다 아닌 "느낌"인가?** → 패턴 3 스타일 전이로 넘어간다

## 9. 우리 프로젝트와 연결

패턴 1 노트에서 [모니터링 에이전트](https://github.com/inseoklee-ai/hackathon1-monitoring-agent)를 **Jinja2 템플릿 + 결정론적 치환**으로 만든 것을 「로짓 마스킹을 극단까지 밀어붙인 형태」라고 정리했다. 문법은 그 축의 **중간 지점**이다.

```
부탁(프롬프트)  →  문법(스키마 강제)  →  로짓 마스킹  →  전면 차단(템플릿)
   보장 없음         구조는 보장            임의 규칙        모델 재량 0
```

나중에 다이제스트에 LLM을 쓰게 되면, **템플릿에서 한 칸 물러서는 첫 후보가 문법**이다. 이유가 셋이다.

- 치환할 값의 **자리와 타입이 보장**된다 → 템플릿 엔진에 그대로 넘길 수 있다
- 서버 쪽 처리라 **로컬 추론이 필요 없다** — 패턴 1에서 겪은 CPU 2~10분 문제를 피한다
- 값을 못 채울 때 `| Literal["Unknown"]` 탈출구로 **모른다고 말하게** 만들 수 있다 → 모니터링 문구에서 지어낸 숫자는 가장 위험한 실패다

## 10. 자가점검

1. JSON 모드로 받은 응답에 악센트 문자가 없을 것이라 믿어도 되는가?
2. 문법에 `>`를 넣지 않았을 때, 비교 질문에 모델은 어떻게 반응하는가?
3. 응답이 끝없는 공백으로 채워졌다. 무엇을 의심해야 하는가?
4. BNF가 Pydantic보다 확실히 나은 축은 무엇인가?
5. 어떤 프레임워크가 "structured output 지원"이라고 광고할 때 확인할 질문은?
6. 실수(float) 필드에 값을 못 채우는 경우, 스키마를 어떻게 써야 하는가?

<details>
<summary><b>정답 펼치기</b></summary>

1. **아니다.** JSON 모드는 "JSON임"만 보장한다. 필드 이름·문자 집합은 모델 성능에 기댄 결과이고, 악센트는 들어갈 때도 안 들어갈 때도 있다. 문자 집합을 보장하려면 BNF(예제 B)가 필요하다.
2. **정답을 못 낸다.** 문법이 허용한 토큰만 나오므로 `3 + 2 = 5` / `2 + 4 = 6` 처럼 **식만 나열하고 비교는 하지 못한다.** 제약이 작동한 결과이자, 문법 설계 실수가 오답으로 나타나는 방식이다.
3. **문법에 막혔는데 공백만 허용된 상태.** 공백은 문법이 대개 허용하고 후보 공간에 거의 항상 있어서, 다른 길이 다 막히면 공백만 반복된다. 문법을 완화하거나 타임아웃을 둔다.
4. **유연성.** 단순한 데이터 형식을 넘는 검증(신용카드 번호 규칙 등)을 문법으로 표현할 수 있다. 편의성·지연시간·모델 지원은 모두 Pydantic이 낫다.
5. **"어떻게 구현했나요?"** — 생성 중에 토큰을 막는지(진짜), 아니면 생성 후 LLM을 한 번 더 불러 형식을 맞추는지(가짜). 후자는 느리고 비싸고 여전히 틀릴 수 있다.
6. **탈출구를 준다.** `currency_rate: float | Literal["Unknown"]`. 반드시 숫자를 내놓으라고 하면 없는 숫자를 지어낸다.

</details>
