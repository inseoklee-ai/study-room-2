4.3.1 문제

RAG를 붙여도 남는 위험
문서 저장소에서 정보를 검색해 온다고 해도 잠재적 위험이 남습니다.

⚠️ 네 가지 위험

위험내용
검색 실패
retrieval failures		관련 없는 문서를 가져오거나 핵심 정보를 놓친다 → 답이 최적에 못 미친다
컨텍스트 신뢰성
context reliability		모두 관련 있어도 일부는 낡았거나 편향됐거나 틀린 정보 → 답도 그렇게 된다
추론 오류
reasoning errors		검색된 정보를 잘못 추론하거나 오독한다
환각 위험
hallucination risks		RAG도 여전히 정보를 꾸며내거나 문서를 잘못 섞는다 — 특히 복잡한 주제에서
현재로서는 이 문제들을
완전히 피할 방법이 없다
🏹 그러나 신뢰도를 평가하고 그 정보를 소비자에게 전달할 모범 사례는 있습니다. 답변이 행동을 유발하는 상황이라면, 사용자가 그 행동을 할지 말지 결정할 수 있도록 신뢰도를 드러내는 일이 중요합니다.
의료 RAG에 "1형 당뇨병 치료 선택지"를 물었다면, 답이 옳도록 하는 것도 중요하고 어떤 선택지가 낡았거나 동료 심사를 안 거친 출처에서 왔는지 드러내는 것도 중요합니다.

4.3.2 해법

다섯 갈래로 신뢰를 쌓는다
지식 베이스가 충분한 질문에만 답하기, 인용 제공, 루프에 사람 넣기, 틀릴 수 있는 정보 검증하기, 적절한 UI 설계.

🚫 도메인 밖 탐지 — 모른다고 말하기

신뢰를 쌓는 가장 좋은 방법 하나는
응답하지 말아야 할 때를 시스템이 안다는 것을 알려 주는 것

의료 RAG에 병원까지 가는 길을 물었다면? 응답을 거절하거나 Google 지도로 넘겨야 한다.

전략내용
임베딩 거리질의를 임베딩해 모든 청크와의 유사도를 본다. 도메인 밖에서는 점수가 가파르게 떨어진다. 최적 임계값은 도메인마다 다르고, 시간에 따라 추적하며 조정할 수 있다
제로샷 분류범주를 정의한다 — 의료라면 ["Medical", "Not Medical"]. 작은 언어 모델이어도 된다. 맥락이 달라지면 예시를 넣어 퓨샷으로. 여러 범주라면 최소 30% 신뢰도를 임계값으로
키워드·용어 요구가장 제한적. 의료라면 의학 사전의 용어가 하나 이상 등장하도록 요구
💡 저마다 장단이 있으니 세 신호의 가중합 같은 하이브리드 접근을 택할 수도 있습니다. 탐지했다면 검색·생성을 단축(short-circuit)하고 거절하거나 다른 리소스로 라우팅합니다.
억지로 답하는 것보다 "그건 제 영역이 아닙니다" 하고 넘겨주는 쪽이 훨씬 신뢰를 얻습니다.

📑 인용 — 세 가지 수준

인용은 신뢰를 쌓는 가장 효과적인 방법 중 하나다. 사용자는 시스템이 성실하게 만들어졌음을 이해하고, 참조는 정확성을 즉시 검증할 수단이 된다.

방법내용특징
출처 수준 추적
source-level		검색 계보를 기반으로. 청크와 함께 저장한 메타데이터를 인용을 아는 프롬프트에 넘겨 생성하고 후처리로 포매팅단순하지만 인용을 과하게 다는 경향
분류 기반
classification		분류기가 인용이 필요 없는 상식과 인용이 필요한 사실 주장을 구분. 기준은 도메인마다 다르다(학술 논문은 더 많이 요구)더 정밀하지만 분류기를 마련·파인튜닝해야 해 복잡도 증가
토큰 수준 귀속
token-level		생성 과정에서 메타데이터를 LLM의 어텐션 메커니즘을 통해 추적 → 토큰 하나하나를 하나 이상의 출처에 귀속. 임계값 이상일 때만 표시패러프레이즈를 귀속 손실 없이 다루고 여러 출처 혼합 지원
⚠️ 토큰 수준 귀속은 집필 시점 기준 활발한 연구 영역이며, 실서비스에 쓸 만한 오픈소스 구현은 아직 없습니다.
💡 왜 필요한가 — 생성 과정에서 원래 청크의 경계가 흐려지고, 여러 청크가 한 문장에 기여하며, LLM이 바꿔 쓰는 경향 때문에 직접적인 텍스트 매칭이 어려워집니다.
세 번째 줄의 예로 책은 "그는 서양 음악사에서 가장 위대한 작곡가 중 한 사람으로 널리 평가받는다" 같은 문장을 듭니다. 상식이 아니라 인용이 필요한 진술이죠.

🛡️ 가드레일 — 네 지점에서

시점검사
검색 전도메인 밖 탐지로 유해·부적절 질의 차단 · 주입 공격 방지를 위한 입력 정제 · 신뢰도가 매우 높은 출처만 남기기
검색 후청크 메타데이터 추적 강제 · 출처와 관련성으로 우선순위 매기고 임계값 미만 제거 · 성찰형 RAG로 사실 확인 · 프라이버시 준수 확인
생성 전데이터 신선도(예: 6개월 초과 제외) · 출처 다양성 강제 · 유해한 내용 확인
생성 후인용과 출처 귀속 강제 · 사실 확인 · 데이터 프라이버시 · 의도치 않은 유해 생성 확인
⛔ 검사를 통과하지 못한 청크는 버립니다 — 응답 생성 단계로 절대 넘기지 않습니다. 가드레일 중 하나라도 실패하면 질의를 다시 쓰고 새 생성이나 새 검색을 트리거합니다.
🔧 도구 — Guardrails AI(PII·도메인 밖·탈옥·욕설 탐지) · DeepEval(인용 정확도·검색 정밀도·환각 탐지 + 레드티밍) · Ragas(답변 정확성·컨텍스트 개체 재현율). 이들을 쓰면 관측 가능성도 함께 좋아집니다.
가드레일이 파이프라인 전반에 깔린다는 게 핵심입니다. 한 곳에서만 막는 게 아니에요.

🔄 CRAG와 Self-RAG — 검사 시점의 차이

요리로 치면 —
CRAG는 재료 검수, Self-RAG는 맛보기 후 다시 조리

🥣 CRAG — 교정형 RAG (생성 전)

문서를 생성 단계로 넘기기 전에 검색된 청크의 품질을 평가하는 평가기를 추가. 신뢰도 점수가 서로 다른 지식 검색 동작을 촉발한다.

  • 웹이나 기업 문서 저장소(SharePoint · Google Drive)를 검색해 보강 — 지식 베이스는 정적인데 온라인 콘텐츠는 더 빨리 갱신되므로
  • "분해 후 재구성" — 관련 없어 보이는 내용을 걸러 핵심에 집중하게

관련 없는 콘텐츠는 검색 결과로 완전히 대체, 중의적인 콘텐츠는 검색 결과와 결합한 뒤 넘긴다

🧠 Self-RAG — 성찰형 (생성 후·전체)

자기 평가(검색 품질을 스스로 비판) · 적응형 검색(더 검색할지 생성으로 갈지 스스로 결정) · 통제된 생성(검색 지식 vs 기반 LLM의 파라미터 지식 사이를 조절)

이 모두는 프롬프트로 달성할 수 있습니다(6장 패턴 17 LLM-as-Judge). 루프와 복잡도가 늘지만 환각을 줄이고 설명 가능성을 높입니다.

Self-RAG는 고정된 결합 방식 대신 맥락에 따라 검색 지식과 파라미터 지식을 더 잘 섞을 수 있습니다.

🖥️ UI 설계 — 블랙박스에서 연구 조수로

사용자는 어떤 문서가 참조됐는지, 정보가 얼마나 최신인지, LLM이 얼마나 확신하는지를 볼 수 있을 때 더 신뢰한다.

  • 시각 지표 — 인용 링크 · 출처 미리보기 · 신뢰도 게이지
  • 인라인 인용과 원문에 원클릭 접근 — 사용자의 지성을 존중하는 태도를 보인다
  • 통제권 — 검색 파라미터 조정 · 날짜나 출처 권위로 필터링 · 초기 응답을 바탕으로 질의 다듬기 → 일방적 전달이 아니라 협업하는 경험
  • 점진적 공개(progressive disclosure) — 단순화된 결과를 먼저, 더 깊이 팔 선택지를 제공 → 깊이를 유지하면서도 압도하지 않는다
  • 피드백 메커니즘 — 좋아요/싫어요 · 정정 · 눈에 보이는 시스템 개선
알 수 없는 블랙박스에서
작업 내용을 검증하고 신뢰할 수 있는 연구 조수로
💡 자기 피드백이 개선된 응답에 반영되는 것을 볼 때 사용자는 시스템의 지속적 개선과 신뢰성에 확신을 갖게 됩니다.
책은 Perplexity AI의 검색 인터페이스를 예로 듭니다. 인용을 어떻게 보여주는지가 신뢰를 크게 좌우해요.

4.3.3 예제

응답에 인용 달기 — 분류 기반
해법 중 가장 효과적인 것이 인용입니다. 분류기로 인용이 필요한 부분을 탐지하고 관련 인용을 제공합니다.

📏 여섯 단계

1최초 응답 생성 — 아직 검토되지 않은 응답
2더 작은 조각으로 청킹 — 이 예제는 문장 수준까지
3인용이 필요한지 검사 — 파인튜닝된 BERT 같은 작은 모델이나 LLM 제로샷 호출
4출처 조회 — 문서 저장소에서 유사 문서 검색
5응답에 인용 넣기
6필요한 경고나 정정 추가
sentences = raw_response.split(".")
for sentence in sentences:
    review = needs_citation(sentence)
    chunks = check_sources(sentence) if review else []
prompt = """Check if the content requires citations. Return
{{"requires_citations": true}} … Content: {content}"""
인용을 얼마나 세밀하게 달고 싶은지에 따라 2단계의 청킹 전략을 바꿔도 됩니다.

    response_with_citations += " [Citation needed] "
⚠️ 6단계가 이 예제의 핵심입니다 — 분류기는 인용을 요구했는데 문서 저장소에서 출처를 못 찾았다면 그때가 사용자에게 알려야 할 순간. 여기서는 [Citation needed]를 보이지만, 그 진술을 붉게 표시하거나 제거하거나 전체를 강제 재생성할 수도 있습니다.
📝 GitHub에는 프롬프트 기반 인용 예제도 있지만 단점이 있습니다 — 생성된 주장을 문서 저장소와 다시 대조하지 않으며, 인용 포매팅을 세밀하게 통제할 수 없습니다.
실제 구현에서는 예제용 텍스트 파일이 아니라 청크의 메타데이터에서 온 제대로 된 출처를 가리켜야 합니다.

⚠️ 4.3.4 한계

💥 Self-RAG처럼 정교한 구현은 파이프라인 복잡도를 높이고 실패 지점을 늘립니다. 도구를 하나 더할 때마다 응답 시간이 늘고 결국 UX에 영향을 주므로, 더 단순한 대안으로 되는지 따져 봐야 합니다.
한계내용
임계값 의존유사도 점수와 임계값에 크게 의존하는데, 이 임계값은 도메인에 극도로 특화돼 세심한 튜닝과 지속적 갱신이 필요하다. 엣지 케이스가 흔들 수 있고 예상보다 많은 노력을 요구한다
안전장치 vs 정보 손실대부분을 걸러 내는 아주 엄격한 RAG는 값진 정보를 지워 버리고 불완전한 답을 만들며 UX를 해친다
확장의 한계검증 단계는 — 루프 안의 사람과 마찬가지로 — 어느 지점을 넘으면 불가능해진다. 지식 베이스가 커지고 상충 정보가 더해지면 거짓 양성도 시간이 갈수록 늘어난다
⚖️ 균형이 이 절의 주제입니다. 너무 느슨하면 신뢰가 안 되고, 너무 빡빡하면 쓸모가 없어집니다.
두 번째가 실무에서 자주 부딪힙니다. 안전하게 만들려다 아무 답도 못 하는 시스템이 되는 거죠.

🔁 두 가지 대안

① 여러 지식 출처를 통합

단일 원샷이 아니라 여러 출처로 검색하는 파이프라인은 전반적으로 더 나은 응답을 낸다.

  • LLM의 파라미터 정보와 검색을 통한 비파라미터 정보를 결합
  • 지식 그래프를 써서 응답 품질을 더 높이기

② 자동 교정 대신 설명 가능성에 집중

환각을 자동으로 고치거나 엄격한 가드레일을 넣기보다 —

  • 검색된 청크를 신뢰도 점수와 함께 노출
  • 시스템의 추론 단계를 사용자에게 제공
  • 인용된 출처를 생성 응답과 나란히 볼 수 있는 대화형 UI
고치려 들지 말고
보이게 하라
두 번째가 이 패턴 전체의 정신입니다. 오류를 없앨 수 없다면 판단 재료를 사용자에게 넘기는 거죠.
