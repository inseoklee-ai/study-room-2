8.4.1 문제

전통적 부하 테스트로는 부족하다
AI 애플리케이션이 겉보기에는 전통적인 서버 애플리케이션처럼 보일지 몰라도요.

❌ 실패 지점만 찾아서는 부족하다

LLM 기반 AI 애플리케이션에서 성능 테스트는 보통 추론 구성의 성능을 테스트하는 일로 귀결된다. 그런데 전통적인 부하 테스트만으로는 충분하지 않다.

전통적 부하 테스트AI 애플리케이션에 필요한 것
서버의 실패 지점을 찾아 준다
400 / 500 오류 같은		성능을 더 세밀하게 이해해야 한다
언제 완전히 실패하느냐가 아니라
서비스 품질이 어떻게 저하되기 시작하는지
❌ 이렇게 말하는 것으로는 부족하다
"응답은 0.3초 안에 생성되어야 하고, 요청의 95%가 이 기준보다 빠르면 통과"
✅ 대신 필요한 것
• 요청의 5% 이상이 느려지기 시작하는 저하 지점
• 애플리케이션을 그 지점 가까이 밀어붙이는 제약이 무엇인지
합격/불합격이 아니라 "어디서 꺾이는가"를 찾는 것입니다.

🔗 제약은 겹쳐서 온다

응답 생성 속도의 경우, 요청 수가 어떤 임계값을 넘거나 요청 크기가 어떤 임계값을 넘을 때 추론 서비스가 느려지기 시작하는 것을 알아챌 수 있다. 어쩌면 여러 제약이 동시에 작용해 저하가 일어날 수도 있다.

1큰 요청 몇 개 때문에 서버 메모리가 바닥난다
2서버가 죽는다
3서버가 다시 뜨기를 기다리는 동안 요청이 쌓인다
💡 어떤 제약이 관련 있는지 이해하면
• 그 제약에 부딪힐 가능성을 낮추는 방향으로 성능 개선에 집중할 수 있다
• 예상되는 사용량 피크에 앞서 필요한 용량을 미리 조달하는 데도 도움이 된다
⚠️ 도구의 공백 — AI 애플리케이션 테스트에는 세밀한 부하 테스트가 필요하지만, 통상적인 부하 테스트 도구에는 LLM 성능 평가와 관련된 특정 지표들이 없다. 지표가 모호하면 테스트가 비효율적이 되고 엉뚱한 제약으로 노력이 흘러간다.
관련 있는 제약과 지표는
무엇인가?

⏱️ TTFT — 첫 토큰까지의 시간

요청을 제출한 시점부터 응답의 첫 토큰이 생성될 때까지의 시간. 사용자가 모델 출력의 시작을 받아 보기까지 얼마나 기다려야 하는지를 알려 준다.

사용자는 TTFT를
아무 일도 일어나지 않는 시간으로 인식한다
⚡ 스트리밍이 왜 마법 같은가 — 토큰이 나오는 즉시 응답을 한 토큰씩 갱신하면(스트리밍), 완성된 응답을 만들어 내는 시간에 대한 제약은 훨씬 느슨해질 수 있다. 응답이 흘러나오기 시작하는 순간 애플리케이션이 사용자의 주의를 붙잡기 때문 — 전체 응답이 도착하는 동안 사용자는 앞부분을 읽고 있다.

다 만들고 한 번에 보여 주면 EERL 전체를 기다리지만, 한 글자씩 흘리면 TTFT만 기다리면 됩니다. 실제 총 시간은 같은데 체감이 완전히 달라집니다.
⚙️ TTFT를 지배하는 것 — LLM의 어텐션 메커니즘. 시간은 주로 두 요인에서 온다.
• 처리해야 할 입력 프롬프트의 크기
• 어텐션 계산을 가속하는 데 쓰이는 KV 캐시의 속도
인터랙티브 애플리케이션에서 가장 중요한 지표입니다.

🛠️ TTFT가 높다면 무엇을 할 수 있나

진행 상황 표시기술적이지는 않지만 놀랍도록 효과적 — 여러 단계를 거친다면 사용자에게 진행 상황을 보여 주어 "체감 TTFT"를 줄인다
💡 네 번째 항목이 미묘합니다 — "예측 가능한 것을 앞에"는 곧 프리픽스 캐시가 잘 맞아떨어지게 프롬프트를 설계하라는 뜻입니다. RAG 결과처럼 매번 바뀌는 것이 앞에 오면 뒤쪽 전부가 캐시 미스가 됩니다.
마지막 항목을 저자가 굳이 적어 둔 것이 인상적입니다.

⏲ EERL — 종단 간 요청 지연

TTFT와 대조적으로 완성된 응답을 생성하는 데 걸리는 시간을 측정한다. 이 지표에는 큐 대기 시간 · 네트워크 지연 · KV 캐시 생성 시간도 포함된다.

1기준 질의 집합 마련 — 프로덕션에서 LLM이 마주칠 요청의 전체 스펙트럼을 대표해야 한다. 요약 · 텍스트 추출을 비롯해 자기 사용 사례에 부합하는 여러 생성 AI 기능을 포괄
2정상 운영 조건에서 보내고 요청 제출 → 응답 수신까지의 시간을 기록
3평균 응답 시간만으로는 충분하지 않다 — 질의 유형에 따라, 그리고 컨텍스트 윈도 · 허용 병렬 요청 처리량 같은 서버 설정에 따라 성능이 어떻게 요동치는지 변동 패턴도 분석하라
📈 변동성은 백분위로 보고한다 — 통상 P50 · P95 · P99를 밀리초 단위로. P95는 요청을 응답 시간 순으로 줄 세웠을 때 95번째 백분위 — "느린 쪽 5%가 겪는 시간"입니다.
💡 이 지표는 사용자가 정상 운영 중 무엇을 기대할 수 있는지에 대한 좋은 이해를 줍니다. 너무 느리다면 이 장의 패턴들을 적용하거나 다른 하드웨어를 써 볼 수 있습니다 — NVIDIA L4 → A100 업그레이드로 대역폭을 늘리거나, Groq 같은 전용 ASIC.
그림 8-12가 EERL의 구간을 그린 것입니다.

📑 추측 디코딩(패턴 24 · 26)과 같은 발상입니다 — 토큰 단위가 아니라 작업 단계 단위로 올린 것뿐이죠. "싸게 먼저 해 보고 틀리면 버린다"는 구조가 동일합니다.
이 대응 관계를 알아 두면 두 기법이 하나로 기억됩니다.

📉 TPS — 초당 토큰 수와 포화점

초당 총 출력 토큰 처리량. 단일 요청이 아니라 시스템 전체의 성능을 측정한다.

1시스템으로 들어오는 요청 수가 늘어나면 TPS도 함께 올라간다
2그러나 결국 포화점(saturation point)에 도달하고, 그 지점을 넘으면 LLM 구성이 더 이상 요청을 감당하지 못한다
3포화점을 지나면 TPS가 떨어지는 것을 관찰하게 된다
📌 원본 수식 이미지 누락
원서 이 자리에 TPS의 정의 수식이 그림으로 들어가 있었으나 원본 파일 반출 과정에서 떨어져 나갔습니다. 수식을 임의로 지어내지 않고 원문 본문과 그림 8-13이 서술하는 구성 요소만 적습니다.

• 분자 — 시간에 걸쳐 생성된 전체 응답 토큰 수
• 분모 — 그 전체 테스트 시간(그림 8-13의 "Overall test time" 구간)
🍳 포화점의 비유 — 손님을 더 받을수록 주방 매출은 늘어납니다. 그런데 어느 순간부터 주방이 엉켜서 오히려 접시가 덜 나옵니다. 그 꺾이는 지점이 포화점입니다. 이 패턴이 "저하 테스트"라 불리는 이유가 바로 이 꺾이는 지점을 찾는 것이기 때문입니다.
이 슬라이드가 패턴 이름의 뜻을 설명합니다.

📥 RPS — 초당 요청 수

시스템이 1초에 성공적으로 완료할 수 있는 평균 요청 수.

📌 원본 수식 이미지 누락
여기에도 RPS 계산 수식이 그림으로 들어가 있었으나 원본 파일에서 떨어져 나갔습니다. 원문이 본문에서 정의한 문장만 그대로 옮깁니다 — "시스템이 1초에 성공적으로 완료할 수 있는 평균 요청 수".
📏 TPS와의 관계 — RPS는 TPS와 밀접하게 연관되어 있는데, 다만 TPS는 응답 길이까지 반영한다는 점이 다르다. 보통은 TPS가 운영상의 제약이 되지만, RPS도 처리량의 척도로 유용하다.

처리량 테스트란 여러 사용자가 동시에 질의를 보내는 상황을 시뮬레이션하고, 성능이 크게 저하되지 않으면서 시스템이 초당 몇 건을 성공적으로 처리하는지 측정하는 것이다.

구분재는 것
지연 시간개별 응답 속도
처리량 테스트동시 요청을 효과적으로 감당하는 능력
📈 모니터링은 요청 수를 세는 것을 넘어선다 — 핵심 지표에는 응답 시간의 일관성 · 오류율 · 동시 부하가 커질 때의 전반적 시스템 안정성이 포함된다. 이것이 처리량 증가가 응답 품질이나 신뢰성에 악영향을 주기 시작하는 지점을 짚어 준다.
📊 RPS 외의 처리량 지표 — 성공 요청률(%) · 오류율(% 또는 초당 오류 수) · 지원 가능한 동시 사용자 수
사용자 기반이 커지고 수요가 늘어나면 결정적으로 중요해지는 지표입니다.

📈 확장성 테스트

처리량 평가에서 한 걸음 더 나아가, 시간에 따라 부하가 점진적으로 늘어날 때 성능 특성이 어떻게 변하는지를 살핀다.

🎯 고정된 부하를 가하는 대신 수요가 점진적으로 커질 때의 행동을 드러내어 확장의 한계를 식별한다. 최소 부하에서 시작해 수요를 늘려 가면 성능 추세를 관찰하고 효율이 떨어지기 시작하는 변곡점을 찾아낼 수 있다.

테스트 중에는 응답 시간 · 처리량 · 오류 빈도를 모니터링한다. 이 지표들은 시스템이 언제 확장 병목에 부딪히는지를 알려 주며, 그 시점을 아는 것은 추론 구성을 설계하는 데 도움이 된다.

🔧 병목의 출처 — GPU 선택에서 올 수도 있고, 인스턴스를 늘려야 할 정도의 사용자 수요에서 올 수도 있다.

💥 스트레스 분석과 부하 테스트

💥 스트레스 테스트

LLM을 정상 운영 범위 너머로 밀어붙여 한계점과 실패 양상을 이해한다.

패턴 — 갑작스러운 트래픽 급증, 복잡한 질의 패턴, 정상 용량을 초과하는 지속적 고부하

핵심 질문 — 요청 부하가 어느 지점에서 구성을 무너뜨리는가? 그만큼 중요한 것은 어떻게 회복하는지다 — 우아하게 실패하는가, 부분 기능을 유지하는가, 아니면 치명적으로 붕괴하는가?
📊 부하 테스트

예상되는 피크 트래픽 조건을 겨냥해, 수요가 높은 기간에도 수용 가능한 성능을 유지하는지 확인한다.

스트레스 테스트와의 차이 — 한계점을 찾으려는 것이 아니라, 시스템이 일상적으로 감당해야 하는, 현실적이지만 부담스러운 시나리오에서의 성능을 검증한다.

필요한 것 — 피크 사용 패턴의 정확한 모델링. 이 테스트는 언제 더 많은 인스턴스로 확장해야 하는지 알려 준다
테스트측정 지표
스트레스 분석최대 부하 용량(실패 전 RPS 또는 동시 사용자) · 실패 임계값 · 복구 시간(정상 복원까지 초 · 분) · 스트레스 하 오류율 · 시스템 가용성 · 자원 고갈 지점
부하 테스트피크 부하 성능(고트래픽 시 RPS) · 부하 하 응답 시간 · 피크 시 오류율 · 큐 길이(대기 중인 요청 수) · 피크 시 자원 활용률
💡 스트레스 테스트에서 진짜 값진 것은 "회복"입니다. 무너지는 지점보다 무너진 뒤 어떻게 되는가가 복원력 개선과 실패 복구 프로토콜을 만드는 지침이 됩니다.
우아하게 실패하는 시스템과 치명적으로 붕괴하는 시스템은 같은 한계점을 가져도 전혀 다릅니다.

🔧 병목이 보이면 무엇부터

응답 시간 같은 성능 병목이 관찰된다면 계산 자원이 부족하다는 신호다.

1먼저 기반 하드웨어의 메모리가 완전히 소진됐는지 확인하고, 그렇다면 컴퓨트 능력이 더 높은 GPU/TPU 플랫폼으로 업그레이드를 고려하라 → 더 큰 프롬프트를 처리하고 수십억 파라미터 모델을 더 빠르게 계산할 수 있다
2업그레이드가 불가능하다면 여러 GPU에 처리 부하를 분산하라 — 데이터 병렬화(GPU마다 전체 모델을 두고 데이터를 나눠 처리) 또는 모델 병렬화(모델을 여러 GPU에 분할)
3마지막으로 이 장에서 논한 패턴들을 적용하라
목표좋은 선택지
빠른 TTFT모델 증류 · 양자화 · 연속 배칭
전체 처리량증류 · 양자화 · 추측 디코딩으로 모델 크기를 줄이는 것
💡 이 표가 8장 전체를 닫습니다 — 패턴 27로 어디가 아픈지 재고, 그 답에 따라 패턴 24 · 25 · 26 중 무엇을 쓸지 고릅니다.
