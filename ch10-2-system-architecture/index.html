에이전트 패턴

워크플로의 각 단계를 구현
각 에이전트는 서로 독립적으로 구현할 수 있습니다.

⚠️ UX가 먼저 전제 조건을 만족해야 한다

UX가 외부 시스템을 참조하지 않고도
일을 끝낼 수 있게 해 줘야 한다

사용자가 워크플로를 이루는 작업들을 에이전트에게 가르칠 수 있으려면 그래야 한다. 필요한 데이터는 도구나 API를 통해 애플리케이션 안으로 끌어오면 된다.

❌ 사용자가 입력할 정보를 찾으려고 애플리케이션 밖으로 나가야 한다면 — 에이전트는 결정을 추천하고, 추천이 틀렸을 때 배우고, 결국 자율적으로 결정하는 데 필요한 컨텍스트를 갖지 못하게 된다.
💡 이 문단이 왜 맨 앞에 오나 — 사용자가 다른 탭에서 자료를 찾아 붙여 넣었다면, 그 "찾는 과정"이 로그에 남지 않습니다. 나중에 그 단계를 자동화하려 해도 학습할 데이터가 없죠.

→ 자동화하고 싶은 일은 먼저 애플리케이션 안으로 들어와야 합니다.
📑 7장 패턴 21 Tool Calling이 여기서 UX 요구사항이 됩니다 — 도구를 붙이는 이유가 "편해서"가 아니라 "학습 데이터를 남기려고"입니다.
기술 선택이 아니라 학습 가능성의 문제로 프레이밍한 대목입니다.

🧩 각 에이전트가 골라 쓰는 패턴

워크플로의 각 단계는 하나 이상의 에이전트가 실행하며, 각 에이전트는 서로 독립적으로 구현할 수 있다.

에이전트가 하는 일쓰는 패턴
행동 계획을 세운다패턴 13 Chain of Thought (5장)
필요한 데이터를 검색한다패턴 6 Basic RAG (3장) · 패턴 9 Index-Aware Retrieval (4장)
도구를 호출한다패턴 21 Tool Calling (7장)
오류에서 회복한다패턴 18 Reflection (6장) · 패턴 31 Self-Check (9장)
위험 ↔ 창의성 균형패턴 29 Template Generation · 패턴 30 Assembled Reformat (9장)
중요한 것은
각 에이전트에 필요한 패턴을 쉽게 구현할 수 있는
추상화 수준과 프레임워크를 고르는 일
💡 예 — RAG가 필요한 에이전트라면 LlamaIndex를 기반 프레임워크로 삼아 시작해 볼 만하다.
📑 "에이전트마다 다른 프레임워크"가 이 설계의 핵심입니다 — 전체를 하나의 멀티에이전트 프레임워크로 묶지 않았기에 가능한 자유입니다.
8개 패턴이 이 한 줄에 몰려 있는 이유입니다.

설계 결정이유
프롬프트를 파일에서시스템 프롬프트가 하드코딩된 문자열이 아니라 Jinja2 템플릿 설정 파일에서 읽어 온다 → 설치본마다 프롬프트 설정을 다르게 가져갈 수 있다
DEFAULT_MODEL간사가 하는 요약 작업에는 품질이나 속도 면에서 특별한 요구사항이 없다
PydanticAILLM과 클라우드에 매이지 않도록
⚠️ retries=2 — 저자가 스스로 안티패턴이라 부른 것

이것은 2장 패턴 1 Logits Masking을 설명하며 다뤘던 "될 때까지 다시 해 보는" 안티패턴입니다. 그런데도 쓴 이유는 —

LLM 호출의 성공률이 90%를 넘을 때는 받아들일 만하다. 그 경우 거절률이 1% 아래로 떨어지면서도 꼬리 지연시간(tail latency)이 합리적인 수준에 머물기 때문이다.
💡 0.9 → 실패 10%, 두 번 재시도 → 0.13 = 0.1%. 안티패턴에도 쓸 수 있는 조건이 있다는 점을 명시한 드문 대목입니다.
안티패턴을 쓰면서 그 근거를 숫자로 대는 태도가 이 책답습니다.

async def consolidate(self,

        # 1단계: 이 주제로 글을 쓸 수 있는 사람을 찾는다
        writer = WriterFactory.create_writer(await self.find_writer(topic))

        # 2단계: 그 작가에게 초기 초안을 만들어 달라고 요청한다

🛡️ 입력 가드레일

시스템이 사용자 입력을 받거나 신뢰할 수 없는 시스템에서 데이터를 읽어 올 때는 반드시 입력 가드레일(패턴 32)을 둬야 한다. 출발점으로는 패턴 17 LLM-as-Judge를 써서 구현할 수 있다.
class InputGuardrail:
    def __init__(self, name: str, condition: str, should_reject=True):
        self.system_prompt = PromptService.render_prompt(
                                "InputGuardrail_prompt",
                                 condition=condition)

        self.agent = Agent(llms.SMALL_MODEL,
                           output_type=bool,
                           model_settings=llms.default_model_settings(),
                           retries=2,
                           system_prompt=self.system_prompt)

async def is_acceptable(self, prompt: str,

return result.output
💡 두 작업을 동시에 시작해서 가드레일이 원래 작업을 늦추지 않게 합니다. 가드레일 검사가 실패하면 두 번째 호출도 함께 종료됩니다.
📑 9장 9.4.3의 코드가 그대로 나왔습니다 — 거기서 저자가 솔직히 밝힌 한계도 그대로 적용됩니다: "LLM이 그 호출을 실행하는 것 자체는 막지 못한다" — 비용은 이미 나가고 유출만 막는 셈입니다.
⚖️ 지연이 중요하면 병렬로, 비용이 중요하면 순차로. 이 앱은 코파일럿이라 지연이 더 중요해서 병렬을 골랐습니다.
선택의 근거가 애플리케이션 성격에서 나온다는 점이 중요합니다.

📊 로그는 모니터링 프로그램의 일부

모든 가드레일은 guards.log에 기록된다. 그래야 —
  • 가드레일을 모니터링하고
  • 특이한 공격을 식별하고
  • 실제로 관측되는 분포에 맞춰 모델을 파인튜닝할 수 있다
이것은 더 큰
체계적 모니터링 프로그램의 일부여야 한다
📑 그 프로그램에서는 성능 저하 테스트(8장 패턴 27)를 수행하고, 애플리케이션이 GPU나 지연시간의 제약에 부딪히는 지점을 찾는다. 그렇게 발견한 병목을 다루는 방법은 8장의 패턴들이 알려 준다.
🔒 가드레일만으로는 부족하다 — 저자는 다음도 반드시 구현하라고 합니다.

• 견고한 접근 통제
• 정책 관리
• 감사 로깅
• 사람이 개입하는 체크포인트(human-in-the-loop checkpoints)

그래야 사용자와 에이전트가 미리 정해 둔 범위 안에서만 움직인다.
9장이 가드레일 하나였다면, 여기서는 그것을 운영 프로그램으로 확장합니다.

📋 관리자 콘솔에서 보이는 것 — 코파일럿 모드에서는 관리자 콘솔로 전환해 로그를 볼 수 있습니다.

• 첫 줄 — "Squaring the circle(원적 문제)"이라는 입력에 대해 AI가 잘못된 작성 에이전트를 제안했다는 알림. AI는 수학 작성 에이전트를 제안했지만 사람이 역사 작성 에이전트로 바꿨다
• 두 번째 줄 — 초기 초안이 수정되었음. AI가 생성한 초안과 사람이 수정한 초안이 둘 다 저장된다
사용자 인터페이스가
평소대로 돌아가는 것만으로
사람 피드백 데이터가 모인다
"원적 문제"는 수학 용어지만 역사적 맥락이 있어 사람이 바꾼 사례입니다.

AI에 들어가고 나온 프롬프트 · 입력 · 출력이 prompts.log와 evals.log에 기록되어 오프라인 평가와 사후 학습을 가능하게 한다.

💡 예 — 키워드가 얼마나 좋은지 평가하려면 그 키워드가 로그에 남아 있어야 합니다. 오프라인 평가 예제는 evals/evaluate_keywords.py에 있습니다.
⏰ 결과는 며칠 뒤에 안다

어떤 활동의 결과가 얼마나 좋았는지는 며칠이 지나서야 알게 되는 경우가 많다. 그러므로 워크플로의 단계들을 서로 엮어 두었다가 실제 성과와 비교해서, 비즈니스에 의미 있는 평가 지표를 끌어낼 수 있어야 한다.
지표이 교육 유스케이스에서는
매력도그 주제를 수업 계획에 넣은 교사의 수
몰입도끝까지 읽은 학생의 수
기능적 성과그 주제에 관한 전국 시험 문항을 맞힌 학생의 비율
📑 사람 피드백과 오프라인 평가는 패턴 5 Content Optimization(2장) · 패턴 15 Adapter Tuning(5장) · 패턴 20 Prompt Optimization(6장)에 쓰여, AI 에이전트를 사람의 선호와 비즈니스 성과에 더 가깝게 정렬시킵니다.
⚠️ 규모의 문제 — 하루 수백만 건을 처리하는 소비자 앱이라면 모든 프롬프트를 로깅하는 것이 성능을 견딜 수 없을 만큼 떨어뜨릴 수 있습니다. 그럴 때는 샘플링 전략을 마련해야 합니다.
세 지표 모두 "글이 좋은가"가 아니라 "일이 되었는가"를 잽니다.

⚠️ 저절로 모이는 피드백의 다섯 가지 부족분

💼 비유 — 신입 사원에게 일을 시키고 상사가 고친 자국만 보고 배우라고 했다고 합시다.
문제속뜻내용
데이터 양
data size		상사가 바빠서 잘 안 고침AI 생성 품질을 개선하기에 충분한 사람의 수정을 얻지 못하는 경우가 많다. 유기적 피드백에만 기댈 수 없다
데이터 복잡도고치는 건 늘 쉬운 일뿐대부분의 워크플로는 비교적 단순한 작업인 반면, 가치가 큰 활동일수록 더 복잡하고 더 드문 입력을 다룬다
세밀한 피드백맨 마지막에 통째로 다시 씀전문가들은 AI가 실수한 바로 그 지점이 아니라 맨 마지막 단계에서 출력을 확 뜯어고친다 → 어느 에이전트를 학습시켜야 하는지가 가려진다
자동화 피로
automation fatigue		잘해질수록 안 읽고 결재AI가 점점 좋아지면 사람은 출력을 대충 훑기만 하고 고치지 않게 된다 — 자동화 역설(Automation Paradox)의 한 갈래
잘못된 레이블상사도 가끔 틀림사람도 완벽하지 않아 잘못 고칠 수 있다. 전문가마다 개인적인 문체가 있고, 시스템 의도와 다르게 상황을 해석할 수도 있다
저절로 모이는 피드백은
양도 부족하고 편향돼 있다
