5.4.1 문제

응답이 원하는 모습이 아니라면
모델의 능력을 여는 정석은 프롬프트입니다. 그런데 응답이 원하는 모습이 아니라면?

🍨 원칙 vs 구체적 아이디어

프롬프트
아이스크림의 맛을 개선할 방법 세 가지를 제안해 줘.

❌ 받은 응답 — 원칙

1. 고품질의 신선한 재료를 사용한다
2. 소금이나 로스팅한 재료를 더해 맛의 깊이를 살린다
3. 베이스를 충분히 냉각하고 빠르게 얼린다

✅ 원하는 응답 — 구체적

1. 민트나 시트러스 제스트를 베이스에 인퓨징
2. 로스팅한 견과류나 부순 쿠키 믹스인
3. 서빙 직전 플레이크 소금을 얹기

나쁘지 않지만 이것들은 원칙이다
💡 이런 시연 예시를 수백 개 갖고 있고, 애플리케이션이 그와 비슷한 응답을 내놓기를 바란다면 어떻게 해야 할까?
차이가 미묘합니다. 틀린 답이 아니라 "우리 스타일이 아닌" 답이에요.

❌ 곧바로 떠오르는 두 선택지 — 둘 다 별로

선택지왜 안 되나
프롬프트 엔지니어링
상세 지시 붙이기		손으로 쓰는 것은 많은 과제로 확장되지 않는다. 복잡한 프롬프트는 비용을 키우고, 표현이 조금만 달라져도 성능이 크게 달라져 테스트가 어렵다. 무엇보다 응답을 시연된 응답에 가깝게 만드는 체계적인 방법이 없다
퓨샷 학습
컨텍스트에 예시 몇 개		선택한 예시가 분포 전체를 담지 못하면 효과가 없다. 예시를 추론 요청마다 함께 보내야 해 컨텍스트를 잡아먹고 비용·지연을 늘린다. 예시 몇 개를 넘어서면 확장되지 않는다
Adapter Tuning은 —
프롬프트 엔지니어링보다 원칙적이고
퓨샷보다 더 많은 예시로 확장되며
전체 파인튜닝보다 덜 번거롭고 사고가 적다
수백~수천 개의 입력-출력 쌍이 있다는 상황에서의 이야기입니다.

5.4.2 해법

어댑터 아키텍처
파라미터 효율적이고, 배포가 편하며, 추론이 빠른 특수한 아키텍처 덕분입니다.

⛔ 먼저 — 쓰면 안 되는 것

Adapter Tuning은 아주 작은 조정을
그것도 몇 개 층에만 가한다

그래서 튜닝된 모델은 원래 하던 일을 대체로 그대로 하면서, 학습된 특화 과제만 조금 더 잘합니다. 파운데이션 모델이 이미 할 수 있는 것에 가까운 능력을 더할 때 잘 작동합니다.

하려는 것써야 할 것
업계 전문 용어 · 새 언어
새 낱말과 연관(당뇨병↔인슐린 결핍)		계속 사전학습(CPT) — 보통 전체 파인튜닝을 수반. Adapter Tuning은 그런 학습이 가능할 만큼 모델을 바꾸지 못한다
새 지식RAG (3장)
새로운 과제 집합Evol-Instruct (패턴 16) — 더 큰 데이터셋과 더 긴 학습
특화 과제
분류 · 요약 · 추출형 QA · 브랜드 톤 챗봇		Adapter Tuning
💡 왜 새 지식이 안 되나 — 어떤 나라가 새 총리를 선출했다고 해 봅시다. 그 이름이 든 문장 수백 개로 학습시킨다고 해서, 사전학습 당시 총리에 대해 마주친 수천 건의 기사를 이길 가능성은 매우 낮습니다.
이 비유가 직관적입니다. 소수의 새 예시가 방대한 옛 학습을 못 덮어써요.

🏗️ 어댑터 층의 구조

어댑터 층은 파운데이션 모델의 기본 빌딩 블록인 트랜스포머 블록 안에 끼워 넣는다. 어디에 끼우는지는 방식마다 다르다.

1차원 축소
768 → 64
→
2비선형 활성화
ReLU
→
3차원 복원
64 → 768
총 파라미터 = 768 × 64 × 2
파운데이션 모델의 수십억 개보다 훨씬 작다
이름유래
PeFT학습할 파라미터가 훨씬 적어서 — 파라미터 효율적 파인튜닝
LoRA비선형성이 트랜스포머 블록보다 낮은 차원(여기선 64)에서 일어나서 — 저랭크 적응. (연구자들이 말하는 엄밀한 LoRA 아키텍처는 아니지만 통칭)
QLoRA파운데이션 모델의 양자화된 버전을 학습 — 양자화 인지 저랭크 적응
768과 64는 예시 숫자입니다. r을 얼마로 잡느냐가 데이터셋 크기에 따라 달라져요.

🎯 세 가지 핵심

1특화 과제를 하는 법을 가르친다 — 분류 · 요약 · 추출형 질의응답 · 회사 브랜드에 맞는 챗봇. 업계 전문 용어나 새로운 사실을 위한 것이 아니다
2파운데이션 모델 가중치는 얼어 있고 어댑터 층이 일부 층에 작은 갱신을 제공한다 → 매우 효율적. GPU 한 장으로 한 시간 안에 끝나는 경우가 많다
3학습 데이터셋이 딥러닝 통상보다 작아도 된다 — 전체 재학습(수백만 토큰)이나 CPT(파국적 망각 위험)가 아니라 어댑터 가중치만 학습하므로. 실무에서 100개 예시로도 충분할 수 있다
학습어댑터 가중치만
조정
→
배포그 가중치만
저장
→
추론파운데이션 모델에
다시 끼워 넣기
💡 파운데이션 모델은 수정되지 않았으므로 어댑터 가중치만 저장하면 됩니다 — 추가 저장 요구가 최소화됩니다. 학습 시간의 대부분은 파운데이션 모델이 여전히 추론을 해야 한다는 사실에서 옵니다.
학습이 빠른 이유가 파라미터가 적어서만은 아닙니다. 순전파는 여전히 전체 모델을 통과해야 하거든요.

💻 학습 — 핵심 설정

# ① 4비트 양자화로 로드 (QLoRA)
BitsAndBytesConfig(load_in_4bit=True,
    bnb_4bit_use_double_quant=True, bnb_4bit_quant_type="nf4", ...)

# ② 어댑터 설정
peft_config = LoraConfig(
    r=16,               # 입력을 16차원으로 축소. 데이터셋 크기에 맞춰
    lora_alpha=16,      # 출력이 α/r 만큼 비례 → α=r 이면 그대로 쓰임
    lora_dropout=0.05,
    target_modules="all-linear",
    modules_to_save=["lm_head", "embed_tokens"])
                          # 어텐션 헤드와 입력 임베딩도 저장

# ③ 지도 학습
sft_config = SFTConfig(output_dir="gemma-radiology",
    num_train_epochs=1, learning_rate=2e-4)  # QLoRA 논문 기준
파라미터의미
학습률작을수록 원래 모델에서 벗어날 여지가 줄어든다
에폭 수많을수록 학습 데이터셋에 더 맞춰지는데, 그 대가로 이전 학습을 잊을 수 있다
💡 오픈 웨이트 모델에 하는 이유 둘 — ① 특화 과제엔 더 작은 모델이면 되고 GPT-4 같은 거대 모델이 필요 없다 ② 인터넷과 분리된 로컬 하드웨어에서 돌릴 수 있다
클로즈드 웨이트 모델은 층에 접근할 수 없어서 완전 관리형 서비스로 우회합니다.

💬 학습 데이터도 메시지로

대상 모델이 추론 시 메시지를 받는다면, 학습 데이터도 메시지로 구성해야 한다.

[
 {'role': 'system',    'content': 'You are a food influencer.'},

                             the flavor of ice cream.'},

                             ingredients like mint or citrus zest...'}

입력 프롬프트user
→
출력 응답assistant
💡 이 메시지들이 전달되면 모델은 자기 응답을 원하는 assistant 출력과 비교해 학습 과정에서 그래디언트를 갱신합니다.
trainer = SFTTrainer(model=model, args=sft_config,

trainer.train(); trainer.save_model()

5.4.3 예제

영상의학 캡션 — 멀티모달
파인튜닝은 텍스트 모델에만 국한되지 않습니다. 이미지를 입력받아 텍스트를 출력하도록 가르쳐 봅니다.

🏥 목표 — 해부학적 서술만

캡션이 이미지에 나타난 해부 구조를 설명하고 문제를 간결히 기술하되, 완전한 진단이나 설명은 하지 않기를 원한다.

✅ 원하는 캡션

좌측 상악동의 폐색을 보여 주는 축상면 전산화 단층 촬영

❌ 파운데이션 모델(Gemini) 응답

부비동의 축상면 CT 영상으로, 좌측 상악동 전체를 채우는 크고 팽창성이며 균질한 저감쇠 종괴가 관찰되어 점액낭종에 합치한다. 팽창하는 병변의 압력 효과로 인한 부비동 골벽의 얇아짐과 휘어짐에 주목하라.

⚠️ 식별은 정확하지만 너무 길고, 진단에 대한 긴 설명이 붙었습니다.
💡 프롬프트 엔지니어링("1~2문장으로", "진단을 설명하지 말 것")으로 고쳐 볼 수도 있지만 — 그것이 선택지가 아닌 경우를 다음 슬라이드에서 봅니다.
답이 틀린 게 아니라 형식이 다른 겁니다. 아이스크림 예와 같은 구조예요.

🚫 프롬프트 엔지니어링이 선택지가 아닌 때

이유내용
비용코너 케이스를 만날수록 프롬프트가 극도로 길어져 두세 쪽 분량의 상세 지시가 되는 일도 드물지 않다. 토큰 수를 크게 늘리고 애플리케이션의 확장을 너무 비싸게 만든다 (8장 패턴 26 프롬프트 압축 참조)
위치규제 때문에 온프레미스에서, 또는 연결성 때문에 엣지에서 돌려야 할 수 있다. 그러면 지시 수행 능력이 더 제한적인 더 작은 모델(8장 패턴 24)을 써야 하고, 상세한 프롬프트가 잘 작동하지 않는다
유지보수상세해질수록 시스템이 프롬프트의 정확한 표현에 극도로 민감해진다. 파운데이션 모델이 바뀔 때마다, 도구 중 하나가 바뀔 때조차 통합 테스트를 해야 한다
이런 상황이라면
특정 과제를 위해 더 작은 모델을 사후 학습하는 것을 고려하라
프롬프트 엔지니어링은 개념 증명에는 유용하지만 프로덕션으로 옮길 때 이 셋에서 막힙니다.

🔁 5.4.4 두 가지 변형

① 모델 병합

예제에서는 어댑터 가중치를 기반 모델과 따로 저장했다 — 저장 공간 절약. 그러나 기반 모델을 로드해 어댑터를 끼워야 하므로 배포 관리가 어려워지고(두 모델을 다 갖고 있어야 한다) 지연도 약간 늘어난다.

peft_model = PeftModel.from_pretrained(model, args.output_dir)
merged_model = peft_model.merge_and_unload()
merged_model.save_pretrained("merged_model", max_shard_size="2GB")

② 클로즈드 웨이트 모델

독점 제공사들은 완전 관리형 서비스를 제공한다 — 지정한 형식의 데이터셋을 가리켜 주기만 하면 파인튜닝하고 엔드포인트에 배포해 준다.

Vertex AI에서는 데이터셋을 같은 메시지 형식으로 구성하고, 기반 모델과 에폭 수를 지정한다. 단순화를 위해 학습률과 어댑터는 배수(multiplier)로 설정한다.

⚠️ 어댑터를 더 크게 잡는 것은 보통 학습 예시가 더 많을 때만 합니다.

병합할지 말지는 저장 공간과 배포 편의의 트레이드오프입니다.
