2.2.1 문제

부탁의 값은 누가 치르는가
LLM 출력은 대개 다운스트림 애플리케이션으로 넘어갑니다. 그쪽은 온갖 파싱과 검증 없이 응답을 바로 다루기를 기대하죠.

⚠️ 지시 이행에 기대는 것의 3가지 죄

원하는 형식은 쉼표로 구분된 목록처럼 단순할 수도, 문법적으로 유효한 SQL 문처럼 복잡할 수도 있다. 순진한 접근은 프롬프트에 형식을 쓰고 따라 주기를 바라는 것.

죄내용
취약함
brittle		LLM 버전이 바뀌면 깨질 수 있다
불안정함
unstable		LLM 생성은 확률적(stochastic)이다
비쌈
expensive		지시를 잘 따르는 것은 보통 더 큰 모델이다
💡 Anthropic 같은 일부 제공자는 실제로 이 접근을 권장합니다. 문제는 이 방법이 나쁘다는 게 아니라 보장이 없다는 것입니다.
세 번째가 은근히 아픕니다. 형식 하나 지키려고 더 큰 모델을 쓰는 건 추론 비용 전체를 올리는 일이에요. 문법을 쓰면 작은 모델로도 형식은 100% 지켜집니다.

🔑 안티패턴으로 만드는 결정적 한 문장

LLM 호출을 소비하는 모든 쪽이
LLM이 지시를 안 따를 가능성에
대비해야 한다

❌ 부탁했을 때

응답을 받는 모든 코드에 try-catch와 검증 로직이 들어간다. 파서 하나가 아니라 호출 지점마다.

✅ 못 박았을 때

그게 전부 사라진다. 다운스트림은 타입을 믿고 바로 쓴다.

더 나은 접근은 원하는 규칙을 일반화 가능한 방식으로 표현하는 것이고, 그것을 문법이라 부릅니다.
형식 검증 코드는 한 곳에 모이지 않습니다. LLM 응답이 흘러가는 모든 경로에 퍼져요. 그게 진짜 비용입니다.

① 방법 1 — BNF 문법 + 로짓 프로세서

1원하는 구문을 형식 문법(BNF, Backus–Naur Form)으로 표현
2이 문법을 적용할 LogitsProcessor를 만든다
3그 로짓 프로세서를 파이프라인에 넘긴다
grammar = IncrementalGrammarConstraint(
              grammar_str, "timestamp_literal", pipe.tokenizer)
grammar_processor = GrammarConstrainedLogitsProcessor(grammar)

results = pipe(input_message, max_new_tokens=256,
               do_sample=False, logits_processor=[grammar_processor])
🔑 제약을 만들 때 루트 요소를 지정합니다 → SQL 명세 전체를 넘기면서도 원하는 데이터 타입이나 명령만 골라 쓸 수 있습니다.
🔍 거의 모든 형식·프로그래밍 언어에 이미 만들어진 BNF가 있습니다. "BNF for [주제]"로 검색하면 정규표현식, SQL TIMESTAMP·CREATE INDEX, CSV 한 행 등이 금방 나옵니다.
책의 타임스탬프 문법 예시는 날짜만 또는 시간만 담긴 경우까지 포함합니다. 허용되는 타임스탬프의 형태가 여러 가지라서요.

🔍 BNF는 겁먹을 게 없다

"이건 이런 것들로 이루어진다"를 적는 표기법일 뿐이다. 기호는 둘뿐 — ::= 는 "~로 정의된다", | 는 "또는".

year ::= [1-2][0-9][0-9][0-9] | unk
  ↑        ↑                     ↑
 이름   이런 모양이거나        아니면 unk
📜 읽으면 — "연도는 1이나 2로 시작하고 숫자가 3개 더 붙거나, 아니면 unk다."
등록해 두면 모델은
물리적으로 다른 형태를 못 만든다
정규표현식을 읽을 줄 알면 BNF도 읽을 수 있습니다. 문턱이 생각보다 낮아요.

②③ JSON 모드와 스키마

② 표준 데이터 형식 — 가장 쉬운 길
response = client.chat.completions.create(
    model=MODEL_ID, messages=input_message,
    response_format={"type": "json_object"})
⚠️ 필수 조건 — 프롬프트가 JSON 출력을 원한다고 명시해야 합니다. response_format은 "JSON이 아닌 토큰을 막는" 장치지 "JSON을 만들라"는 지시가 아닙니다.
③ 사용자 지정 스키마 — 구조화된 출력
@dataclass
class Receipt:
    items: LineItem[]
    total_amount: float

response = client.models.generate_content(
    model='gemini-2.0-flash', contents=[...],
    config={'response_mime_type': 'application/json',
            'response_schema': Receipt})
💡 응답 자체는 여전히 JSON 문자열입니다. Pydantic 객체는 오로지 구조를 지정하는 용도이고, 파싱은 json.loads(..., object_hook=...)로 따로 합니다.
dataclass를 넘긴다고 dataclass 객체가 돌아오는 게 아닙니다. PydanticAI 같은 래퍼가 그 파싱을 대신 해주는 거예요.

2.2.3 예제

A 산술식 · B 파이프 · C JSON · D 인보이스
예제 네 개가 전부 다른 걸 증명합니다. 특히 B와 C를 나란히 보는 게 중요해요.

🔢 예제 A — 산술식

초등 교육 소프트웨어. 답("36")이 아니라 산술식을 생성하게 하고 싶다 — 다스의_수 × 다스당_개수 = 달걀_수

root  ::= (expr "=" ws term "\n")+
expr  ::= term ([-+*/] term)*
term  ::= ident | num | "(" ws expr ")" ws
ident ::= [a-z] [a-z0-9_]* ws
num   ::= [0-9]+ ws
질문응답판정
사과가 총 몇 개?bill_apples + mae_apples = total_apples
3 + 2 = 5		✅ 정확
사과가 오렌지보다 많나?3 + 2 = 5
2 + 4 = 6		❌ 못 냄
문법이 정말로 출력을 제약하는지는 문법이 허용하지 않는 답이 정답인 질문을 던져 확인할 수 있습니다.
정답은 (3+2) > (2+4)인데 문법에 > 가 없습니다. 그래서 모델은 식만 나열하고 비교는 하지 못했어요.

🎭 같은 사실을 뒤집어 읽기

✅ 저자의 해석

문법에 >가 없으니 출력할 수 없다. 제약이 제대로 작동하는 증거.

⚠️ 뒤집으면

문법을 잘못 만들면 모델은 틀린 답을 낼 수밖에 없다. 그것도 아주 그럴듯하게.

📝 객관식 시험지에서 정답 보기를 빼버린 것과 같습니다. 학생은 답을 알아도 고를 수 없어 오답을 찍고, 채점자는 학생이 모른다고 오해합니다.
📑 패턴 1의 SWIFT 아크로스틱과 같은 종류의 함정입니다 — 제약을 걸면 규칙은 지켜지지만, 무엇을 포기했는지는 결과에 안 나타납니다.
이 덱에서 가장 중요한 슬라이드입니다. 내가 만든 문법이 정답을 막고 있는지는 반례를 던져보기 전엔 모릅니다.

🔢 예제 B — 문법이 데이터를 정제한다

record    ::= author separator title separator year
author    ::= [a-zA-Z ]* | unk
title     ::= [a-zA-Z ]* | unk
year      ::= [1-2][0-9][0-9][0-9] | unk
unk       ::= "NULL"
separator ::= "|"

악센트·발음 구별 기호가 붙은 비영어 문자를 허용하지 않는다. 다운스트림이 7비트 ASCII를 기대하는 레거시 시스템이라면 결정적이다.

입력출력관찰
Gabriel García Márquez, 1985Gabriel Garcia Marquez | Love in the Time of Cholera |1985악센트 제거
Tirukkural (ྌி்), 연도 정보 상충Valluvar | The Tirukkural |NULL타밀 문자 탈락
연도 NULL
💡 본문에 제목이 두 형태로 등장하지만 문법에 맞는 것은 하나뿐이고 그것이 결과에 나타납니다. 연도는 정보가 상충하자 지어내지 않고 NULL을 골랐습니다.
NULL이 바로 탈출구입니다. 문법이 "모르겠으면 NULL"이라는 길을 열어둔 덕분에 환각이 막혔어요.

⚠️ 예제 C — JSON 모드의 한계

{"author": "Gabriel García Márquez",
 "title": "Love in the Time of Cholera",

필드가 author·title·year인 것은 제약된 결과가 아니라 GPT-4o-mini 같은 고성능 모델에 의존한 결과입니다.

JSON 모드는 "JSON임"만 보장하고
"무엇이 들어가는지"는 보장하지 않는다
예제 B와 나란히 놓으면 차이가 분명합니다. 같은 입력인데 B는 문법이 실제로 악센트를 제거했고 C는 운에 맡겼어요.

📦 예제 D — 보장의 맛

class CurrencyEnum(str, Enum):
    USD = 'USD'; UKP = 'UKP'; INR = 'INR'; EUR = 'EUR'

@dataclass
class Invoice:
    purpose: str
    amount: float
    currency: CurrencyEnum = CurrencyEnum.USD

agent = Agent(model, result_type=Invoice, system_prompt=system_prompt)
response = agent.run_sync(paragraph)   # → Invoice 객체가 보장된다
입력 → 출력
"Requesting reimbursement for taxi ride to airport. I paid $32.30."

Invoice(purpose='taxi ride to airport', amount=32.3,
        currency=<CurrencyEnum.USD: 'USD'>)
💡 PydanticAI를 쓰면 LLM 비종속적(LLM-agnostic)으로 구조화된 출력을 얻습니다. 모델을 바꿔도 이 코드는 그대로입니다.
1장에서 본 "LLM 비종속 프레임워크"의 실제 이득이 여기서 나타납니다.

❌ 책이 안티패턴으로 못 박는 프롬프트

"제발 추가 서식이나 긴 설명을 붙이지 마세요.
그냥 YES 또는 NO로만 답하세요. 반드시 대문자로 써 주세요."

대신 보장한다.

agent = Agent(model, result_type=Literal["YES", "NO"])

실무 프롬프트를 보면 "반드시", "절대", "제발"이 참 많습니다. 그 문장이 보이면 문법으로 바꿀 수 있는지부터 확인하세요.

2.2.4 고려사항과 대안

BNF vs Pydantic · 실패 · 이름의 함정
여기부터가 이 패턴을 실제로 쓸 때 다치는 지점들입니다.

⚖️ 변형 — BNF vs Pydantic

Pydantic이 나은 점이유
사용 편의성dataclass 몇 줄이 BNF 규칙보다 쉽다
지연 시간BNF는 클라이언트 처리, Pydantic은 서버 처리 → 네트워크 호출이 줄어든다
모델 지원BNF는 logprobs 접근 필요(보편적이지 않다). 모든 현대 모델이 dataclass 제약을 지원
🔑 그럼에도 BNF가 유연하다 — 스타일 규칙이 단순한 데이터 형식 이상이면 BNF여야 합니다. Enum을 넘어서는 검증은 Pydantic으로 하기 어렵습니다.
<credit_card_number> ::= <visa> | <mc> | <amex>
<visa> ::= "4" <digit>{12,15}
<mc>   ::= ("51".."55" <digit>{14}) | ("2221".."2720" <digit>{12})
<amex> ::= "34" <digit>{13} | "37" <digit>{13}
같은 일을 Pydantic으로 하려면 @field_validator로 검증 로직을 직접 써야 하고, 책에 40행 가까운 구현이 실려 있습니다 — 더 이상 단순한 dataclass가 아닙니다. 자바스크립트에서는 Zod로 같은 일을 합니다.
스키마 방식이 파이썬에만 국한되지 않는다는 점도 책이 짚습니다. Zod로 Ollama와 OpenAI의 스키마 지정 기능을 쓸 수 있어요.

🔁 언제 패턴 1로 갈아타나

  • 규칙을 dataclass로 표현할 수 없다 — 표현이 아니라 로직이다 (특정 상황에서만 경쟁사 제품명 마스킹)
  • BNF가 지나치게 복잡하고 디버깅이 어렵다
  • 규칙이 동적이며 내용에 따라 달라진다 — 신제품 출시 얘기일 땐 가리고 기출시 제품엔 안 가림
  • 규칙을 DB나 규칙 엔진에서 가져와야 한다 — 가릴 대상이 고객사마다 다름
  • 마스킹이 사용자 입력에 의존한다 — 자동완성 유스케이스
  • 규칙이 외부 도구·API 호출을 수반한다
💡 공통점은 "규칙이 고정된 모양이 아니다"입니다. 모양이 고정이면 문법, 그때그때 달라지면 로짓 마스킹.
패턴 1의 대안들(스타일 전이 · 더 강력한 모델 · 될 때까지 다시 해 보기 · 성찰)은 같은 이유로 문법의 대안이기도 합니다.
