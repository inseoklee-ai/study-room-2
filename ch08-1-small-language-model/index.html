8.1.1 문제

GPU 요구사항과 느림
설명을 단순하게 하려고 이 절은 로컬에서 직접 돌린다고 가정합니다.

💰 GPU 요구사항

프런티어 LLM을 자체 하드웨어에서 돌리려면 최신 GPU와 메모리가 넉넉한 VM이 필요하다. 하이퍼스케일러(AWS · Azure · GCP · OCI) 위에 있다면 이 요구사항은 높은 청구서와 물량 부족으로 돌아온다 — 집필 시점 기준 하이퍼스케일러는 원하는 하드웨어가 동나는 일이 예사다.

Meta Llama 4 Scout —
80GB H100 GPU 4장
단일 인스턴스 시간당 10달러 초과
2025년 6월 기준
💡 API로 부르면 해결되나? 기계를 직접 운영할 필요는 없어지지만 비용과 가용성 문제가 사라지지는 않습니다. 메모리와 물량 부족을 내가 관리하느냐 제공자가 관리하느냐가 달라질 뿐입니다.
📑 그래서 이 절의 해법은 완전 관리형 원격 모델만 쓰는 경우에도 그대로 적용됩니다 — 호스팅되는 SLM 버전으로 갈아타면 됩니다.
자체 호스팅이든 API든 결국 같은 제약에 부딪힙니다.

❌ 그냥 작은 모델을 쓰면 안 되나

작업이 쉽다면 그럴 수도 있다. 그러나 작은 모델은 복잡한 작업에서 자주 무너진다. 파이썬 코드의 문서를 생성해 보자.

그냥 작은 모델로 바꾸는 것만으로는 같은 품질을 얻을 수 없습니다.

8.1.2 해법

세 가지 선택지
보통은 프런티어 모델로 프로토타입을 만든 뒤 작은 것으로 바꾸려 시도하게 됩니다.

✅ 세 가지 선택지

옵션무엇을 하나대가
1. 증류
distillation		모델의 지식 범위를 좁혀 크기를 줄인다. 작은 모델은 내 애플리케이션에 필요한 작업만 한다일반성을 잃는다
2. 양자화
quantization		모델 파라미터의 정밀도를 낮춰 메모리를 덜 쓰게 한다정확도를 아주 조금 양보
3. 추측 디코딩
speculative decoding		작은 모델과 큰 모델을 한 쌍으로 쓴다. 정확도 손해 없이 지연 시간을 줄인다복잡도가 늘어난다
❌ 다루지 않는 대안 — 모델 프루닝(model pruning)
지연 시간을 줄이는 또 다른 방법이지만, 여기 세 선택지보다 결과 품질이 떨어지는 편이라 이 장에서는 다루지 않는다. 다른 대안들과 달리 프루닝은 LLM 성능에 상당한 타격을 준다.
💡 저자가 왜 안 쓰는지까지 적어 둔 대안입니다. 이런 명시적 배제는 드물어서 기억해 둘 만합니다.
세 선택지는 단독으로도, 조합해서도 씁니다.

📚 출처 — 제프리 힌턴 · 오리올 비니알스 · 제프 딘, "Distilling the Knowledge in a Neural Network" (2015). 오늘날 ML에서 널리 쓰이는 기법의 토대가 됐다.
💡 핵심 장치 — 고정된 정답을 주는 대신 교사 모델이 생성한 토큰을 작은 모델의 기대 출력으로 삼는다. 학습 중에는 큰 모델의 temperature로 확률 분포를 제어할 수 있다.
그림 8-1이 이 교사-학생 워크플로를 그린 것입니다.

💡 왜 "정답"이 아니라 "교사의 확률분포"를 베끼나

📝 비유 — 수학 선생님이 정답만 알려 주는 경우와 "나는 이 문제 답이 3번일 확률 60%, 1번 20%, 4번 10%로 본다"고 사고 과정을 알려 주는 경우. 후자가 훨씬 많은 정보를 전달합니다. 오답 중에서도 어떤 게 더 그럴듯한지까지 배우니까요.
이것이 "암흑 지식"
dark knowledge

큰 모델은 다음 토큰으로 무엇이 올지 모든 후보에 확률을 매긴다. 정답 하나만 베끼면 이 풍부한 정보가 버려진다. 그래서 증류는 확률 분포 전체를 베끼게 한다.

장치역할
온도
temperature		큰 모델이 "3번 99.9%"처럼 너무 확신하면 나머지 정보가 사실상 0이 된다. 온도로 나누면 분포가 납작해져 "3번 60%, 1번 20%…"처럼 차이가 드러난다 — 배울 게 생긴다
KL 발산
KL divergence		두 확률 분포가 얼마나 다른지를 재는 자. 학생의 분포가 교사와 같아질수록 0에 가까워진다. 학습은 이 값을 최소화하는 방향
  • 로짓(logit) — softmax를 거치기 전, 모델이 각 토큰에 매긴 원점수
  • softmax — 로짓을 합이 1인 확률로 바꾸는 함수
  • alpha — "교사 흉내"와 "정답 맞히기" 중 어디에 무게를 둘지 정하는 손잡이
증류는 정답을 베끼는 게 아니라
교사의 망설임까지 통째로 베끼는 것
이 한 줄이 증류의 전부라고 해도 됩니다.

⚙️ 증류 학습 과정

1교사 응답 생성 — torch.no_grad()로 순전파에만 집중. 큰 모델은 기울기를 계산 · 갱신할 필요가 없어 자원을 아끼고 추론이 빨라진다
with torch.no_grad():
    teacher_outputs = self.teacher_model(**inputs)
    teacher_logits = teacher_outputs.logits
2학생 응답 생성 + 표준 언어 모델링 손실 확보
student_outputs = model(**inputs)
student_logits = student_outputs.logits
task_loss = student_outputs.loss
3온도 스케일링 — 두 분포를 더 비교 가능하게. 온도가 낮으면 확신이 높은 쪽으로 몰리고, 높으면 평평해진다. 급격한 갱신 요동을 막아 준다
student_logits = student_logits / self.temperature
teacher_logits = teacher_logits / self.temperature
여기까지가 준비 단계입니다. 다음 슬라이드에서 손실을 계산합니다.

📏 유사도 측정 — KL 발산

📌 원본 수식 이미지 누락
원서 이 자리에 KL 발산의 정의 수식이 그림으로 들어가 있었으나 원본 파일 반출 과정에서 떨어져 나갔습니다. 임의로 수식을 지어내지 않고 원문이 이어서 설명하는 항의 구성만 옮깁니다.

• 첫 번째 항(엔트로피) — P의 로그 확률로 계산된다
• 두 번째 항(교차 엔트로피) — Q의 확률을 사용한다

여기서 log_softmax 항이 P(학생의 분포)의 로그 확률을 제공하며, 덕분에 계산이 효율적으로 이뤄진다.

distillation_loss = torch.nn.functional.kl_div(
    torch.log_softmax(student_logits, dim=-1),   # 학생
    torch.softmax(teacher_logits, dim=-1),        # 교사
    reduction='batchmean'
) * (self.temperature ** 2)
요소이유
학생 = log_softmax
교사 = softmax		PyTorch kl_div() 구현 방식과 얽힌 수학적 이유. 교사에 softmax를 쓰는 것은 그것이 유효한 확률 분포(합이 1)임을 보장하기 위함 — KL 발산의 수학적 정의와도 맞아떨어진다
'batchmean'학습 중 배치 전체에 걸쳐 손실을 평균
온도의 제곱을 곱함온도 스케일링은 분포를 부드럽게 만들어 지나친 확신을 막는다. 어떤 토큰을 1에 가깝게 예측하던 것을 0.6 · 0.2 · 0.1 식으로 눌러 주면, 교사가 가진 대안 토큰들에 대한 "암흑 지식"이 보존되어 학습 신호가 풍부해진다
온도의 제곱을 곱하는 이유를 원문이 명시적으로 설명하는 드문 대목입니다.

⚖️ 두 손실 합치기

loss = (1 - self.alpha) * task_loss + self.alpha * distillation_loss
alpha의미
alpha = 1증류 손실만 쓴다 — 학생이 교사에게서 배운다
alpha = 0작업 손실만 쓴다 — 학생이 데이터에서 배운다

합쳐진 손실로 학생 모델을 갱신하고, 학습이 원하는 손실 최솟값에 도달할 때까지 다음 배치를 처리한다.

🔄 메타 증류 루프 — 증류는 반복 과정으로 적용할 수 있다. 큰 모델에서 훨씬 작은 버전으로 가려면, 성능을 유지하면서 크기를 점진적으로 줄이기 위해 여러 라운드의 증류가 필요할 수 있다.
👥 앙상블 증류(ensemble distillation) — Zeyuan Allen-Zhu · Yuanzhi Li (2020). 여러 교사의 지식을 하나의 학생에게 증류할 수 있음을 보였다.

쓰는 이유 셋 — ① 교사마다 답의 서로 다른 측면을 조금씩 보여 줄 때 ② 작업 자체에 불확실성이 클 때 ③ 여러 전문 모델을 하나의 범용 모델로 압축해 프로덕션 구성을 단순화할 때
💡 실무 흐름 — 첫 버전을 프런티어 모델로 프로토타입 배포 → 들어오는 프롬프트를 로깅 → 그 유형의 프롬프트에서 잘 동작하는 증류 모델을 만든다.
"프롬프트의 구체적 유형을 식별할 수 있는 한" 증류가 효과적이라는 단서가 붙습니다.

📅 양자화를 언제 하나 — 세 시점

시점방식내용
학습 전
사전학습 최적화		저정밀도 변환학습 시작 전 낮은 정밀도로 변환 → 학습 단계 메모리 ↓, 학습 비용 절감. 다만 GPU가 저정밀도 연산을 지원해야 효과를 온전히 누린다
QAT
양자화 인식 학습		순전파에 가짜 양자화 연산을 끼워 넣는다. 모델이 학습 중에 양자화 효과를 직접 겪으며 그에 강건해지도록 "배운다". 양자화 오차를 최소화하도록 파라미터를 적응시킬 수 있어 학습 후 양자화보다 결과가 좋은 경우가 많다. 여러 해 동안 프로덕션에서 쓰여 왔고, 구글 딥마인드의 최근 연구가 놀라운 결과를 보였다
학습 중혼합 정밀도 학습연산별로 다른 정밀도 — 계산은 효율을 위해 FP16, 가중치 갱신은 안정성을 위해 FP32로 누적. 지원 프레임워크: DeepSpeed(MS), Megatron-LM(NVIDIA)
동적 양자화활성값 통계를 바탕으로 학습 중에 양자화 파라미터를 조정 → 매우 중요한 활성값은 덜 압축하고, 덜 중요한 것은 더 강하게. PyTorch가 여러 해 동안 훌륭히 지원
학습 후
PTQ		다음 슬라이드에서 세 방식을 따로 다룹니다
QAT는 "쓸 수 있다면 매력적인 대안"으로 8.1.4에서 다시 언급됩니다.

🔧 학습 후 양자화 — 세 방식

방식내용
가중치 전용 양자화
weight-only		모델 가중치만 양자화하고 활성값은 높은 정밀도로 둔다. 학습 가능한 파라미터는 낮은 정밀도로 저장하되, 네트워크를 흐르는 계산값은 FP32 같은 높은 정밀도로 계산.
→ 표준 기법: GPTQ(GPT quantization), AWQ(activation-aware weight quantization)
전체 모델 양자화
full-model		가중치와 활성값을 모두 양자화. 효율 이득이 가장 크지만 품질 저하도 더 클 수 있다.
→ 정적(보정 데이터셋으로 파라미터 결정) 또는 동적(추론 중 즉석에서 계산)
🔬 더 고급인 학습 후 기법
  • QLoRA(quantized low-rank adaptation) — 원본 베이스 모델과 함께 동작하는 어댑터를 파인튜닝하는 LoRA 개념 위에 얹은 것. 이미 양자화된 모델을 효율적으로 파인튜닝하는 데 쓸 수 있다
  • SpQR(sparse-quantized representation) — 양자화와 가중치 희소화를 결합한다
  • BitNet — 양자화를 이진 또는 삼진 표현까지 밀어붙인 극단적 저비트 접근. 마이크로소프트는 모델의 1비트 양자화를 발표했다
📑 패턴 15 어댑터 튜닝(5장)이 QLoRA의 바탕입니다. 5장을 봤다면 LoRA는 이미 아는 개념일 겁니다.
세 고급 기법은 이름만 알아 둬도 충분합니다.

💻 방법 — BitsAndBytesConfig

quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_quant_type="nf4",

quant_type="nf4"Normal Float 4 — 언어 모델에 특화되어 가중치의 통계적 성질을 더 잘 보존하도록 최적화된 형식
use_double_quant=True양자화 상수 자체를 다시 양자화 — 성능에 큰 영향 없이 메모리를 추가로 줄인다
quantized_model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=quantization_config,
    device_map="auto", torch_dtype=torch.float16, token=hf_token
)
✅ 이후에는 다른 허깅페이스 모델과 똑같이 씁니다 — quantized_model.generate(...)로 로컬 추론하거나, 저장해서 배포하면 됩니다.
💡 실무 권고 — 모델을 직접 호스팅하기로 했다면 그 모델의 4비트 버전이 정확도를 얼마나 잃는지 확인해 볼 가치가 있다. 손해가 크지 않다면 비용과 지연 시간을 상당히 아낄 수 있다.
측정해 보라는 것이 요점입니다. 대개 손해가 생각보다 작습니다.

교사 모델

매우 정확한 출력을 내지만 계산 비용이 크고 상대적으로 느린 정교한 LLM.

토큰 생성의 기준(ground truth) 역할
학생 모델

더 작고 효율적이며 빠르지만 덜 정확할 수 있는 SLM.

교사 모델의 행동을 모방하도록 특별히 학습된다 — 예: 30억 파라미터가 4,050억 파라미터를 흉내 내도록
1학생이 먼저 토큰 시퀀스를 빠르게 제안한다
2교사가 학생의 제안을 병렬로 평가해, 자신이라면 같은 시퀀스를 생성했을지 검증한다
3동의하면 시퀀스를 받아들여 곧바로 출력
4동의하지 않으면 정확도를 확보하기 위해 표준적인 토큰 단위 생성 방식으로 되돌아간다

🧠 추측 디코딩이 왜 통하나

모든 토큰이
큰 모델의 계산력을 필요로 하지는 않는다

토큰의 난이도는 편차가 크다 — 흔한 단어나 뻔한 마무리처럼 단순하고 예측 가능한 토큰은 작은 학생 모델도 안정적으로 만들어 내는 반면, 복잡하거나 맥락 의존적인 토큰은 교사의 고급 능력이 필요하다.

Step 1:
Student: "The [talented] [chef]"
Teacher: ✓ Accepts (common phrase)

Step 2:
Student: "cooked [a] [delicious]"
Teacher: ✓ Accepts (common food context)

Step 3:
Student: "[soup]"
Teacher: ✗ Rejects
Teacher generates: "bouillabaisse" (rare, specific word)

Step 4:
Student: "[for] [dinner]"
Teacher: ✓ Accepts (common ending)
⚡ 속도가 빨라지는 두 이유 — ① 제안 토큰을 작은 LLM으로 생성하고, 게다가 여러 토큰을 한 번에 생성할 수 있다(검증해 줄 모델이 있으니 그럴 여유가 있다) ② 예측 검증도 빠르며, 작은 모델이 틀린 토큰만 고치면 된다
그림 8-3이 이 한 번의 순전파를 그린 것입니다.

🔧 방법 — vLLM

llm = LLM(
    model="google/gemma-2-9b-it",        # 검증 · 교정
    tensor_parallel_size=1,
    speculative_model="google/gemma-2-2b-it",  # 다음 토큰 예측
    num_speculative_tokens=5,
)

🌐 비유 — 번역 회사에서 신입이 초벌 번역을 빠르게 해 놓으면 베테랑이 읽으면서 확인합니다. 읽고 확인하는 건 처음부터 번역하는 것보다 훨씬 빠릅니다. 틀린 문장만 베테랑이 다시 씁니다. 결과물의 품질은 베테랑이 전부 번역한 것과 똑같습니다 — 시간만 줄어든 거죠.
질문답
왜 품질이 안 떨어지나최종 출력은 항상 큰 모델이 승인한 토큰뿐. 작은 모델이 틀리면 큰 모델이 자기 답으로 갈아 끼운다 → 정확도는 큰 모델과 동일

⚠️ 8.1.4 — 한계

기법한계
증류일반성의 상실 — 학생 모델은 학습한 작업에서만 뛰어난 경우가 많고 교사의 폭넓은 능력은 희생한다. 도메인 특화 앱이라면 감수할 만하지만, 일반적인 환경에서는 특히 어렵거나 이례적인 예제에서 교사보다 확실히 못한 성능을 보이는 게 보통이다
편향과 오류를 그대로 물려받는다 — 교사 모델에 있던 것을
양자화성능 ↔ 자원 효율의 트레이드오프 — 비트 정밀도가 낮을수록(4비트, 2비트) 메모리 · 계산을 더 아끼지만 정확도 저하가 더 크게 나타나는 것이 보통
모든 아키텍처가 똑같이 반응하지 않는다 — 트랜스포머는 특히 어텐션 메커니즘과 일부 피드포워드 네트워크 층의 양자화에 민감할 수 있다
하드웨어 지원이 결정적 — 어떤 형식은 최적화된 커널이 없어 메모리를 덜 쓰고도 추론이 오히려 느려질 수 있다. 어떤 GPU는 int8 전용 텐서 코어를, 다른 GPU는 int4를 최적 지원한다
📌 원문 각주의 오기 — 원문은 "정밀도가 높은 형식(1비트 정수 같은)에 비해"라고 적었지만, 1비트는 4비트 · 2비트보다 정밀도가 낮습니다. 문맥상 8비트 · 16비트 같은 더 높은 정밀도 형식을 뜻하는 것으로 읽어야 합니다.
하드웨어 지원 문제는 실무에서 가장 자주 발목을 잡는 항목입니다.
