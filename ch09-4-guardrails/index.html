지켜야 할 다섯 영역
구체적인 윤리적·법적·기능적 범위 안에서 동작하도록 보장해야 하는 일이 잦습니다.

🛡️ 무엇으로부터 지켜야 하나

영역내용
보안
security		프롬프트 인젝션과 탈옥을 막아야 한다. 인젝션은 LLM이 시스템 프롬프트와 사용자 입력을 모두 텍스트로 처리한다는 점을 파고든다 — 그 때문에 모델이 정당한 지시와 악의적 명령을 구분하기 어렵다.

📑 패턴 24(SLM)가 여기서 실전에 쓰입니다 — 가드레일 판정은 단순한 이진 분류라 프런티어 모델이 필요 없습니다. 9.4.3에서 저자가 "SLM을 써서 지연을 관리 가능한 범위로 유지하라"고 권하는 근거이기도 합니다.
🔍 모델만 쓰는 것은 아니다 — LLM Guard는 정규표현식에 걸리는 문자열을 거부하는 기능도 지원합니다.
scanner = Regex(
    patterns=[r"Bearer [A-Za-z0-9-._~+/]+"],  # 정규식 패턴 목록
    is_blocked=True,   # True 이면 패턴을 '나쁜 것'으로 취급
    match_type=MatchType.SEARCH,   # SEARCH 또는 FULL_MATCH
    redact=True,       # 마스킹 활성화 여부
)
sanitized_prompt, is_valid, risk_score = scanner.scan(prompt)
🔑 저 정규식이 잡는 것은 Bearer 토큰입니다 — 사용자가 실수로 API 키를 프롬프트에 붙여 넣는 사고를 막습니다. 가장 값싸고 확실한 가드레일은 여전히 정규식입니다.
모든 검사에 모델이 필요한 것은 아니라는 점이 실무적입니다.

🛠️ 커스텀 가드레일과 묶음 적용

직접 코드로 로직을 구현하거나, 파운데이션 모델에 프롬프트를 넣거나, SLM을 사후 학습시켜 만들 수 있다. 다음은 패턴 17 LLM-as-Judge로 특정 주제의 프롬프트를 거부하는 예다.

banned_topics = ["religion", "politics", "sexual innuendo"]
system_prompt=f"""
I will give you a piece of text. Check whether the text touches
on any of these topics.

        {banned_topics}

Return True or False, with no preamble or special markers.
Text:
"""
llm = ...
response = llm.complete(prompt).text.strip()
is_valid = (response == "False")
📑 패턴 17이 재활용됩니다 — 6장에서 품질 평가 도구로 소개된 것이 여기서는 안전 검사 도구가 됩니다. 채점표를 든 심사위원은 "잘 썼는가"뿐 아니라 "써도 되는가"도 판정할 수 있습니다.
묶음이 준비되면 하나씩 차례로 적용
def apply_guardrails(guardrails, prompt):
    sanitized_prompt = prompt   # 초기값
    for scanner in guardrails:
       sanitized_prompt, is_valid, _ = scanner(sanitized_prompt)
       if not is_valid:
          raise Exception("...")
    return sanitized_prompt
✅ 출력이나 검색 결과, 도구 파라미터에 적용하는 것도 비슷하게 동작합니다. 시그니처를 통일해 뒀기에 for 루프 하나로 끝납니다.
검사 코드를 흩뿌리지 않고 한 겹으로 모으는 것이 이 패턴의 실체입니다.

제인 오스틴 RAG
제인 오스틴의 글을 근거로 질문에 답하도록 설계된 RAG 시스템입니다.

(원망을 사지 않으면서 충고할 수 있을까?)

응답
Yes, it is possible to give advice without being resented for it.

"a wonderful instance of advice being given on such a point,

🔧 두 가드레일 구현

가드레일 1 — 고유명사를 일반 식별자로
def guardrail_replace_names(to_scan: str):
    system_prompt="""
I will give you a piece of text. In that piece of text, replace
any personal names with a generic identifier.

Example:
  Input:  I met Sally in the store.
  Output: I met a woman in the store.

Return only the modified text, with no preamble or special markers.
    """
    sanitized_output = llm.complete(system_prompt+"\n"+to_scan).text.strip()
    no_change = (sanitized_output == to_scan)

    return {
        "guardrail_type": "PII Removal",
        "activated": not no_change,
        "should_stop": False,          # 수정만, 차단 안 함
        "sanitized_output": sanitized_output,
    }
가드레일 2 — 금지 주제 거부
def guardrail_banned_topics(to_scan: str):
    banned_topics = ["religion", "politics", "sexual innuendo"]
    ...
    response = llm.complete(system_prompt+"\n"+to_scan).text.strip()
    is_banned = (response == "True")

    return {
        "guardrail_type": "Banned Topic",
        "activated": is_banned,
        "should_stop": is_banned,       # 차단
        "sanitized_output": to_scan,
    }
📑 가드레일을 여러 개 적용하기 쉽도록, 모든 가드레일 함수의 시그니처를 똑같이 맞춰야 합니다. should_stop의 차이가 "수정"과 "거부"를 가릅니다 — PII는 고쳐서 통과, 금지 주제는 멈춤.
같은 반환 구조를 강제하는 것이 이 계층의 설계 원칙입니다.

🎒 질의 엔진 감싸기

class GuardedQueryEngine(RetrieverQueryEngine):
    def __init__(self, query_engine: RetrieverQueryEngine):
        self._query_engine = query_engine

    def query(self, query):
        # 입력에 가드레일 적용
        gd = apply_guardrails(query,
                 [guardrail_replace_names, guardrail_banned_topics])
        if not gd["should_stop"]:
            print(f"Modified Query: {gd['sanitized']}")
            query_response = self._query_engine.query(gd["sanitized"])
            # 출력에는 다른 묶음을 적용
            gd = apply_guardrails(str(query_response),
                                  [guardrail_banned_topics])
            if not gd["should_stop"]:
                return Response(gd["sanitized"],
                               source_nodes=query_response.source_nodes)
        return Response(str(gd))
💡 입력과 출력의 묶음이 다릅니다 — 입력에는 PII 제거 + 금지 주제 둘 다, 출력에는 금지 주제만. 출력에 PII 제거를 안 거는 이유는 이미 입력에서 가려졌기 때문입니다.

⚠️ 9.4.3 — 가장 복잡한 방식

🚨 가드레일은 애플리케이션 아키텍처에 상당한 엔지니어링 복잡도와 지연을 끌어들인다.

GenAI 애플리케이션을 구현하는 가장 복잡한 방식이 바로 맞춤 사후 학습된 가드레일과 함께 배포하는 것이므로, 이 복잡도가 정당한지 반드시 확인하라.

우려하는 핵심 위험을 더 저렴하게 막을 방법이 있을지도 모른다.
💰 지연을 줄이는 두 가지

① 예제의 가드레일은 프런티어 모델 API를 호출해 구현했지만 꼭 그럴 필요는 없다 — SLM(패턴 24)을 써서 지연을 관리 가능한 범위로 유지할 수 있다

② 가드레일과 LLM 코드를 순차로 돌릴 필요도 없다
try:
  input_guardrail_results, turn_result = await asyncio.gather(
      apply_guardrails( ... ),
      llm.complete( ... ),
  )
except InputGuardrailTriggered:
  ...
⚠️ 병렬화의 한계를 저자가 솔직히 밝힙니다 — 입력 가드레일이 허용되지 않는 사용을 탐지하면 예외를 던져야 하고, 그러면 두 번째 호출의 실행이 멈춥니다. 다만 이렇게 하면 LLM이 그 호출을 실행하는 것 자체는 막지 못합니다 — 대신 악의적 입력의 결과를 애플리케이션이 사용하지 못하게 하는 데 초점을 맞추게 됩니다.
💡 비용은 이미 나갔고 유출만 막는 셈입니다. 지연이 중요하면 병렬로, 비용이 중요하면 순차로.
가드레일 다섯 개를 순차로 돌리면 응답이 다섯 배 느려질 수 있습니다.
