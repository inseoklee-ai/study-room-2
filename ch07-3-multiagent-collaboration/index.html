✨ 창발적 능력(emergent capabilities) — 최근 연구는 멀티에이전트 시스템이 명시적으로 학습시키지 않은 행동을 보일 수 있다고 시사한다. 상호작용과 협업을 통해 개별 구성 요소의 합을 넘어서는 능력이 나타난다.
서로 다른 관점과 능력을 가진 에이전트 간 상호작용이 단일 모델에서 나오기 힘든 접근으로 이어집니다.

🏢 계층 구조 — 가장 단순한 형태는 프롬프트 체이닝

  • 임원-작업자(executive-worker) — 고수준 임원 에이전트가 과제를 분해해 전문 작업자에 위임하고, 그 출력들을 통합해 일관된 응답을 만든다
  • 다층 계층 — 임원-작업자 계층이 여러 겹, 중간 관리자가 전문 에이전트 그룹을 조율
  • 보통 의사결정을 중앙집중시키며 상위가 하위에 대한 권한을 갖는다

🤝 P2P 네트워크 — 합의와 투표

권한과 책임을 에이전트들에 더 고르게 분산시킨다. 에이전트들은 동등한 자격으로 일하며, 경직된 계층적 통제 없이 정보를 공유하고 활동을 조율한다. 과제는 하향식 배정이 아니라 집단적 노력으로 처리된다.

💰 시장 기반 — 경매와 효용 극대화

경매와 효용 극대화 같은 경제학적 아이디어로 활동을 조율한다. 에이전트가 자기 능력과 가용성에 따라 입찰하는 과정을 통해 과제나 자원을 배분한다.

밀봉 입찰 경매 — 중고차
def run_auction(agents, car_description):
    bids = {}
    for agent in agents:
        prompt = f"""Here is the car for auction:\n {car_description}\n\n
What is your maximum bid? Please respond with only the number."""
        bid_response = agent.run(prompt)
        bids[agent.name] = int(bid_response.output)

    highest_bid = 0; winner = None
    for agent_name, bid_amount in bids.items():
        if bid_amount > highest_bid:
            highest_bid = bid_amount; winner = agent_name
    return winner, highest_bid
💡 중고차 이야기가 아닙니다 — 각 에이전트가 현재 자원으로 그 과제를 얼마나 잘 해낼 수 있는지 독립적으로 판단할 수 있는 모든 과제 배정에 경매를 쓸 수 있습니다. 예: 서로 다른 알고리즘으로 최적화 문제를 푸는 에이전트들이 예상 개선폭이나 예상 최적화 시간에 근거해 입찰.
입찰가는 곧 "내가 이 일을 얼마나 잘할 수 있는가"의 자기 신고입니다.

다단계 문제 해결의존 관계가 있는 순차 단계 — 계획 · 실행 · 모니터링 · 적응을 나눠 맡거나, 해법을 점진적으로 다듬거나, 단계마다 검증 에이전트가 정확성 · 일관성 · 안전성을 검사

전문 도메인 통합도메인 특화 툴 · DB · API의 인터페이스 역할, 서로 다른 모달리티(텍스트 · 이미지 · 오디오 · 비디오)나 채널(웹 · 음성 · 텍스트) 통합
자기 개선 시스템평가자 에이전트가 다른 에이전트들의 성능을 평가하고 개선점을 짚어 낸다
💡 저자가 굳이 "단연 가장 흔하고, 유용하고, 덜 복잡한"이라고 못 박은 것은 병렬 실행 하나뿐입니다. 나머지는 그만큼 조심해서 쓰라는 뜻이죠.
다음 예제는 이 특성을 여럿 포함합니다.

7.3.3 예제

AG2로 중3 워크북 만들기
마이크로소프트에서 출발한 오픈소스 멀티에이전트 협업 프레임워크 AG2를 씁니다.

📚 여덟 단계 워크플로

중3 수준 워크북 제작을 맡았고, 그 콘텐츠를 만드는 데 에이전틱 접근을 쓴다.

1사람 사용자가 Task Assigner(과제 배정자)에 주제를 보내며 시작
2Task Assigner가 콘텐츠 작성 팀 중 하나에게 배정 — "플라시 전투는 왜 결정적이었나?"라면 역사 텍스트로 학습된 에이전트에게
3역사 작성 에이전트가 팩트체커와 교과서(RAG) 같은 툴을 써서 초안 생성
4초안이 여러 역할의 에이전트로 이루어진 검토 패널에 보내진다
5검토 패널이 서로 다른 관점을 제시하며 토론
6패널 서기(secretary)가 피드백을 구체적인 지시 목록으로 요약
7그 피드백이 역사 작성 에이전트에게 전달된다
8작성 에이전트가 반영해 다시 쓰고 최종 콘텐츠로 제출
📑 여러 패턴이 한 워크플로에 — 라우터(계층형) + RAG(패턴 6) + 검토 패널(P2P) + Reflection(패턴 18)의 성격이 모두 들어 있습니다.
그림 7-6이 이 상호작용을 그린 것입니다.

① 1단계 — 워크플로 설정 · 라우터

워크플로의 초기 부분은 계층 구조다 — 모든 요청이 Task Assigner로 흘러가고, Task Assigner가 작성자 중 하나를 고른다. 작업자 무리 앞에 분류기를 세운 이 패턴을 라우터(router)라고 부른다.

사람human
→
분류기task_assigner
→
작성자 Ahistory_writer
작성자 Bmath_writer
llm_config = LLMConfig(
    api_type="google", model="gemini-2.0-flash",
    api_key=os.environ.get("GEMINI_API_KEY"),
    temperature=0.2,
)
history_writer_prompt="You are a historian ..."
math_writer_prompt="You are a math teacher ..."
with llm_config:
    history_writer = ConversableAgent(name="history_writer",
                            system_message=history_writer_prompt)
    math_writer = ConversableAgent(name="math_writer",
                            system_message=math_writer_prompt)
    human = ConversableAgent(name="human",
                            human_input_mode="ALWAYS")
에이전트는 넷입니다 — 사람 프록시, Task Assigner, 작성자 둘.

🎯 Task Assigner에는 창의성이 너무 많으면 곤란하다

그러므로 temperature를 0으로 두고 출력을 제약한다 — 2장 패턴 2 Grammar 사용.

task_assigner_prompt="""You have two writers, one who is ....
assign it to the person who is likely to be better informed and
able to create content to answer it."""

class TaskAssignmentResponse(BaseModel):
    writer: Literal['HISTORIAN', 'MATH WRITER']

llm_task_config = LLMConfig(
    ...
    temperature=0.0,
    response_format=TaskAssignmentResponse
)
with llm_task_config:
    task_assigner = ConversableAgent(name="task_assigner",
                                     system_message=task_assigner_prompt)
📑 2장 패턴 2 Grammar가 여기서 살아납니다 — 라우터의 출력은 다음 코드가 분기에 쓸 값이므로 자유 텍스트여서는 안 됩니다. Literal로 두 값만 허용하면 파싱이 절대 실패하지 않습니다.
💡 온도 0 + 문법 제약은 "판단하는 에이전트"의 표준 설정입니다. 창작하는 에이전트(작성자 둘)는 0.2를 쓴 것과 대비해 보세요.
같은 시스템 안에서도 역할에 따라 온도를 달리 준다는 점이 실무 포인트입니다.

②③ 2~3단계 — 배정하고 초안 만들기

task_response = human.run(recipient=task_assigner,
                            message=question, max_turns=1)
task_response.process()

writer = json.loads(task_response.messages[-1]['content'])['writer']
if writer == 'HISTORIAN': writer = history_writer
else:                     writer = math_writer

content_response = task_assigner.run(recipient=writer,

initial_draft = content_response.messages[-1]['content']
💡 max_turns를 늘리면 Task Assigner가 사람에게 후속 질문이나 명확화 질문을 할 수 있습니다.
질문 — 플라시 전투는 왜 그렇게 결정적이었나?

→ {"writer": "HISTORIAN"}

초안(발췌) — "…이 전투의 의의는 영국이 인도 아대륙 전체에 대한 지배를 점진적으로 확대해 가는 길을 열었다는 데 있다. 벵골에서 얻은 부로 영국 동인도회사는 군사 · 행정 활동에 자금을 댈 수 있었고…"
질문 — x²+50=150. Solve for x.

→ {"writer": "MATH WRITER"}

초안(발췌) — "자, 여러분, 이 방정식을 같이 풀어 봅시다. 우리 목표는 'x'를 고립시키는 것…등식 양변에 제곱근을 취합니다: √(x²) = ±√100. '±' 기호에 주목하세요! 이건 아주 중요합니다…"
같은 라우터가 전혀 다른 톤의 두 작성자에게 정확히 나눠 보냅니다.

④ 4단계 — 교육과정 검토 패널 구성

reviewers = []
with llm_config:
    reviewers.append(ConversableAgent(name="district_admin",
      system_message="""You are a school district representative who
wants to ensure that materials are concise and easy to understand.
You want to keep the cost of printing and remedial education down."""))
    reviewers.append(ConversableAgent(name="school_admin", ...))
    reviewers.append(ConversableAgent(name="secretary", ...))
    reviewers.append(ConversableAgent(name="conservative_parent", ...))
    reviewers.append(ConversableAgent(name="liberal_parent", ...))

앞에서는 상호작용과 인계(handoff)를 직접 코딩했다. AG2에는 사전 제작 오케스트레이션 패턴이 여럿 들어 있는데, 모든 구성원에게 발언 기회를 주는 라운드 로빈이 검토 패널에 알맞다.

pattern = RoundRobinPattern(
    initial_agent=reviewers[0], agents=reviewers, user_agent=None,
    group_manager_args={"llm_config": llm_config})

reviews, context, last_agent = initiate_group_chat(
    pattern=pattern,
    max_rounds=len(reviewers)+1,   # 모두가 한 번씩 발언
    messages=f"""You are part of a review panel ...
    {question} ... {answer}""")
검토 패널은 P2P 성격입니다 — 서로 다른 관점이 동등하게 발언합니다.

⑤ 5단계 — 검토 패널 토론

플라시 전투에 관한 글을 놓고 각 검토자가 자기 관점에서 피드백을 주고 다른 이의 피드백에 응답한다.

교육구 행정관
"부와 권력을 축재한다(Amass wealth and power)": 좋습니다만, "축재하다(amass)"보다 더 친숙한 단어를 쓸 수 있지 않을까요? "얻다(gain)"나 "모으다(collect)"는 어떨까요?
보수 성향 학부모
"영국 지배의 확립(Establishment of British dominance)": 이것을 본질적으로 부정적인 것으로 규정하지 않도록 "영국의 관여(British involvement)"로 완화했습니다. 학생들이 일방적 서사가 아니라 복잡성을 이해하기를 바랍니다.
진보 성향 학부모
… 다시 말하지만 "무역 활동(trade operations)"이라는 말은 무해하게 들립니다. 동인도회사는 단지 무역을 관리한 것이 아니라 정치적 · 군사적 통제를 적극적으로 확대하고 있었습니다.
💡 세 검토자가 정확히 반대 방향으로 밀고 있는 데 주목하세요. 이것이 P2P의 값어치입니다 — 단일 에이전트라면 어느 한쪽으로 기울어 끝났을 텐데, 여기서는 긴장이 그대로 기록됩니다.
어느 한쪽 손을 들어 주지 않는 것이 이 패널의 목적입니다.

⑥⑦⑧ 6~8단계 — 요약 · 전달 · 재작성

📝 라운드 로빈은 에이전트를 추가한 순서대로 호출하므로 마지막에 말하는 것은 서기다. 서기의 시스템 프롬프트는 전체 대화를 요약해 단계 목록으로 종합하라고 지시한다.
서기의 지시
"자원을 추출한다(Extract resources)"를 "수익을 창출한다(generate revenue)"로 바꿀 것. 회사의 재정적 목표를 여전히 정확히 반영하면서도 덜 비난조인 표현이다.
rewrite_response = last_agent.run(recipient=history_writer,
      max_turns=2, message=f"""
Please incorporate the feedback from a review panel to update
content you wrote for a 9th-grade workbook.
You were asked: {question}
You wrote: {answer}
The reviewer panel has provided the following feedback:
{reviews.chat_history[-1]['content']}
Incorporate the feedback to rewrite the content.""")
max_turns=2 — 명확화 질문을 한 차례 주고받을 수 있다는 뜻입니다.
서기의 요약이 그대로 작성 에이전트의 입력이 됩니다.

🎉 최종 콘텐츠 — 더 명료하고 균형 잡힌 답

최종 콘텐츠 (발췌)

1757년의 플라시 전투는 인도에서 영국의 영향력이 형성되는 역사에서 전환점이 됐다. …회사의 승리는 태수 궁정 내부의 분열과 불화에 힘입은 것이었고… 이 승리로 영국 동인도회사는 세력을 공고히 하고 인도 영토에 대한 지배를 확대할 수 있었으며, 무역 활동을 더 효과적으로 관리하고 수익을 창출할 수 있게 됐다. …영국의 존재가 철도와 관개 시설 개발 같은 기반 시설의 진전을 가져오기도 했지만, 여기에 인도의 자원과 노동이 상당히 동원되었고 그것이 많은 인도인에게 장기적인 경제적 · 사회적 어려움을 남겼다는 점도 함께 인정해야 한다.
서기의 추가 지시 — 마지막 두 문장을 합칠 것: 그러면 장기적 영향을 강조하는 더 강한 마무리 문장이 된다.
최종 마무리
플라시 전투로 인해 영국은 결정적 발판과 인도에서 영향력을 확대하는 데 필요한 자원을 얻었다. 이 전투는 오래도록 지속되는 결과를 남겨, 여러 세대에 걸쳐 그 지역의 경제와 사회를 빚어냈다.
💡 초안의 "지배를 점진적으로 확대해 가는 길"이 최종본에서는 공과를 나란히 적는 문장으로 바뀌었습니다. 이것을 해낸 것은 더 큰 모델이 아니라 서로 다른 입장의 검토자들입니다.
패널의 긴장이 실제로 결과물의 균형으로 옮겨졌습니다.

7.3.4 고려사항

중대한 과제가 남아 있다
여기가 이 절에서 가장 중요한 부분입니다.

⚙️ 오버헤드와 일관성

집필 시점 기준 멀티에이전트 시스템의 구현과 평가에는 여전히 중대한 과제가 남아 있다 — 계산 오버헤드, 일관성 유지, 오류 누적, 예측 불가능한 창발 행동.

  • 가능하면 동료 관계로 병렬 실행 — 체감 시간(wall-clock time)이 줄어든다. 전체 계산 오버헤드는 그대로지만. 비동기 수행으로 지연 시간을 더 줄일 수 있다
  • 통신 오버헤드는 상당하다 — 조율의 계산 비용은 에이전트 수에 대해 비선형으로 증가하므로 확장성을 제한한다
  • 일관성 유지가 어렵다 — 에이전트마다 속도나 지연이 다를 때 특히. 전문 에이전트로 나누는 접근은 일관성의 복잡도를 통신의 복잡도와 맞바꾸는 셈이다
  • 예상하지 못한 행동 — 에이전트 간 양성 피드백 루프가 오류와 편향을 증폭시켜 시스템 불안정을 초래할 수 있다. 에이전트가 시스템 전체 목표를 희생하며 자기 목표를 최적화하는 전략을 발전시킬 수도 있다
🏢 Anthropic의 권고 — 이런 시스템을 구현할 때 복잡한 프레임워크보다 단순하고 조합 가능한 패턴을 쓰라.
"오버헤드는 그대로다"라는 단서가 중요합니다. 병렬화는 비용이 아니라 시간을 줄입니다.

📡 Agent2Agent 프로토콜이 통신을 단순화한다

A2A는 서로 다른 프레임워크로 작성돼 서로 다른 머신에서 도는 에이전트들이 매끄럽게 통신하게 해 준다.

파이썬 (Pydantic AI) — A2A로 노출
from pydantic_ai import Agent
agent = Agent('openai:gpt-4.1', ...)
app = agent.to_a2a()
uvicorn agent_to_a2a:app --host 0.0.0.0 --port 8093
TypeScript (Mastra) — 그 URL만 알면 호출
import { A2A } from "@mastra/client-js";
const a2a = new A2A({ serverUrl: "https://...server.com:8093" });

const task = await a2a.sendTask({
  id: randomUUID(),
  message: { role: 'user', parts: [...] }
});
const stream = a2a.streamTaskUpdates(task.id, (update) => {
  console.log("Task update:", update);
});
📑 패턴 21의 MCP와 짝 — MCP가 에이전트↔툴의 표준이라면, A2A는 에이전트↔에이전트의 표준입니다.
프런트엔드 개발자가 파이썬 에이전트를 웹 URL 하나로 부를 수 있게 됩니다.

📉 오류는 사슬을 따라 누적된다

🏃 비유 — 사람 8명이 이어달리기로 문서를 만든다고 합시다. 한 사람이 95% 정확도로 일한다면, 8명을 거친 결과는 0.958 ≈ 66%입니다. 각자는 훌륭한데 전체는 3분의 1이 망가집니다.
