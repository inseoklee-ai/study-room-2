8.5.1 문제

LLM은 상태가 없다
LLM은 각 프롬프트를 고립된 채로 처리합니다.

🧠 기억이 필요한 자리들

LLM은 각 프롬프트를 고립된 채로 처리하며, 상호작용을 넘나들며 이전 맥락 정보를 유지하는 능력이 없다. 그러나 온갖 종류의 애플리케이션에서 이전 호출의 정보를 기억하는 것은 중요하다.

애플리케이션무엇을 기억해야 하나
챗봇 · 가상 비서사용자의 선호를 기억해야 하고, 세션을 넘어 대화 이력과 맥락 상태를 유지해야 할 수도 있다 — 사용자가 매번 같은 말을 반복해야 한다면 짜증스러우니까
코딩 어시스턴트여러 파일과 세션에 걸쳐 프로젝트 구조 · 의존성 · 코딩 패턴을 인지하고 있어야 한다
워크플로 에이전트
7장 패턴 23		워크플로 단계 사이에 맥락이 유지되어야 하는 경우가 많다
큰 문서 처리컨텍스트 윈도보다 큰 문서를 다룰 때, 앞서 읽은 핵심 정보를 기억해야 핵심 절들을 식별하고 종합할 수 있다
모든 AI 앱사용자 행동 · 선호 · 과거 상호작용에 따라 응답을 조정해야 할 수 있다
LLM 호출은 하나하나가
상태 없이(stateless)
이전 호출과 독립적이다
이 다섯 가지가 모두 같은 한계에 부딪힙니다.

🎭 지금은 흉내로 해결한다

챗봇 같은 대화형 애플리케이션은 이전 대화 턴을 프롬프트 앞에 덧붙이는 방식으로 상태 유지를 흉내 낸다.

PydanticAI — 이전 메시지를 명시적으로 전달
result1 = agent.run_sync(...)
result2 = agent.run_sync(..., message_history=result1.new_messages())

워크플로 에이전트는 현재 상태를 입력으로 받고 확장된 상태를 출력으로 돌려주는 방식으로 맥락을 유지한다.

LangGraph — 각 노드의 시그니처
def some_node(current_state: CurrentState) -> NextState:
    next_state = current_state.copy()
    ...
    next_state['confirmed_amount'] = 3450
    return next_state
⚠️ 두 접근 모두의 문제 — 본질적으로 대화 이력 전체를 프롬프트에 넣는다. 오늘날 컨텍스트 윈도가 크긴 하지만(집필 시점 Gemini는 100만 토큰), 사용자의 상호작용 이력 전체를 매 프롬프트마다 앞에 붙이는 것은 비용 면에서 불가능하다.
트랜스포머는 시퀀스 길이에 대해
2차(quadratic)로 확장된다
대화가 2배 길어지면 비용은 4배
그래서 "다 넣기"는 어느 순간 반드시 무너진다
❓ 컨텍스트 윈도를 넘치게 하거나 감당 못 할 비용을 치르지 않으면서 과거 상호작용의 기억을 관리하려면 어떻게 해야 할까?
컨텍스트 윈도가 커진다고 해결되는 문제가 아니라는 점이 핵심입니다.

8.5.2 해법

네 가지 기억
사람의 기억 분류를 그대로 가져온 것입니다.

🌟 네 가지 기억을 사람의 기억에 빗대면

☕ 비유 — 단골 카페 사장님을 떠올려 보세요.
① 지금 주문 중인 "아까 말한 그거"를 기억하고 — 작업 기억
② "지난주에 오셨을 때 산미 있는 게 별로라 하셨죠"를 떠올리고 — 일화 기억
③ "이 손님은 항상 얼음 적게"라는 카드를 갖고 있고 — 절차 기억
④ "이 손님이 아이슬란드 여행 간다고 했지"라는 사실 자체를 알고 있습니다 — 의미 기억
기억무엇을 저장검색 기준
작업 기억
Working		지금 세션의 메시지 목록최근 N토큰
일화 기억
Episodic		과거 세션의 메시지 원본주로 최신성
절차 기억
Procedural		지시문과 사용자 프로필이 사용자인가
의미 기억
Semantic		추출한 사실주로 내용 유사도
장기 기억은
현재 세션의 즉각적인 대화 맥락을 넘어서는
정보를 저장하고 검색하는 능력
헷갈리는 것은 일화와 의미 두 쌍입니다. 저장 대상과 검색 기준이 다릅니다.

📝 작업 기억 — "그거"가 무엇인가

💬 사용자가 "그거 라지로 바꿔 줘"라고 말한다면 "그거"는 무엇을 가리키는가? 알아내려면 현재 사용자 세션의 이전 메시지들에 접근해야 한다.

구현은 단순하다 — 메시지를 받거나 생성할 때마다 리스트에 저장하면 된다. 다만 당연한 단서가 붙는다.

1무한할 수 없다 — 리스트를 쳐내야 감당 못 할 정도로 커지지 않는다
2최근 N개 메시지만 남기는 단순한 방식은 실패한다 — 메시지 하나가 너무 크면
3단순하고 믿을 만한 구현은 일정한 토큰 한도 안으로 잘라 내는 것
⚠️ 유효한 상태로 남도록 쳐내야 한다
• 메시지가 잘려 반쪽만 남아서는 안 된다
• 그 AI 메시지를 만들어 낸 사용자 프롬프트와 떨어진 AI 메시지가 있어서는 안 된다
• 역할과 어조 같은 일관성을 위해 모든 턴에 걸쳐 유지되는 시스템 프롬프트를 쓴다
LangChain — 메시지 이력을 1,000 토큰으로 제한
from langchain_core.messages import trim_messages
trim_messages(
    messages,
    strategy="last",
    token_counter=ChatOpenAI(MODEL_ID),
    max_tokens=1000,
    start_on="human",
    end_on=("human", "tool"),
    include_system=True,
)
start_on · end_on을 지정하는 이유는 대부분의 채팅 모델이 대화 이력이 사람 메시지로 시작하기를 기대하기 때문입니다. include_system=True는 호출 사이에 시스템 지시문을 유지하도록 지정합니다.

📚 일화 기억 — 이전 세션과의 연속성

🏝️ 상황 — 사용자가 "아이슬란드에서 뭘 할 수 있을까?"라고 묻는다. 어쩌면 이 사용자는 이틀 전에 같은 질문을 했고, AI가 온천을 추천했는데 사용자가 그 아이디어를 물렸을 수도 있다. 그렇다면 그 추천을 되풀이하지 않는 게 좋을 것이다.
작업 기억은 현재 세션의 메시지
그렇다면 이전 대화에서
관련 메시지를 어떻게 가져올까?
1모든 메시지를 데이터베이스 같은 영속 저장소에 저장해 둔다
2현재 질의나 대화와 관련 있는 메시지를 그 데이터베이스에서 검색한다
3찾아낸 관련 메시지들이 일화 기억을 채우는 데 쓰인다
🔍 내용뿐 아니라 메타데이터도 함께 검색해야 한다. 예컨대 이 사용 사례에서는 메시지가 —
• 이 사용자의 것이고
• 최근(지난 한 주쯤)이며
• 여행에 관한 것이기를 원할 수 있다
📑 패턴 6 기본 RAG(3장)와 마찬가지로, 관련 메시지는 코사인 유사도 · 키워드 · 또는 둘의 혼합으로 검색할 수 있습니다. 일화 기억은 사실상 대화 이력에 대한 RAG입니다.
그림 8-18이 일화 기억의 구성을 그린 것입니다.

📋 절차 기억 — 지시문과 프로필

시스템 지시문과, 지시문을 만드는 데 쓰이는 사용자 프로필 같은 속성들을 저장하고 검색하는 능력.

⚙️ 사용자가 시스템 프롬프트를 직접 지정할 수 있게 해 주면, 애플리케이션에서 받는 모든 응답을 개인화할 수 있다. LLM 어시스턴트 Bench.io가 그런 화면을 제공한다.
다만 사용자가
시스템 프롬프트로 자기 얘기를 해 주기를
기다릴 필요는 없다
1각 사용자의 메시지를 관찰한다
2관련 사실을 프로필로 추출한다 — 예: 사용자가 견과류 알레르기가 있다고 언급하면
3그 사용자의 시스템 프롬프트를 구성하는 데 쓰이는 프로필 정보에 추가한다
💡 두 가지 배치 선택 — 프로필 정보를 시스템 프롬프트에 넣을 수도, 프롬프트의 컨텍스트에 넣을 수도 있다. 즉 사용자별 시스템 프롬프트를 구성해 프로필의 어떤 부분을 포함할지 제어할 수 있다.
📑 6장 패턴 20 프롬프트 최적화가 기계가 프롬프트를 쓰게 하는 것이었다면, 절차 기억은 사용자가 프롬프트를 쓰게 하는 쪽입니다. 둘 다 프롬프트를 코드 밖으로 빼내는 발상입니다.
그림 8-19와 8-20이 이 두 방식을 각각 보여 줍니다.

💡 의미 기억 — 사실 자체를 남긴다

이전 메시지에서 뽑아내는 핵심 사실이 사용자 프로필 정보에만 국한될 필요는 없다.

✈️ 사용자가 "아이슬란드에 도착하는 날 뭘 할 수 있을까?"라고 묻는다면, 그가 말해 준 가장 최근 여행 정보를 가져오는 것이 도움이 될 것이다.
주로 내용을 기준으로
정보를 저장하고 검색하는 능력
주로 최신성을 기준으로 하는 일화 기억과는 다르다
LangGraph — 기억 저장
store = PostgresStore(
    connection_string="postgresql://.../dbname",
)
trip_memories_ns = (user_id, "trip_memories")   # 네임스페이스
memory = {"trip": {"from": "SEA", "to": "KEF", "depart_time": ...}}
memory_id = hash(json.dumps(memory, sort_keys=True))
store.put(trip_memories_ns, memory_id, memory)
검색 — 가장 최근 여행
most_recent_trip = in_memory_store.search(trip_memories_ns)[-1]
💡 대신 특정 기간 내의 모든 최근 여행을 살펴보거나, 아이슬란드와 관련된 것들만 볼 수도 있습니다. 무엇이 관련 있는지의 논리는 만드는 사람의 몫입니다.
  • 네임스페이스(namespace) — 기억을 사용자 · 주제별로 나눠 담는 칸
  • 2차 확장(quadratic scaling) — 입력 길이가 n배면 비용이 n²배가 되는 것
저자가 마지막 문장을 명시적으로 남긴 점이 중요합니다 — 프레임워크가 대신 정해 주지 않습니다.

8.5.3 예제

Mem0로 여행 어시스턴트
좌석 선호, 선호 항공사나 호텔 체인, 이미 다녀온 목적지 같은 맥락을 기억합니다.

🛠️ Mem0 설정

📚 Mem0 — Chhikara 외가 2025년 논문 "Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory"에서 소개한 저지연 기억 관리 접근의 구현. 진행 중인 대화에서 관련 정보를 동적으로 추출 · 통합 · 검색해 그래프 기반 기억 표현으로 만든다. 앞의 네 가지 기억을 모두 표현할 수 있다.
config = {
    "vector_store": {
        "provider": "chroma",        # 의미 기반 검색용
        "config": {
            "collection_name": "mem0_basic_example",
            "path": "/tmp/chroma_db",   # 기억을 저장할 위치
        }
    },
    "llm": {
        "provider": "openai",
        "config": {"model": "gpt-4o-mini", "temperature": 0.1}
    },
    "embedder": {
        "provider": "openai",           # 텍스트를 벡터로 변환
        "config": {"model": "text-embedding-3-small"}
    }
    "history_db_path": os.path.join(temp_dir, "history.db")
}

memory = Memory.from_config(config)
📑 네 조각이 각각 다른 기억을 떠받칩니다 — 벡터 스토어는 의미 기억, LLM은 사실 추출, 임베더는 검색, history DB는 감사 추적. 다음 슬라이드들에서 하나씩 봅니다.
설정만 봐도 이 프레임워크가 무엇을 합치는지 보입니다.

✅ 쓰는 법은 두 줄

대화를 기억에 추가
conversation = [
    {"role": "user", "content": """I'm looking to travel from
Seattle to Reykjavik. What's the best way to do this?"""},
    {"role": "assistant", "content": """The best way to travel from
Seattle to Reykjavik is to fly. The flight is about 10 hours long."""}
]

memory.add(conversation, user_id="megan")
나중에 검색
query = "What are my options to travel to Reykjavik?"
relevant_memories = memory.search(query=query, user_id="megan", limit=3)

# 반환: ["Interested in travel from Seattle to Reykjavik"]

이제 검색으로 돌아온 기억들을 LLM 요청의 요청 컨텍스트에 한 번 주입하면 된다.

이게 전부다
Mem0 같은 프레임워크는 기억이 정확히 어떻게
검색되고 순위가 매겨지는지의 세부를 추상화해 준다
💡 저장한 것은 대화 두 턴인데 돌아온 것은 "Interested in travel from Seattle to Reykjavik"이라는 한 문장의 사실입니다. 메시지가 아니라 사실이 저장된 것 — 이것이 의미 기억입니다.
이제 그 뒤에서 무슨 일이 벌어지는지 봅니다.

🔍 기억 추가는 어떻게 동작하나

식별자효과
user_id="megan"장기 기억이 이 사용자와 연결되어 세션을 넘어 지속된다
metadata={...}다른 종류의 메타데이터도 지정 — {"food": "vegan"}
run_id="..."메시지를 단일 세션 동안만 유지 — 이것이 단기 기억을 구현하는 방법
client.add(messages, user_id="megan", metadata={"food": "vegan"})
client.add(messages, user_id="megan", run_id="iceland-trip-planning")
🤖 user_id가 사람 사용자만을 위한 것일 필요는 없다 — AI 어시스턴트에게도 사용자 ID를 부여해, 서로 다른 사용자에게 일관된 응답을 주고 세션을 넘어 세부를 기억하게 할 수 있다.

기억을 다루는 도구들은 데이터를 그래프나 관계형 데이터베이스로 조직하는 경우가 많다. 이 방식은 사용자 선호와 연결 관계 같은 절차 기억 요소를 관리하는 데 도움이 된다.

🔗 의미 기억과 절차 기억을 결합하거나, 그래프 데이터베이스와 벡터 데이터베이스를 결합하면 좋은 결과가 나온다. 이 조합이 적절한 맥락을 제공해 연관된 사용자 콘텐츠의 검색을 돕는다.

벡터 DB (Chroma)의미 기억 — 내용 유사도 검색

🍴 필터로 무엇을 가져올지 고른다

돌려받을 기억은 필터(filters)로 제어할 수 있다 — 기억에 거는 추가 조건이다.

✈️ 예 — 사용자의 항공편을 예약할 때마다 음식 선호와 관련된 기억을 추출하도록 필터를 걸 수 있다.
query = "Book a flight from SEA to KEF on June 6"

    "AND": [
        {
            "categories": {
                "contains": "food_preferences"
            }
        }
    ]
}
client.search(query, user_id="megan", filters=filters)

상당 부분을 추상화한
단순한 인터페이스로
네 가지 기억을 모두 지원한다
💡 이 필터가 하는 일을 곱씹어 보세요 — 질의는 "항공편 예약"인데 가져오는 것은 "음식 선호"입니다. 의미 유사도만으로는 절대 연결되지 않을 두 가지를, 사람이 아는 도메인 규칙으로 이어 붙인 것이죠.

⚠️ 8.5.4 — 고려사항

🏢 프로덕션이라면 마이크로서비스로
Mem0 같은 프레임워크는 벡터 DB · 관계형 DB · 여러 LLM 구성 등 여러 인프라 조각을 결합한다. 프로덕션 사용 사례라면 파이썬 모듈을 직접 쓰는 대신 마이크로서비스로 배포할 것을 강력히 권한다. Mem0 서버가 출발점이 될 수 있다.
⏱️ 백그라운드 스레드 — 사용자 경험이 느려지지 않도록, 메시지와 기억을 이력에 쓰는 작업은 백그라운드 스레드에서 수행할 수 있다.
기억언제 중요한가어떤 앱에
작업 기억현재 대화 맥락 유지챗봇
일화 기억특정 상호작용에 대한 메시지를 찾을 때다단계 워크플로가 포함된 앱과 작업
절차 기억사용자 패턴과 선호를 학습개인화
의미 기억이전 대화에서 추출한 사실과 지식 관리큰 문서 처리
💡 만드는 애플리케이션에 따라 네 가지 중 하나 이상을 관리해야 할 수 있습니다. 전부 다 쓰는 것이 기본값이 아닙니다.

⭐ 저자의 권고 — 일화보다 의미

일반적으로는
일화 기억보다 의미 기억을
쓰는 편이 좋다
일화 기억의 문제내용
검색 지연모든 메시지를 있는 그대로 저장하고 런타임에 관련 메시지를 찾아내는 데 의존한다. 저장은 저렴하지만 관련 메시지를 검색하는 데 상당한 지연이 붙을 수 있다
디버깅 난이도캐시 미스로 인한 기억 오류는 원인을 추적하기도 꽤 어렵다
✅ 그래서 — 메시지를 있는 그대로 저장하는 대신, 메시지에서 기억할 만한 정보를 추출해 그것만 저장하는 편이 나은 경우가 많다. 그러면 양이 적고 더 결정론적으로 검색할 수 있다.
📑 7장의 메아리 — 패턴 23에서 저자들은 "단일 에이전트로 되면 그냥 그렇게 하라"고 했습니다. 여기서도 같은 태도입니다 — 더 많이 저장하는 것이 더 좋은 것이 아니다. 검색이 결정론적일수록 디버깅이 쉽습니다.
