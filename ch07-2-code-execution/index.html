7.2.1 문제

툴 호출로는 부족할 때
LLM은 그래프를 그리거나 이미지에 텍스트로 주석을 다는 일에 그다지 능하지 않습니다.

❌ 그래프를 그릴 때 API를 부르지 않는다

하려는 일실제로 필요한 것
그래프 그리기Matplotlib 같은 프로그래밍 언어나 Mermaid 같은 DSL로 그래프 명세를 작성
이미지에 주석 달기ImageMagick 같은 프레임워크를 일련의 명령줄 지시로 호출해 명세를 공급
데이터베이스 조회SQL을 입력으로 받는 함수 — 대표적인 사례
호출할 함수가
짧은 파라미터 목록이 아니라
DSL로 된 긴 구문을 입력으로 받는 경우
Tool Calling으로는 충분하지 않다
🍳 비유 — ① 메뉴판에서 고르기("2번 세트, 매운맛, 곱빼기") — 고를 수 있는 게 정해져 있고 옵션은 몇 개뿐 ② 레시피를 적어 주방에 넘기기("이 재료를 이 순서로, 이 온도에서") — 표현할 수 있는 게 무한
①이 Tool Calling, ②가 Code Execution입니다.

원하는 일을 이미 해 주는 소프트웨어 시스템이 있는데 그것이 DSL로 구동된다면, Code Execution을 쓰는 편이 낫다.

💡 파운데이션 모델들은 Matplotlib 코드 · SQL 구문 · Mermaid 마크다운을 꽤 잘 생성합니다. 그러므로 그래프를 만들고, 데이터베이스를 조회하고, 차트를 그릴 수 있습니다.
💾 데이터베이스를 갱신해야 할 때 — LLM이 데이터 무결성을 유지해 주기를 기대하는 것보다, LLM이 SQL을 생성하고 그것을 하나의 트랜잭션으로 데이터베이스에 보내는 편이 쉽습니다.
Code Execution은
자연어 이해와 계산적 문제 해결 사이의 간극을 메운다
📑 ReAct 프레임워크의 일부로 구현할 수도 있습니다 — 교차되는 행동 중 일부가 툴 호출이 아니라 코드 실행이 되는 식으로.
자연어 지시에 응답해 문제를 풀고, 데이터를 분석하고, 시각화를 만드는 인터랙티브 계산 도구를 만들 수 있게 됩니다.

7.2.3 예제

농구 토너먼트 대진표
조지아가 64강에서 곤자가에 졌고, 그 곤자가는 32강에서 탈락했다는 걸 그림으로 보여 주려 합니다.

① LLM이 DOT 코드를 생성한다

Graphviz라는 그래프 그리기 프로그램의 DSL인 DOT은 그래프를 간결하게 표현할 수 있게 해 준다. 변환 예시를 LLM에게 보여 준다.

프롬프트 — 입력 예시
• Saturday, March 29, 2025 (Elite Eight)
• (1) Florida 84, (3) Texas Tech 79
• (1) Duke 85, (2) Alabama 65
프롬프트 — 출력 예시 (DOT)
"Florida" -> "Texas Tech" [label="84-79"]
"Duke" -> "Alabama" [label="85-65"]
subgraph cluster_elite_eight {
  label = "Elite Eight"
  {rank = same; "Texas Tech"; "Alabama"; ... }
}
💡 프롬프트에 "서브그래프 이름은 반드시 cluster_xxx 형태로" 같은 제약을 명시합니다 — DSL의 문법 규칙을 지키게 하는 것이죠.
📑 5장 패턴 13 Few-shot CoT가 여기서도 쓰입니다 — 변환 예시 하나로 형식을 시연합니다.
토너먼트 결과 자체는 웹 검색(패턴 21)이나 RAG(패턴 6)로 얻을 수 있습니다.

② 생성된 DSL을 실행한다

dot -Grankdir=LR -Tpng tournament.dot -o tournament.png
1LLM이
tournament.dot 생성
→
2파일로 저장
→
3dot 프로그램이
PNG 생성
LLM은 그림을 그리지 않는다
그림을 그릴 설계도를 쓴다
💡 이 분업이 핵심입니다 — LLM은 "무엇을 그릴지"를 아는 데 능하고, Graphviz는 "어떻게 배치할지"를 계산하는 데 능합니다. 각자 잘하는 걸 합니다.
📈 결과 이미지는 64강 → 32강으로 이어지는 토너먼트 진행을 한눈에 보여 줍니다. 라벨은 DOT 코드에 적힌 문자열 그대로입니다.
LLM에게 좌표를 계산시켰다면 훨씬 나쁜 결과가 나왔을 겁니다. 레이아웃은 Graphviz가 훨씬 잘하죠.

🔒 7.2.4 — 반드시 샌드박스에서

샌드박스(sandbox environment)는 LLM이 생성한 코드를 기반 시스템을 위험에 빠뜨리지 않고 실행할 수 있는 격리되고 안전한 공간이다.

항목내용
제약CPU · 메모리 · 네트워크 접근 · 실행 시간에 제약. 무한 루프와 자원 고갈을 막기 위해 모니터링
구현Docker 같은 컨테이너, 가상 머신, 또는 강한 보안 경계를 갖춘 특수 런타임
1샌드박스 안이라 하더라도 곧바로 실행하기보다 먼저 검증하라 — 단순한 구문 확인부터 정적 코드 분석, 형식적 정확성 검사까지
2컴파일 오류나 검증·런타임 실패는 LLM에 돌려보내 수정 후 재시도하게 한다 (6장 패턴 18 Reflection)
3샌드박스 컨테이너를 최신 상태로 유지하라 — 샌드박스 OS나 격리 메커니즘의 취약점이 호스트 시스템 접근을 허용할 수 있다
⚠️ 샌드박스와 검증을 갖추더라도 보안은 여전히 과제입니다 — 악의적 사용자는 자원 제약을 초과시키거나, 데이터를 빼내거나, 유해한 코드를 생성하도록 프롬프트를 조작하려 합니다.
패턴 21의 프롬프트 인젝션 이야기가 여기서도 그대로 적용됩니다.

🚩 Tool Calling과 Code Execution의 갈림길

상황선택
항공권 예약 — 편명 · 날짜 · 좌석등급 세 개면 끝Tool Calling
DB 조회 — SQL 한 덩어리를 넘겨야 함Code Execution
차트 그리기 — Matplotlib / Mermaid 명세를 써야 함Code Execution
주가 조회 — 종목코드 하나Tool Calling
파라미터 몇 개로 말이 되면 툴
문법이 있는 긴 문장을 써야 하면 코드
⚠️ 대신 위험이 커진다 — 코드는 무엇이든 할 수 있다는 게 장점이자 문제입니다. 파일을 못 건드리게, 네트워크를 못 쓰게, 오래 못 돌게 미리 막아 둔 방에서 돌려야 합니다.
  • DSL(domain-specific language) — 한 가지 일만 위한 작은 언어. SQL, Graphviz의 DOT, Mermaid
  • 샌드박스(sandbox) — 코드가 바깥에 손대지 못하게 가둔 실행 환경
  • Reflection(패턴 18) — 실행이 실패하면 오류 메시지를 모델에 돌려주고 고쳐 오게 하는 것
패턴 21과 22를 가르는 실무 기준입니다. 이 표만 기억해도 충분해요.

⚠️ 언제 잘 작동하나

2025년 6월 기준 —
코드 실행 환경은 입력이 아주 엄격히 통제되거나
Reflection이 가능한 샌드박스에서 돌지 않는 한
신뢰도가 떨어지는 편
✅ Code Execution은 생성되는 코드가 좁은 DSL이고 실행 환경에 파서가 있을 때 더 잘 작동합니다 — 예제의 Graphviz 코드가 그런 경우입니다.
조건판단
좁은 DSL + 파서 있음
Graphviz DOT · Mermaid · SQL		잘 작동한다
범용 프로그래밍 언어
임의의 파이썬 코드		엄격한 통제나 Reflection 없이는 위험
💡 왜 좁은 DSL이 유리한가 — 할 수 있는 일이 애초에 적기 때문입니다. DOT으로는 파일을 지울 수도, 네트워크를 부를 수도 없습니다.
패턴 21의 "무엇을 할 수 있는지 미리 좁혀 두라"는 원칙이 여기서도 통합니다.
