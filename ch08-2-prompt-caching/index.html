8.2.2 해법

어디에 캐시할 것인가
요청 전체가 반복될 필요도 없습니다. 일부만 반복돼도 동작합니다.

📡 가장 큰 구분 — 클라이언트 측 vs 서버 측

💻 클라이언트 측

• 지연 시간 감소 폭이 가장 크다
• 캐시 운영 책임을 내가 진다
• 같은 클라이언트에서 반복되는 요청에만 통한다
☁️ 서버 측

• 분산된 클라이언트가 많을 때(원격 LLM에 직접 접근하는 모바일 앱 등)
• Anthropic · OpenAI · 구글 같은 모델 제공자를 쓴다면 좋은 선택지
🍳 비유 — 식당에 손님이 옵니다. 세 가지 방식이 있어요.
① 완성된 요리를 냉장고에서 꺼내 준다(응답 캐시)
② 메뉴 이름이 조금 달라도 같은 요리로 친다(시맨틱 캐시)
③ 육수는 미리 우려 놓고, 주문 들어오면 그 육수로 요리를 새로 한다(프리픽스 캐시)
무엇을 재사용속도창의성
응답 캐시
클라이언트		완성된 응답가장 빠름 (LLM 호출 0)매번 똑같은 답
시맨틱 캐시
클라이언트		비슷한 질문의 응답매우 빠름뉘앙스 손실 가능
프리픽스 캐시
서버		모델의 초기 내부 상태TTFT만 개선그대로 유지
그림 8-4가 이 선택지들을 한 장에 그린 것입니다.

💾 클라이언트 측 — 메모이제이션

생성된 모든 응답은 응답 캐시(response cache)라 부르는 키-값(KV) 캐시에 저장된다 — 키는 프롬프트, 값은 응답.

✅ 캐시 적중 시 — 네트워크 호출이 아예 없으니 생성 지연 시간이 줄고, LLM을 호출하지 않으니 LLM 비용도 절약됩니다.
LangChain — 캐시를 고르고 set_llm_cache 를 호출
from langchain_core.caches import InMemoryCache
from langchain_core.globals import set_llm_cache

set_llm_cache(InMemoryCache())

prompt_template = PromptTemplate.from_template("""
    What are the steps to put a freeze on my credit card account?
    """)
chain = prompt_template | model | parser
💡 인메모리 외에 Redis · Cassandra 등도 지원합니다. 어떤 저장소를 고르든 설정 방식은 같습니다 — 캐시를 고르고 set_llm_cache를 부르면, 이후 LLM 호출마다 LangChain이 요청을 쏘기 전에 캐시를 먼저 확인합니다.
모델 제공자의 클라이언트 측 캐싱 — OpenAI

    messages=[{"role": "user", "content": """What is the capital of
Monaco? Provide a detailed answer."""}],

환경변수 하나로 클라이언트가 응답을 그 디렉터리에 캐시합니다.

🧠 시맨틱 캐싱 — 정확히 일치하지 않아도

❌ 응답 캐싱의 단점 — 텍스트가 정확히 일치해야 한다. 한 글자만 달라도 미스입니다.

이를 피하려면 시맨틱 캐시를 쓴다 — 완전히 같은 질의뿐 아니라 비슷한 질의도 캐시에서 찾는다. 구현 방법은 셋이다.

방법내용
키의 정규형 사용
canonical form		요청의 정규 표현을 키로 쓴다 — 동의어를 치환하고, 의미를 바꾸지 않는 구절을 제거. 어간 추출(stemming)이나 텍스트 정규화 같은 NLP 연산으로 만든다
같은 응답에
여러 키 사용		최초 요청에 대해 의미적으로 비슷한 요청들을 생성하고, 그 모든 유사 키에 같은 응답을 저장한다 → 이후 비슷한 질의에서 적중 확률이 올라간다
→ 이 덱의 「예제」에서 이 방식을 만들어 봅니다
임베딩 기반
유사도 검색		KV 스토어 대신 벡터 스토어를 써서, 주어진 질의와 충분히 가까운 캐시 요청을 찾는다. 오픈소스 GPTCache가 이 방식
data_manager = get_data_manager(CacheBase("sqlite"),
                                VectorBase("faiss", ...))
cache.init(
    embedding_func=onnx.to_embeddings,
    data_manager=data_manager,
    similarity_evaluation=SearchDistanceEvaluation(),
)
cache.set_openai_key()
⚠️ 임베딩 방식의 문제 — 유사도 임계값을 찾아야 한다. 캐시 적중 시의 거짓 양성과 미스 시의 거짓 음성 사이에서 균형점을 잡아야 한다.

⚠️ 시맨틱 캐싱 전반의 단점 — 살짝 다른 질의에 같은 응답이 돌아갈 수 있고, 그 과정에서 뉘앙스가 사라진다. 시스템이 계속 같은 응답을 내놓으면 덜 "똑똑해" 보일 수도 있다.
정확도를 조금 내주고 적중률을 사는 거래입니다.

☁️ 서버 측 — 프리픽스 캐싱

요청 전체를 캐시하는 대신, LLM 제공자가 프롬프트의 공통 부분(대개 길다란 시스템 프롬프트나 예시들)에 대해 이전에 계산한 모델 내부 상태를 재사용한다. 같은 프리픽스를 쓰는 이후 프롬프트들은 중복된 초기 계산을 건너뛴다.

❓ "초기 상태"가 뭔가요 — LLM은 긴 시스템 프롬프트를 읽으면서 내부에 어떤 계산 결과(KV 캐시)를 쌓습니다. 시스템 프롬프트가 매번 같다면 이 계산도 매번 같습니다. 그러니 한 번 계산해서 저장해 두고 불러 쓰자는 것이죠.
이점내용
창의성에 영향을 주지 않는다생성은 매번 LLM이 수행하며, 재사용되는 것은 초기 상태뿐. 클라이언트 측과 달리 미리 계산된 응답이 쓰이지 않는다
TTFT를 크게 줄인다전체 지연 시간에는 큰 영향을 주지 않지만, 초기 상태를 불러오므로 첫 토큰까지의 시간(TTFT)은 크게 준다. 응답 스트림이 시작되기를 기다리는 채팅 같은 스트리밍 앱에서 특히 유익 — Anthropic의 연구가 훌륭한 결과를 보였다
🔢 최소 토큰 수 조건 — OpenAI · Anthropic · 구글은 요즘 프롬프트를 암묵적으로 캐시하지만, 캐시되려면 프롬프트가 최소 토큰 수를 넘겨야 합니다. 제공자 · 모델마다 다르지만 대체로 1,024 토큰을 넘어야 합니다. 캐시된 응답의 토큰 비용이 더 저렴하므로 전체 비용이 줄어듭니다.
🔧 독점 모델만의 것이 아니다 — vLLM 같은 오픈소스 추론 서버도 지원하며, 사실 자동 프리픽스 캐싱을 처음 지원한 것이 vLLM입니다.
🎬 컨텍스트 캐싱(context caching) — 서버 측의 또 다른 선택지. 사용자가 프롬프트와 함께 주는 비디오 · 문서 · 이미지 같은 추가 컨텍스트를 캐시한다. Gemini가 멀티미디어 콘텐츠를 캐시해 이후 요청에서 재사용하는 방법을 제공합니다.
답을 통째로 재사용하면 빠르지만 뻣뻣해지고, 준비 과정만 재사용하면 유연하지만 절약 폭이 작습니다.

8.2.3 예제

디스크 기반 캐시
서버 측은 제공자가 암묵적으로 해 주므로 클라이언트 측 구현에 집중합니다.

📁 프롬프트를 해싱해 파일명으로

Redis 같은 KV 데이터베이스를 쓰는 대신, 프롬프트를 해싱해 그 해시를 JSON 데이터 구조의 파일명으로 쓴다.

class PromptCache:
    def __init__(self, cache_dir: str = ".prompt_cache"):
        self.cache_dir = Path(cache_dir)
        self.cache_dir.mkdir(exist_ok=True)
        self.client = Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

    def _get_cache_key(self, prompt: str) -> str:
        """Generate a unique cache key for the prompt."""
        return hashlib.md5(prompt.encode()).hexdigest()

    def _get_cache_path(self, cache_key: str) -> Path:
        return self.cache_dir / f"{cache_key}.json"
def get_cached_response(self, prompt: str) -> Optional[Dict]:
    cache_key = self._get_cache_key(prompt)
    cache_path = self._get_cache_path(cache_key)

    if cache_path.exists():
        with open(cache_path, 'r') as f:
            return json.load(f)
    return None
cached_response = self.get_cached_response(prompt)
if cached_response:
    return cached_response["content"]   # LLM 생성을 건너뛴다
반환값이 None이 아니면 곧바로 이전 응답을 돌려줍니다.

  The requests should be in the same language as the prompt.

  Here is the prompt:
  {prompt}

  Return a JSON array of {self.num_semantic_requests} requests.
  """
  response = self.client.messages.create(...)
  try:
      return json.loads(response.content[0].text)

semantic_requests = self._get_semantic_requests(prompt)
all_requests = [prompt] + semantic_requests

for request in all_requests:

고려사항내용
멀티테넌트 사용
multitenant use		여러 테넌트가 함께 쓴다면 캐싱은 한 사용자의 정보가 다른 사용자에게 새어 나갈 위험을 만든다.
→ 직접 구현한다면 사용자 식별자를 캐시 키의 일부로
→ 제공자의 암묵적 캐싱을 쓴다면 시스템 프롬프트에 사용자 식별자를 넣어 사용자별로 만든다
→ 더 정교하게는 연합 학습(federated learning) 접목 — Gill 외(2024)
캐시 무효화
invalidation		구성할 때 각 항목을 언제 무효화할지 정해 두라. 제공자들은 TTL을 5분으로 잡지만 더 길게 설정할 수 있는 경우가 많다.
→ 모델 버전이 바뀌면 캐시 전체를 무효화하라. 결과가 크게 달라지기 때문
클라이언트 측 대
서버 측		제공자의 암묵적 서버 측 캐싱은 비용을 아껴 주지만 지연 시간 개선은 TTFT에 한정된다 — 캐시로 초기 상태를 불러올 뿐 여전히 응답 전체를 생성하니까.
→ 자주 오는 요청의 전체 지연 시간을 줄이는 게 목표라면 클라이언트 측을 택하라
비용을 아끼려면 서버 측으로 충분
전체 지연 시간을 줄이려면 클라이언트 측
